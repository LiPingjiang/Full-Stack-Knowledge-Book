# 13.1 岗位拆解与知识映射

## 不是"会写 Hive SQL 的人"，而是"能把多国外卖数据建成可靠数仓并支撑 AI 知识库的人"

如果把这个岗位一句话说清楚，它招的不是"会写几条 Hive SQL 的 ETL 开发"，而是一个能把**多国家、多时区、多语言、多币种**的外卖业务数据体系，从原始状态推进到稳定数仓 + 数据中台 + AI 知识库的复合型数据研发工程师。

它面对的问题不是单点的"跑个 SQL 出报表"，而是一组同时成立的矛盾：

1. **多国多时区**：同一套离线调度，不能在北京时间 0 点统一跑一次完事——沙特 UTC+3、香港 UTC+8、巴西 UTC-3，各 region 需要按本地时区切天统计；
2. **多语言多币种**：搜索词、商家名、商品名可能包含阿拉伯语、繁体中文、葡语，跨 region 汇总 GMV 需要汇率折算，不能简单相加；
3. **流量与营销耦合**：外卖场景的流量链路（曝光→点击→进店→加购→下单→支付→配送）和营销链路（发券→核销→ROI）深度交织，归因口径复杂；
4. **离线实时双链路**：日级报表走离线 Spark/Hive，实时大屏走 Flink，两者必须对账一致；
5. **数据治理 + AI 基建并重**：不仅要保障数据稳定性和质量，还要把数仓中的结构化知识（指标口径、表说明、业务规则）做成 AI 可检索的 RAG 知识库。

这决定了这个岗位的核心画像：**维度建模硬功夫 + 大数据全栈 + 多时区/多语言/多币种领域理解 + 数据治理 + RAG 知识库工程化**。

## 从 JD 逐条翻译岗位硬门槛

### 硬门槛 1：本科 + 三年以上流量或营销方向数仓建设经验

关键不是"三年数仓"，而是**流量或营销域**——曝光、点击、转化、券、ROI、A/B 实验、归因。在外卖场景里对应首页推荐流量、搜索流量、发券营销、商家曝光、漏斗转化。

做过电商/出行/内容平台的流量数仓可以对齐包装；做过纯财务/风控数仓则方向不匹配。

**知识映射：**
- ✅ [6.7 数据仓库设计](../part6-bigdata/07-数据仓库设计.md) — 分层建模、事实表与维度表设计
- ✅ [6.1 大数据技术栈全景](../part6-bigdata/01-大数据技术栈全景.md) — 数仓分层 ODS/DWD/DWS/ADS
- ⚠️ 本章补充：流量域的 MVMC 页面事件模型、营销域的活动周期事实表设计

### 硬门槛 2：概念、逻辑、物理三层建模 + 各类建模方法落地

概念层（业务主题域划分）→ 逻辑层（Kimball 星型/雪花、维度建模、总线架构）→ 物理层（Hive 分区分桶、数据湖表格式、OLAP 物化视图）。

面试必问：ODS/DWD/DWS/ADS 怎么分、缓慢变化维（SCD Type 1/2/3）怎么处理、宽表 vs 星型怎么选、营销活动周期型事实表怎么建模型。

**知识映射：**
- ✅ [6.7 数据仓库设计](../part6-bigdata/07-数据仓库设计.md) — Inmon vs Kimball、星型/雪花/星座模型、SCD 与拉链表
- ⚠️ 本章补充：多 region 维度表设计（region 作为退化维度还是独立维度）、多语言 SCD 处理

### 硬门槛 3：Hadoop/Spark/Hive/Flink/数据湖/OLAP 全栈，懂适配场景与优化

不是"用过"，是能讲清**为什么这个组件放这一层**：

- 离线：Hive/Spark SQL 调优（数据倾斜、CBO、小文件、分区裁剪）
- 实时：Flink（状态管理、watermark、exactly-once、反压）
- 数据湖：Iceberg/Hudi/Paimon 至少其一，懂 schema evolution、time travel
- OLAP：ClickHouse/Doris/StarRocks 至少熟一种，知道什么时候用预聚合、物化视图、明细查询

## 这份岗位最看重的能力组合

### 第一类：数仓建模硬功夫

- 分层建模：ODS / DWD / DWS / ADS 或 Medallion（Bronze/Silver/Gold）
- 事实表与维度表设计：事务事实表、周期快照事实表、累积快照事实表
- SCD 处理：Type 1/2/3、拉链表
- 宽表 vs 星型：什么时候用宽表提升易用性、什么时候保持星型减少冗余
- 主题域划分：不重不漏、每域约 20 张表

### 第二类：大数据全栈工程能力

- Hive/Spark 离线调优：数据倾斜、小文件、分区裁剪、CBO
- Flink 实时计算：状态、watermark、exactly-once、反压
- 数据湖：Iceberg/Hudi/Paimon、schema evolution、time travel
- OLAP：Doris/ClickHouse/StarRocks、物化视图、预聚合

### 第三类：国际化外卖领域理解

- 多时区改造：离线调度多班车、天表按本地时区切分、BI 看板动态时区
- 多语言处理：维度表多语言属性、搜索词多语言分词
- 多币种处理：跨 region GMV 汇总汇率折算
- 外卖漏斗：曝光→点击→进店→加购→下单→支付→配送→核销
- 营销归因：发券→核销→ROI、首次/末次/全链路归因口径

### 第四类：数据治理 + AI 基建

- 数据质量：DQC 规则、波动监控、SLA 分级
- 元数据管理：血缘采集、口径管理、智能巡检
- RAG 知识库：数仓元数据 → Embedding → 向量库 → 智能问答

## 覆盖度总结

这份案例对全书的覆盖度非常高，尤其是第六章和第七章：

- **已覆盖的通用能力**：分层建模、Spark 调优、Flink 实时、数据湖、OLAP、数据质量、元数据治理、RAG 实战；
- **需要在本章补充的能力**：多时区数仓改造、多语言维度建模、多币种指标设计、外卖流量/营销域事实表设计、归因口径、数仓元数据 → RAG 知识源方案。

如果说第十二章验证的是"第六章的数据工程体系离一个现代云数仓案例还差哪几块拼图"，那么第十三章验证的是：**在传统数仓能力之上叠加国际化领域理解和 AI 基建能力，能不能拼成一个完整的复合型数据研发岗位故事。**
