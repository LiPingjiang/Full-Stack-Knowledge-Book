# 国际化外卖数据开发岗位 · 一页速览

> 某出行平台国际化外卖业务线 · 流量/营销域数仓建设 + 数据中台基建 + 数据治理 + AI 知识库

---

## 岗位本质

不是纯 ETL 开发，而是"数仓建模 + 大数据全栈 + 国际化领域 + AI 基建"的复合型数据研发。要解决的核心矛盾：多国多时区运营下，如何让同一套数仓同时服务各 region 本地化运营决策和跨 region 统一对比分析。

## 三条职责 → 四类能力

| 职责 | 核心能力 | 关键词 |
|------|----------|--------|
| 业务数据需求 + 中台基建 | 分层建模、事实表/维度表设计 | ODS→DWD→DWS→DWT→ADS、MVMC 事实表、营销归因 |
| 数据治理 + 稳定性 | DQC 规则、SLA 分级、血缘追溯 | 预检/灰度/回滚/告警四件套 |
| 新技术 + 架构升级 + AI 落地 | 数据湖、流批一体、RAG 知识库 | Iceberg/Paimon、Flink+Doris、向量库+Embedding |

## 国际化三大独有挑战

**多时区**：北京时间 0 点统一调度对外卖失效——沙特错 5 小时、巴西错 11 小时，午高峰被切成两天。解决方案：ODS 按 UTC 保真存储，DWS 按 region 本地时区切天，调度系统按各 region 本地 0 点触发多时区班车。

**多语言**：商家名/商品名/搜索词可能包含阿拉伯语（RTL）、繁体中文、葡语。解决方案：独立翻译维度表（`dim_xxx_i18n`），DWD 保留原始搜索词，DWS 做标准化，DWT 按需跨语言映射。

**多币种**：跨 region GMV 不能直接相加。解决方案：DWD 保留原币种，DWS 折算 USD（T+1 汇率维表，按交易日期关联），DWT 跨 region 以 USD 汇总。

## 分层架构要点

```
ODS  → UTC + region 分区，保真不转换
DWD  → 时间双轨制（UTC + 本地时区），按业务过程建事实表
DWS  → region × 本地时区 × 天 聚合，口径收口
DWT  → 跨事实表整合，漏斗 + 归因宽表（首次/末次/全链路三口径）
ADS  → BI 看板（多时区动态筛选）+ Flink 实时大屏 + API
```

## 八条实战教训（Keeta 2023-2026）

1. **多时区改造是全链路工程**——覆盖 ODS 到 BI 全链路，不是只改调度参数
2. **一开始就要着眼"万物到家"**——餐饮 SPU/SKU 模型无法承载零售多维规格
3. **商品和营销最容易踩坑**——不同国家营销玩法和类目体系差异大
4. **数据保障要四种能力**——预检、灰度发布、回滚、监控告警
5. **实时与离线对账注意编码差异**——order_id 编码不同不可直接 join
6. **指标口径变更必须监控和周知**——枚举值变化、金额边界、实验污染均引发过事故
7. **跨时区抹平潮汐效应**——停服窗口需按各 region 低峰分别安排
8. **坚持分层设计，边行军边修路**——不牺牲架构质量换短期交付
