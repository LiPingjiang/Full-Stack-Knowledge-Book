# 13.5 面试准备路径与高频问题

## 准备优先级

### 第一优先级：把"国际化场景下的数仓分层"讲顺

你至少要能用 3 分钟讲清楚：
- 为什么 ODS 保持 UTC 存储，DWS 按各 region 本地时区切天
- 为什么 DWD 事实表采用时间双轨制（UTC + 本地时区）
- 为什么不能在北京时间 0 点统一调度一次
- 多时区班车的三种方案各自优缺点

如果这部分讲不顺，后面讲 Spark 调优和 RAG 知识库都很难加分。

### 第二优先级：讲清流量域和营销域的事实表设计

面试官会要求你画图或口述：
- 流量域的 MVMC 页面事件事实表怎么设计，粒度是什么
- 营销域的发券→核销→ROI 链路怎么建事实表
- 归因口径在 DWD 和 DWT 层的分工（DWD 只记事件，DWT 做归因）
- 多币种在哪一层做折算，为什么

### 第三优先级：大数据全栈调优实战

面试官会追问具体技术细节：
- Spark 任务数据倾斜怎么定位、怎么改、资源怎么调
- Flink 实时 GMV 和离线对账差 0.3% 怎么查
- 数据湖（Iceberg/Paimon）相比 Hive 表在国际化场景下有什么优势
- Doris/ClickHouse 物化视图什么时候用

### 第四优先级：RAG 知识库方案

这是 JD 里的加分项，但面试官很可能会深挖：
- 如果让你给数据团队搭 RAG 知识库，数仓侧要产出什么
- 向量库怎么选，为什么
- Embedding 更新怎么增量跑
- 数仓知识文档和通用文档的分块策略有什么不同

### 第五优先级：数据治理和稳定性

成熟的数据工程面试很少只问"怎么建"，一定会继续追问：
- 多时区下 SLA 怎么定义
- 数据质量规则体系怎么建
- 小文件怎么治理
- 血缘采集怎么做

## 高频问题与参考回答框架

### 问题 1：如果让你给国际化外卖设计一套数仓，你会怎么分层？

**答题框架：**

先按五层分：ODS 保真接入（UTC + region 分区，append-only），DWD 按业务过程建明细事实表（时间双轨制：UTC 原始值 + 本地时区派生值），DWS 按 region × 本地时区 × 天 聚合收口指标口径，DWT 跨事实表整合漏斗和归因宽表，ADS 面向 BI 看板和 API 输出。

重点说明三件事：
1. 多时区是核心改造——ODS 保持 UTC 不做转换，DWS 按各 region 本地时区切天，调度系统按各 region 本地 0 点分别触发班车；
2. 币种折算在 DWS 层做——DWD 保留原币种，DWS 增加 USD 折算字段，跨 region 汇总以 USD 为统一口径；
3. 归因不在 DWD 做——DWD 只记录事件，归因在 DWT 层建宽表同时存储首次/末次/全链路三种口径。

最后补一句：ADS 层直接对接实时大屏（Flink + Doris）和离线报表，多时区动态筛选在 BI 看板层实现。

### 问题 2：为什么不能在北京时间 0 点统一调度？

**答题框架：**

以外卖场景为例。外卖业务强本地运营、高峰时段明显，午高峰 11-14 点、晚高峰 17-21 点是核心运营时段。以沙特 UTC+3 为例，北京时间 0 点等于沙特时间 5 点，统一调度意味着每日统计的是沙特时间 5:00 到次日 5:00 的数据——午高峰被完整包含但跨了两天，日 GMV 和日活都会失真。

解决方案是多时区班车：调度系统（如 Crane/Airflow）的 Cron 表达式携带时区参数，各 region 的天表任务在该 region 本地 0 点后触发。ETL 工具通过业务线参数（如 `--bn sa`）指定时区，自动渲染时间条件。BI 看板层也支持多时区动态筛选——日期筛选器关联时区，按各 region 当地时间偏移查询。

### 问题 3：画一张外卖营销活动（发券→核销→ROI）的离线+实时数仓分层图

**答题框架：**

离线链路：ODS 接入发券日志和支付 Binlog → DWD 建 `fact_coupon_issue`（发券事实）和 `fact_payment`（支付事实）→ DWS 建 `dws_region_daily_marketing`（各 region 每日营销汇总：发券量/领券量/核销量/补贴金额/带券 GMV）→ DWT 建 `dwt_marketing_attribution`（归因宽表：首次/末次/全链路三种口径）→ ADS 建 `ads_marketing_roi_report`（ROI 报表）。

实时链路：发券 Binlog → Kafka → Flink 实时聚合核销金额 → Doris → BI 实时看板。

关键点：DWD 层不做归因，只记录事件。归因在 DWT 层做，同时存三种口径。ROI = 带券 GMV / 补贴金额，跨 region 时先折算为 USD 再相除。

### 问题 4：Spark 任务数据倾斜怎么定位、怎么改？

**答题框架：**

定位：先看 Spark UI 的 Task Duration 分布，如果个别 Task 耗时远超中位数就是倾斜。再看是哪个 key 倾斜——外卖场景常见的是大商家（如麦当劳的订单量远超普通商家）或头部城市。

改法：看倾斜程度选方案。轻度的用 `broadcast join`（如果小表<5GB）把 map 端 join 消除 shuffle。中度的用 salting（加盐打散）：给倾斜 key 加随机后缀 `merchant_id_0` ~ `merchant_id_9`，扩 10 倍后均匀分布到 10 个 Task，join 完再去掉后缀。重度的用自定义 partitioner 或 AQE（自适应查询执行，Spark 3.0+ 自动处理中等倾斜）。

资源调整：增加 executor 内存不解决问题（倾斜是数据分布问题不是资源问题），增加 partition 数量可能有帮助（让每个 Task 处理更少的数据）。

详见 [6.4 Spark 数据倾斜治理](../part6-bigdata/04-Spark-数据倾斜治理.md)。

### 问题 5：Flink 实时 GMV 和离线对账差 0.3% 怎么查？

**答题框架：**

按四个维度排查：

1. **时间窗口口径**：实时按 processing time 切窗口，离线按 event time 过滤？如果是，实时窗口可能把跨天边界的订单算错日期。改为两者都用 event time，watermark 设置一致的迟到窗口。

2. **迟到数据处理**：Flink watermark 允许的延迟窗口（如 5 分钟）内的数据会更新之前的窗口结果，但超窗口迟到的数据会被丢弃。离线补跑是全量重算，不会丢。差 0.3% 可能就是被丢弃的迟到数据。

3. **去重逻辑**：实时流式去重（按 order_id 去重，但跨 checkpoint 可能重复）vs 离线批量去重（全局去重），边界 case 可能不一致。检查是否有 "同一订单被算两次" 或 "同一订单被实时丢了一次"。

4. **币种折算**：实时用的是实时汇率还是缓存汇率？离线用的是 T+1 官方汇率？如果汇率口径不同，折算后金额会有差异。统一为 T+1 汇率或说明差异来源。

### 问题 6：跨国家时区/币种口径怎么在维度表里落地？

**答题框架：**

region 既作为退化维度（冗余在事实表中做分区和过滤），也建独立的 `dim_region` 维度表（包含 region 代码、时区、币种、语言、国家名称等属性）。维度表更新时（如某个 region 调整时区或币种），只改维度表，不用改事实表。

币种折算：DWD 保留原币种 `amount_original` + `currency_code`，DWS 增加折算 `amount_usd`，按 T+1 官方汇率关联 `dim_exchange_rate` 维表折算。汇率维表是 SCD，按交易日期关联对应日期的汇率，不能用最新汇率折算历史数据。

跨 region 汇总 GMV 时先各 region 按本币种计算日 GMV，再折算为 USD，最后以 USD 口径相加。直接把不同币种的原金额相加是没有意义的。

### 问题 7：如果让你给数据团队搭 RAG 知识库，数仓侧要产出什么？向量库怎么选？

**答题框架：**

数仓侧要产出四类知识源：表级知识文档（表名/字段/分区/SLA/负责人）、指标口径文档（指标名/定义/公式/统计周期/版本变更）、业务规则文档（归因口径/汇率规则/时区规则/去重逻辑）、SQL 模板库（高频查询模板供 Text2SQL 参考）。

这些知识本来就在元数据系统和指标平台中维护，只需要批量导出为结构化文档，分块后做 Embedding 写入向量库。

向量库选型：自建部署选 Milvus（开源、大规模、HNSW 索引、社区活跃），快速原型选 Weaviate（内置向量化模块、支持混合检索），团队小不想运维选 Pinecone（托管服务）。数仓知识量不大（几万到几十万 chunk），HNSW 索引延迟足够低。

分块策略：按表分块（一张表一个 chunk）、按指标分块（一个指标一个 chunk）、按规则分块（一条规则一个 chunk），chunk metadata 记录关联关系（"这个指标在哪张表里算"）。混合检索：向量相似度 + 关键词 BM25（表名/字段名用精确匹配比语义匹配更准确），top-20 后用 Cross-Encoder rerank。

增量更新：监听元数据变更事件，对变更文档重新生成 chunk 并更新向量库，保留版本历史（旧口径标记 `valid_to`）。

详见 [7.1 RAG 实战](../part7-ai-engineering/01-RAG实战.md) 和 [6.19 元数据管理与智能数据治理](../part6-bigdata/19-元数据管理与智能数据治理.md)。

### 问题 8：数据湖（Iceberg/Paimon）相比 Hive 表在国际化场景下有什么优势？

**答题框架：**

三个核心优势：

1. **Schema evolution**：国际化业务变化快，新 region 上线可能需要给所有表加 region 字段。Hive 加字段需要重写分区甚至整张表，Iceberg/Paimon 支持 schema 演进（add column 不需要重写），更适合快速迭代。

2. **Time travel**：国际化场景下口径变更频繁（归因口径改了、汇率源换了），time travel 能回到历史某个 snapshot 查看口径变更前的数据，便于审计和对比。

3. **分区演进**：随着业务发展，分区策略可能从 `dt` 变为 `dt + region`，Hive 不支持分区演进（需要重建表），Iceberg 支持 partition evolution（历史数据保持旧分区，新数据用新分区）。

Flink + Paimon 的流批一体方案在实时入湖场景下也有优势——一条链路同时产出实时和离线数据，减少流批不一致问题。详见 [6.9 湖仓一体](../part6-bigdata/09-湖仓一体.md)。

## 一个 90 秒自我表达模板

> "如果把国际化外卖数据开发这个岗位抽象一下，我理解它不是单纯的 Hive SQL 开发，而是一个'数仓建模 + 大数据全栈 + 国际化领域 + AI 基建'的复合角色。在数仓分层上，我会用 ODS/DWD/DWS/DWT/ADS 五层，但关键改造是时间双轨制——ODS 按 UTC 保真存储，DWS 按各 region 本地时区切天，调度系统按各 region 本地 0 点分别触发班车。在流量域，我会建 MVMC 页面事件事实表记录曝光/点击/搜索事件；在营销域，我会按业务过程建发券和支付事实表，归因口径在 DWT 层做，同时保留首次/末次/全链路三种口径。币种折算在 DWS 层做——DWD 保留原币种，DWS 折算为 USD 供跨 region 汇总。实时链路用 Flink 直写 Doris 做实时大屏，和离线做流批对账。在 AI 基建方面，我会把数仓的表结构、指标口径、业务规则结构化为知识文档，分块做 Embedding 写入向量库，支撑数据团队的智能问答——这本质上是数仓元数据的自然延伸，不是一个独立的 AI 项目。"

这个模板的重点不是"面面俱到"，而是让面试官在一分半钟内听到四件事：
- 你懂国际化场景的特殊性（多时区、多币种）；
- 你懂分层与取舍（哪一层做什么、归因在哪做）；
- 你懂实时和离线双链路；
- 你能把 AI 知识库自然地长在数仓之上。

## 推荐反问

1. 现在团队面临的最大数据挑战是接入混乱、口径混乱，还是多时区改造还没做完？
2. 多个 region 的离线调度目前是已经做了多时区班车改造，还是仍在用北京时间统一调度？
3. 实时链路和离线链路目前是分开的两套，还是在做流批一体的整合？
4. JD 里提到的"企业知识库 + 向量数据库"，是已经有雏形了需要优化，还是从 0 到 1 要建？
5. 这个岗位更偏数据平台基建，还是更偏面向业务方的需求交付？

好的反问不是礼貌动作，而是在确认：**这家公司到底需要一个"搭平台的人"，还是一个"接需求的人"，还是两者兼备的人。**
