# 13.2 国际外卖数仓架构全景

## 先从业务形态反推数据域

国际外卖平台和国内外卖最大的区别，不在于业务流程本身（都是用户下单→商家接单→骑手配送），而在于**同一套业务流程在不同国家的时区、语言、币种、法规下运行**。这意味着数仓架构要在"统一"和"本地化"之间找平衡。

从业务形态可以直接反推出七类数据域：

| 数据域 | 典型内容 | 工程特征 |
|--------|----------|----------|
| 流量域 | 页面曝光、点击、搜索、推荐、首页 feed | 埋点驱动、事件粒度、多语言搜索词 |
| 交易域 | 下单、支付、退款、取消、核销 | 事务驱动、多币种金额 |
| 配送域 | 接单、分配骑手、取餐、送达 | 状态流转、ETA 预估 |
| 营销域 | 优惠券发放/领取/核销、活动配置、补贴 | 活动周期型、归因复杂 |
| 用户域 | 用户画像、注册、留存、价值分层 | 跨 region 同一用户识别 |
| 商家域 | 商家信息、商品、类目、营业状态 | 多语言名称、多 region 类目映射 |
| 归因域 | 激活归因、订单归因、唤起归因 | 跨域关联、多种归因口径 |

这决定了它不是一个纯离线数仓，而是一个**离线 + 实时 + AI 知识库的三层复合平台**。

## 推荐的分层架构：多时区友好的 ODS → DWD → DWS → DWT → ADS

国际外卖场景下，标准的 ODS/DWD/DWS/ADS 四层仍然适用，但每一层都需要增加多时区和多 region 的适配。

```text
数据源
  ├─ APP/Web 埋点日志（多 region、多语言）
  ├─ 业务 MySQL（订单、支付、配送、营销系统）
  ├─ CDC 日志（Binlog 变更流）
  ├─ 外部数据（天气、汇率、地理参考）
  └─ 历史文件 / 第三方回传
          ↓
ODS（贴源层，按 UTC 时间 + region 分区，append-only）
          ↓
DWD（明细层，按业务过程建事实表，时间字段保留 UTC 原始值 + 本地时区派生值）
          ↓
DWS（汇总层，按 region × 本地时区 × 统计粒度 聚合，公共指标口径收口）
          ↓
DWT（主题层，跨业务过程整合宽表，漏斗/归因/用户价值）
          ↓
ADS（应用层，面向 BI 看板、数据产品、API）
```

### ODS 层：按 UTC 存储，保留原始时区信息

这一层的关键原则是**保真接入，不做时区转换**。

建议：
- 分区设计：`dt`（UTC 日期）+ `region`（地区标识），或使用 `dt_utc` + `hour_utc` 更细粒度
- 时间字段：保留原始的 `event_time_utc`（UTC 时间戳），同时冗余 `event_time_local`（本地时区时间）和 `timezone`（时区标识）
- 埋点日志以 JSON 半结构化优先落，后续在 DWD 层再结构化展开
- MySQL/CDC 数据按业务系统原貌接入，不做字段转换

这层的目标不是好查，而是**可回放、可审计、可跨时区重新解释**。

### DWD 层：按业务过程建事实表，时间双轨制

这一层是整个平台的工程核心。每个业务过程对应一张明细事实表。与国内数仓的关键区别是**时间字段采用双轨制**：每条记录同时保留 UTC 时间和本地时区时间。

核心事实表：

**流量域：**
- `fact_page_event`：页面事件事实表（MVMC 模型：模块-视图-模型-点击），每行一条埋点日志
- `fact_search_event`：搜索事件事实表（搜索词、搜索来源、搜索结果数）

**交易域：**
- `fact_order`：下单事实表（订单 ID、用户、商家、金额、region、币种）
- `fact_payment`：支付事实表
- `fact_refund`：退款事实表

**配送域：**
- `fact_delivery`：配送事实表（接单时间、分配骑手时间、取餐时间、送达时间）

**营销域：**
- `fact_coupon_issue`：发券事实表
- `fact_coupon_redeem`：核销事实表
- `fact_marketing_activity`：营销活动事实表

每张表的关键字段设计要点：
- 时间字段：`event_time_utc`（UTC 时间戳）+ `event_time_local`（本地时间）+ `region` + `timezone`
- 金额字段：`amount_original`（原币种金额）+ `currency_code`（币种代码）+ `amount_usd`（折算 USD 金额，可选在 DWD 或 DWS 层折算）
- 用户标识：`user_id` + `union_id`（跨端去重）+ `device_id`
- 地理维度：`city_id` + `region` + `latitude` + `longitude`

### DWS 层：按 region × 本地时区 × 统计粒度 聚合

这一层是**口径收口的关键层**。与国内数仓不同，聚合维度必须同时包含 `region` 和本地时区切分。

核心汇总表：
- `dws_region_daily_traffic`：各 region 每日流量汇总（按本地时区切天）
- `dws_region_daily_order`：各 region 每日订单汇总
- `dws_user_daily_behavior`：用户每日行为汇总
- `dws_merchant_daily_performance`：商家每日表现汇总
- `dws_region_daily_marketing`：各 region 每日营销指标汇总

关键设计决策：**天表的分区是按 region 本地时区切的**。沙特的天表分区 `dt=2025-09-15` 对应的是沙特时间 9 月 15 日 0:00 到 23:59，而不是北京时间 9 月 15 日。这意味着同一个 UTC 时间可能落在不同 region 的不同日期分区里。

### DWT 层：跨业务过程整合，漏斗与归因

这一层跨事实表整合，产出面向分析场景的主题宽表：

- `dwt_user_funnel_daily`：用户漏斗宽表（曝光→点击→进店→加购→下单→支付，按 region × 本地时区 × 天）
- `dwt_marketing_attribution`：营销归因宽表（发券→核销→ROI，多种归因口径）
- `dwt_user_value_monthly`：用户价值月表（LTV、复购率、留存）
- `dwt_merchant_score_monthly`：商家评分月表

### ADS 层：面向消费场景

- `ads_region_realtime_dashboard`：实时大屏（Flink 直写 Doris/ClickHouse）
- `ads_marketing_roi_report`：营销 ROI 报表
- `ads_user_retention_cohort`：用户留存 cohort 分析
- `ads_api_city_snapshot`：面向 API 的城市快照

## 离线链路：多时区班车调度

国际外卖数仓与传统数仓在离线链路上最大的区别是**多时区班车调度**。

### 问题：北京时间 0 点统一调度为什么不行

以沙特为例（UTC+3），北京时间 0 点等于沙特时间 5 点。如果沿袭国内模式在北京时间 0 点后调度，每日统计结果是沙特时间 5:00 到次日 5:00 的数据，而不是预期的沙特时间 0:00 到次日 0:00。外卖业务有明显的午高峰和晚高峰，如果时区不对齐，高峰时段的订单可能被切到两天。

### 方案：多时区班车

- **方案一**：DWD/DWS 层按小时表（hourly partition）建设，DWT/ADS 层按 region 本地时区从小时表聚合出天表。优点是底层统一，缺点是小时表存储量大。
- **方案二**：直接在调度系统（如 Crane/Airflow）中支持多时区触发——Cron 表达式携带时区参数，各 region 的天表任务在该 region 本地 0 点后触发。ETL 工具（如 sqlweaver）支持 `--bn hk`、`--bn sa` 等参数指定时区，自动渲染时间条件。
- **方案三**：底层保持 UTC 存储，所有天表按 UTC 建设，BI 看板层做动态时区转换——日期筛选器关联时区，按各 region 当地时间 0 点到此刻分别查询。

实践中通常是方案二 + 方案三的组合：调度层按各 region 本地时区触发班车，BI 看板层支持多时区动态筛选。

### Spark 任务的数据倾斜处理

外卖场景下数据倾斜高发场景：
- 大商家（如麦当劳、星巴克）的订单量远超普通商家
- 头部城市（如利雅得、香港）的订单量远超其他城市
- 某些 region 的数据量远超其他 region

处理方案详见 [6.4 Spark 数据倾斜治理](../part6-bigdata/04-Spark-数据倾斜治理.md)，核心手段：salting（加盐打散）、broadcast join（小表广播）、自定义 partitioner、AQE（自适应查询执行）。

## 实时链路：Flink + OLAP 双时区

### 实时 GMV 大屏

链路：Binlog CDC → Kafka → Flink 实时聚合 → Doris/ClickHouse → BI 看板

关键设计：
- Flink 窗口按 event time（而非 processing time）切分，watermark 处理迟到数据
- 实时大屏指标同时提供 UTC 口径和各 region 本地时区口径
- 跨 region 汇总时先按各自币种计算，再在展示层按汇率折算

### 流批对账

实时链路（Flink）和离线链路（Spark/Hive）产出的同一指标会有差异。面试高频追问"实时 GMV 和离线对账差 0.3% 怎么查"，排查思路：
- 检查时间窗口口径是否一致（实时按 processing time，离线按 event time？）
- 检查迟到数据处理方式（Flink watermark 允许的延迟窗口 vs 离线补跑全量）
- 检查去重逻辑（实时流式去重 vs 离线批量去重，边界 case 可能不一致）
- 检查币种折算（实时用的是实时汇率还是缓存汇率？离线用的是 T+1 汇率？）

## AI 知识库层：数仓元数据 → RAG 知识源

这是这个岗位 JD 中"企业知识库 + 向量数据库 + RAG 智能问答"的落地位置。

### 整体架构

```text
数仓元数据（表结构、字段含义、指标口径、业务规则、SQL 模板）
  ├─ 结构化抽取 → Markdown 文档 / JSON Schema
  ├─ 文档分块（chunk + overlap）
  ├─ Embedding 模型 → 向量
  └─ 写入向量库（Milvus / Weaviate）
          ↓
用户自然语言提问
  ├─ 意图识别（是查数、问口径、还是问表结构？）
  ├─ 混合检索（向量相似度 + 关键词 BM25 + Rerank）
  ├─ 上下文组装 → LLM 生成回答
  └─ 如果是查数请求 → Text2SQL → 数仓执行 → 结果返回
```

### 数仓侧需要产出什么

1. **表级知识文档**：每张表的用途、字段列表、分区策略、更新频率、数据源、负责人
2. **指标口径文档**：每个指标的名称、定义、计算公式、统计周期、适用 region、版本变更历史
3. **业务规则文档**：归因口径说明、汇率折算规则、多时区切天规则、去重逻辑
4. **SQL 模板库**：高频查询的 SQL 模板，供 Text2SQL 参考和复用
5. **数据血缘图**：表与表之间的依赖关系，供"这个指标的上游数据有哪些"类问题检索

### 向量库选型考虑

- **Milvus**：开源、支持大规模、HNSW/IVF-PQ 索引、社区活跃——适合自建部署
- **Weaviate**：内置向量化模块、支持混合检索（vector + keyword）——适合快速原型
- **Pinecone**：托管服务、免运维——适合团队小、不想维护基础设施的场景

索引选型：HNSW 适合低延迟查询（<10ms），IVF-PQ 适合大规模数据（>1000 万向量）节省内存。实际场景中数仓元数据量不大（通常几万到几十万 chunk），HNSW 足够。

## 这个场景最关键的五个建模决策

### 决策 1：region 是退化维度还是独立维度

region 可以作为退化维度直接冗余在事实表中（一行记录携带 region 字段），也可以建独立的 `dim_region` 维度表（包含 region 代码、时区、币种、语言、国家名称等属性）。

建议两者结合：事实表中冗余 `region` 字段做分区和过滤，同时建 `dim_region` 维度表做属性关联。这样既保证了查询性能（不用 join 就能按 region 过滤），又保证了维度的可维护性（时区/币种等属性变更只改维度表）。

### 决策 2：天表分区按 UTC 还是本地时区

这是一个没有标准答案但必须做决策的问题。实践中的做法：**DWS 层天表按 region 本地时区分区**，这样业务方查沙特的日数据时分区直接对应沙特的日历。ODS 层保持 UTC 分区不变。

### 决策 3：币种折算在哪一层做

DWD 层保留原币种金额（`amount_original` + `currency_code`），不做折算。DWS 层增加 `amount_usd`（折算 USD）字段，使用 T+1 的官方汇率。跨 region 汇总时以 USD 为统一口径。如果需要实时折算，在 ADS 层使用实时汇率 API。

### 决策 4：营销归因口径怎么在模型里落地

不要在 DWD 层做归因——DWD 只记录事件本身。归因在 DWT 层做：建 `dwt_marketing_attribution` 表，同时存储首次归因、末次归因、全链路归因三种口径的关联结果。下游按需选择口径，而不是在 DWD 层就绑定一种归因逻辑。

### 决策 5：多语言维度表怎么建

方案一：维度表增加多语言字段（`name_zh`/`name_en`/`name_ar`/`name_pt`），适合语言种类有限且固定的场景。

方案二：建独立的翻译表（`dim_merchant_i18n`），字段为 `merchant_id` + `lang_code` + `name`，适合语言种类多或频繁新增的场景。

国际外卖场景建议方案二，因为新开城国家会引入新语言，翻译表更容易扩展。

## 一套足够务实的落地方案

如果只给三个月，优先级如下：

### 第一步：建立多时区 ODS + 核心 DWD

先把埋点日志和业务 MySQL 接进来，建好流量域的 `fact_page_event` 和交易域的 `fact_order`。重点：时间字段双轨制（UTC + 本地时区），分区设计包含 region。

### 第二步：做 DWS 汇总层和核心指标口径

按 region × 本地时区 × 天 聚合，统一日活、日单量、日 GMV 等核心指标的口径。这一步最关键的是**与产品/运营对齐归因口径和统计口径**，不能数仓自己定。

### 第三步：实时大屏 + BI 看板

Flink 实时 GMV 大屏 + Doris/ClickHouse OLAP 查询层。多时区动态筛选在 BI 看板层实现。

### 第四步：数据治理 + RAG 知识库

数据质量规则体系、SLA 分级保障、元数据管理。在元数据基础上建设 RAG 知识库，先做表结构和指标口径的智能问答。

这套顺序的核心思想是：**先把"能稳定支撑各 region 的日数据看板"跑通，再谈 AI 知识库和架构升级。**

## 真实世界经验：Keeta 数仓建设的实战教训

以下经验来自 Keeta 搜索推荐团队和境外数据组在 2023-2026 年间的公开实践总结，对国际化外卖数仓建设有直接参考价值。

### 教训一：多时区改造是全链路工程，不是"加一个参数"

Keeta 搜推团队的多时区改造实践表明，改造涉及三个层面：在线逻辑（新增 region 字段传入 fetch 函数）、离线服务逻辑（特征查询页面和算子计算的适配性改造）、离线落盘（新增 region 字段供多时区班车使用）。团队新建了 `hyperFetchV4` 函数而非修改原函数，原因是要保证境内线上稳定性——国际化改造必须做境内外隔离，不能在境内线上逻辑上直接改。

这意味着数仓的多时区改造同样不能只改调度系统，而是要覆盖：ODS 分区策略、DWD 时间字段、DWS 聚合口径、DWT 跨 region 汇总逻辑、BI 看板动态筛选、元数据管理全链路。任何一个环节漏掉 region 维度，都可能导致数据口径不一致。

### 教训二：业务架构要"一开始就着眼于万物到家"

Keeta 早期只面向餐饮做单品类架构设计，后来向零售扩展时发现：餐饮模型不能简单扩字段承载零售，需要额外建设后台类目、类目属性、标品/CSPU、总部商品、库存等完整基础设施。零售业务对数据平台的要求与餐饮完全不同——餐饮是"先选店再选商品"，零售是"先找商品再看哪家有"，商品信息不完整会直接阻断用户决策。

数仓层面的影响是：商品域的事实表和维度表设计必须预留零售扩展性。餐饮的 SPU/SKU 模型不足以承载零售的多维规格、条码、容量、包装、重量等属性。如果一开始只做餐饮维度建模，后续扩展的改造成本巨大。

### 教训三：商品和营销是国际化最容易踩坑的两个领域

闪购早期发展经验表明，"商品"和"营销"两个领域遇到的问题最多。原因是零售品类商家经营 UE 结构与餐饮存在显著差别，营销成本必须在商品颗粒度上做更精细的控制。

在国际化场景下这个问题更突出：不同国家的营销玩法不同（沙特的 Ramadan 期间特殊运营、巴西的分期付款优惠），商品类目体系不统一（同一商品在不同国家的分类可能不同），需要从一开始就设计统一的类目属性底座和灵活的营销事实表。

### 教训四：数据保障平台要有四种保护能力

Keeta 搜推数据保障平台建设针对四个核心问题：监控告警感知能力不足（数据生产流程卡住时没有告警）、无预检能力（未经验证的数据直接发布到线上）、无灰度能力（发布过程中无灰度流程）、无快速回滚能力（出问题后无法快速回滚数据）。

数仓层面同样需要这四种保护能力：预检（PreCheck）——DWD/DWS 任务产出后先做数据质量校验（空值率、波动率、行数对比），通过后才允许下游依赖；灰度发布（GrayRelease）——新口径或新逻辑先在部分 region 或部分数据分区上跑，对比旧口径结果后再全量；回滚（Rollback）——数据异常时能快速回滚到上一版本的数据，基于多版本机制；监控告警（MonitorAndAlarm）——SLA 超时告警、数据质量规则告警、产出延迟告警。

### 教训五：实时与离线对账要注意编码差异

Keeta 搜索流量数据的实践发现：实时和离线的 `order_id` 格式不一样（编码不同），不可直接 join，只能比较指标值。对账分两步：第一步总量对数（分别查实时和离线的总量指标如 count、sum、distinct count），第二步明细数据对比（通过 event_identifier 逐条核对）。

国际化场景下这个问题更复杂：不同 region 的数据编码可能不同，实时流和离线表的 ID 生成策略可能不一致，跨 region 对账时需要先统一编码或改用指标值对比。

### 教训六：指标口径变更必须建立监控和周知机制

Keeta 神会员项目曾发生多起数据口径相关的线上事故：券类型取值对齐问题导致大数据事故——数仓在业务系统调研环节没有充分对齐字段含义、枚举值和使用方式，相近含义的字段没有对齐 gap。交易与营销的金额边界不清导致回退平台预算数值与预期不符。实验用户污染问题——跨业务对接场景缺乏业务差异化分析。

核心教训是三条：数仓对核心字段的枚举值变化要有监控能力，及时感知问题风险；变更周知流程需要触达到一线研发，不能只通知接口人；涉及金额的场景都应该加强告警建设，约定各业务交易与营销的边界。

### 教训七：跨时区会抹平潮汐效应，需要适配运维机制

Keeta 的业务架构思考指出：国内幅员辽阔只用了一个时区，外卖业务的潮汐效应明显。境外业务扩展到多时区后，跨时区的作用会相对抹平潮汐效应，进一步压缩服务停服时间窗口。这意味着数仓的停服窗口和运维节奏需要适配——不能按国内"凌晨停服一次"的模式，而是要找到各 region 的低峰窗口分别做运维。

### 教训八：坚持分层设计，边行军边修路

Keeta 团队的述职复盘总结了两条核心经验：坚持数仓分层设计原则，不为了短期交付而牺牲架构质量；采取"边行军边修路"策略，在支持业务迭代的过程中持续夯实数据底座，避免"烟囱式"开发和脱离业务空谈基建。

走过的弯路包括：前期对潜在卡点评估不足导致交付延迟；为之前的设计不足"打补丁"影响合作方满意度；知识沉淀不足，解决问题的经验缺乏系统性梳理与文档化。后续规划方向是：深化数仓体系建设（围绕供给、场景、用户标签开展主题数据建设），推动指标体系完成治理迁移，探索 AI 赋能应用（智能问数机器人）。
