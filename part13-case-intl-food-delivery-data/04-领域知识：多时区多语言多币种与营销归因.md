# 13.4 领域知识：多时区、多语言、多币种与营销归因

## 这一节在讲什么

这一节不重复通用数仓理论（那些在 [6.7 数据仓库设计](../part6-bigdata/07-数据仓库设计.md) 里已经讲透），而是聚焦国际化外卖场景特有的领域知识。分四个模块：多时区改造、多语言处理、多币种折算、营销归因口径。

## 模块一：多时区改造

### 1.1 为什么多时区是国际化数仓的头号问题

外卖业务有三个特征使得多时区不是"锦上添花"而是"必须解决"：

第一，**强本地运营**。外卖的运营决策——排班骑手、商家补贴、营销活动——都按当地日历进行。如果数据按北京时间切天，沙特运营看到的"今日订单"其实是沙特时间 5 点到次日 5 点，午高峰被切成两天。

第二，**高峰时段明显**。午高峰（11:00-14:00）和晚高峰（17:00-21:00）是外卖最重要的运营时段。如果时区不对齐，高峰时段的数据可能横跨两个"数据日"，导致高峰指标失真。

第三，**多国同时运营**。一个平台同时在香港（UTC+8）、沙特（UTC+3）、巴西（UTC-3）运营，北京统一调度意味着香港还好（时差 0），沙特数据错 5 小时，巴西数据错 11 小时。

### 1.2 三种改造方案对比

| 方案 | 核心思路 | 优点 | 缺点 | 适用场景 |
|------|----------|------|------|----------|
| 小时表 + 本地聚合 | DWD/DWS 按小时分区，DWT 从小时表按 region 时区聚合出天表 | 底层统一、灵活 | 小时表存储量大、聚合计算开销 | region 数量多、时区差异大 |
| 多时区班车调度 | 调度系统按各 region 本地 0 点分别触发天表任务 | 逻辑清晰、存储不膨胀 | 调度复杂度高、跨 region 汇总难 | region 数量适中（3-10 个） |
| UTC 存储 + BI 转换 | 底层全 UTC，看板层动态做时区转换 | 底层最简单 | BI 查询性能差、跨表关联难 | 临时过渡方案，不推荐长期使用 |

实践推荐：**方案二为主，方案一为辅**。核心 region 走多时区班车调度，同时保留小时表供临时分析和跨时区聚合。

### 1.3 ETL 工具层面的时区支持

以美团 sqlweaver 为例（行业通用方案类似）：通过 `--bn hk`（香港）、`--bn sa`（沙特）等业务线参数指定时区，工具自动将 SQL 模板中的时间变量渲染为对应时区的时间条件。例如 `--cts 1714924800`（东八区时间戳）配合 `--bn sa`，自动渲染为沙特时间 `2024-05-06 00:00:00` 对应的时间条件。

调度系统（如 Crane/Airflow）层面：Cron 表达式需要支持指定时区参数，JVM 时区参数需要显式设置 `-Duser.timezone=GMT+08`，跨日判断逻辑需要识别当地时区而非服务器时区。

### 1.4 BI 看板的多时区动态筛选

看板层面需要支持"按 region 当地时间看数"。以美团 BI 仪表板为例的实现方式：
- 组织架构筛选器节点携带时区属性（region → timezone 映射）
- 日期筛选器关联时区开关，动态偏移到各 region 当地日期
- 多 region 同时查询时取各 region 当地日期最大值作为查询日期，各 region 分别按当地时间 0 点到此刻查询
- SQL 层面按 region 分别拼接时间条件：`WHERE (region='SA' AND dt=20250915 AND time BETWEEN '00:00' AND '15:29') OR (region='HK' AND dt=20250915 AND time BETWEEN '00:00' AND '20:29')`

### 1.5 SLA 定义的多时区适配

国内的 SLA 通常承诺"每日 8 点前产出昨日数据"。国际化场景下需要明确：SLA 是按各 region 本地时间承诺（沙特 8 点前产出沙特昨日数据），还是按 UTC 统一承诺？建议按各 region 本地时间承诺，因为运营决策是按本地日历做的。

## 模块二：多语言处理

### 2.1 多语言影响的范围

多语言不是"把界面翻译一下"那么简单，在数仓层面它影响三个维度：

**维度表多语言属性**：商家名称、商品名称、类目路径在不同 region 可能是不同语言。比如同一个连锁品牌在沙特叫 "McDonald's"（英语），在巴西叫 "McDonald's"（葡语拼写相同但上下文不同），在香港叫 "麥當勞"（繁体中文）。

**搜索词多语言**：用户的搜索词包含阿拉伯语、繁体中文、葡语。搜索词分析需要考虑多语言分词、语义理解。不同语言的搜索词可能指向同一个商品/品类。

**埋点数据多语言**：页面上的文案、按钮名称、错误提示在不同语言版本下不同。埋点参数中可能包含本地化文本。

### 2.2 维度表多语言方案

**方案一：宽表多语言列**

```sql
CREATE TABLE dim_merchant (
    merchant_id   BIGINT,
    name_zh       STRING,  -- 中文名
    name_en       STRING,  -- 英文名
    name_ar       STRING,  -- 阿拉伯名
    name_pt       STRING,  -- 葡语名
    -- ...其他维度属性
);
```

优点：查询简单，一个表搞定。缺点：新增语言需要改表结构（DDL 变更），不适合频繁新增语言的场景。

**方案二：独立翻译表**

```sql
CREATE TABLE dim_merchant_i18n (
    merchant_id   BIGINT,
    lang_code     STRING,  -- 'zh', 'en', 'ar', 'pt'
    name          STRING,
    description   STRING,
    updated_time  TIMESTAMP
);
```

优点：新增语言不需要改表结构，只需插入新行。缺点：查询时需要 join 翻译表。

**建议**：国际外卖场景推荐方案二。因为新开城国家会引入新语言，翻译表更容易扩展。查询时在 DWS/ADS 层将翻译冗余进宽表，减少下游 join。

### 2.3 搜索词多语言处理

搜索词分析在国际化外卖中是一个独立的子问题。需要考虑：

- **分词**：阿拉伯语从右到左书写（RTL），分词逻辑不同；中文需要分词器（如 IK Analyzer）；葡语按空格分词但需要处理变位。
- **同义词**：不同语言的搜索词可能指向同一个品类。如"pizza"和"披萨"和"بيتزا"应映射到同一个品类。
- **搜索归因**：用户用阿拉伯语搜索"بيتزا"最终下单了，归因到搜索流量时需要保持原始搜索词，不要在 DWD 层做翻译。

建议：DWD 层保留原始搜索词（`search_keyword_original`），DWS 层增加标准化搜索词（`search_keyword_normalized`，做小写化、去空格等基础标准化），DWT/ADS 层按需做跨语言映射。

## 模块三：多币种折算

### 3.1 币种折算在哪一层做

| 层级 | 做不做折算 | 为什么 |
|------|-----------|--------|
| ODS | 不做 | 保真接入，保留原始值 |
| DWD | 保留原币种 + 币种代码，不折算 | 明细层不应引入汇率不确定性 |
| DWS | 增加 `amount_usd`（USD 折算），使用 T+1 官方汇率 | 跨 region 汇总需要统一口径 |
| DWT | 跨 region 聚合时以 USD 为口径 | 主题层做跨 region 对比 |
| ADS | 如需实时折算，使用实时汇率 API | 实时大屏场景 |

### 3.2 汇率数据源

需要一个汇率维表（`dim_exchange_rate`），字段包含：`from_currency`、`to_currency`、`rate`、`rate_date`、`rate_source`（官方/中间价/市场价）。

关键设计：汇率维表是一张**缓慢变化维**，汇率每日变动。在 DWS 层做折算时，需要按交易日期关联对应日期的汇率。不能总是用"最新汇率"折算历史数据，否则历史指标会每天变动。

### 3.3 跨 region GMV 汇总

跨 region 汇总 GMV 的正确做法：
1. 各 region 先按本币种计算日 GMV（DWS 层）
2. 按 T+1 汇率折算为 USD（DWS 层增加 `gmv_usd` 列）
3. 跨 region 汇总时以 USD 口径相加（DWT/ADS 层）

不能直接把沙特里亚尔、港币、巴西雷亚尔的原币种金额相加——那是没有意义的。

### 3.4 币种精度问题

不同币种的最小单位不同：里亚尔有 2 位小数（halala）、港币有 2 位小数（cent）、日元没有小数。金额字段统一用 DECIMAL(18,4) 存储，展示时按币种规则格式化。

## 模块四：营销归因口径

### 4.1 外卖场景的营销链路

外卖营销的核心链路是：**发券 → 领券 → 使用券下单 → 支付 → 核销（订单完成）**。归因要回答的问题是：这笔订单是因为哪张券、哪个活动、哪个渠道带来的。

### 4.2 三种归因口径

| 归因口径 | 定义 | 适用场景 |
|----------|------|----------|
| 首次归因 | 订单归因到用户触点的第一次营销触达 | 看拉新效果——"第一次接触是什么" |
| 末次归因 | 订单归因到下单前最后一次营销触达 | 看促转化效果——"最后推动下单的是什么" |
| 全链路归因 | 所有触达都分享归因权重（均分或加权） | 看全链路贡献——"整个营销链路每个环节的作用" |

### 4.3 在数仓模型中怎么落地

**DWD 层只记录事件，不做归因**：发券记录在 `fact_coupon_issue`，支付记录在 `fact_payment`，两者通过 `user_id` + `merchant_id` + `order_id` + 时间窗口关联，但不在 DWD 层绑定归因结果。

**DWT 层建归因宽表**：建 `dwt_marketing_attribution` 表，同时存储三种口径的关联结果。每行记录：`order_id` + `coupon_id_first` + `coupon_id_last` + `attribution_type` + `attributed_channel`。下游按需选择口径查询。

**关键设计**：归因的时间窗口需要与产品/运营约定。常见做法是"7 天内有效"——如果用户 7 天前领了券但没用，7 天后才下单，不算这张券的归因。也有用"当天有效"或"1 小时内有效"的，取决于营销活动的性质。

### 4.4 营销 ROI 指标体系

| 指标 | 定义 | 计算方式 |
|------|------|----------|
| 发券量 | 发出去的优惠券总数 | `COUNT(*) FROM fact_coupon_issue WHERE dt=...` |
| 领券量 | 用户领取的优惠券数 | `COUNT(DISTINCT coupon_id) WHERE status='received'` |
| 核销量 | 被使用下单的优惠券数 | `COUNT(*) WHERE status='redeemed'` |
| 核销率 | 核销量/领券量 | `核销量 / 领券量` |
| 补贴金额 | 优惠券面值总额 | `SUM(coupon_value) WHERE status='redeemed'` |
| 带券 GMV | 使用优惠券的订单 GMV | `SUM(order_amount) WHERE has_coupon=true` |
| ROI | 带券 GMV / 补贴金额 | `带券 GMV / 补贴金额` |
| 增量 GMV | 带券订单 - 对照组订单 | 需要 A/B 实验数据支持 |

关键注意点：ROI 计算时 GMV 和补贴金额必须统一币种（先折算为 USD 再相除）。跨 region 比较 ROI 时注意不同 region 的营销阶段不同（新市场靠补贴拉新，成熟市场靠券提复购），不能简单横向对比。

### 4.5 外卖漏斗指标

外卖场景的核心漏斗比一般电商更长，因为多了配送和核销环节：

```
曝光 → 点击 → 进店 → 加购 → 下单 → 支付 → 配送中 → 送达 → 核销
  ↓      ↓      ↓      ↓      ↓      ↓      ↓      ↓      ↓
PV     CTR   进店率  加购率  提单率  支付率  配送率  达成率  完单率
```

每一步的转化率是核心指标。漏斗分析在 DWT 层建 `dwt_user_funnel_daily` 宽表，每个用户每天一行，各步骤用 0/1 标记是否到达。

## 模块五：RAG 知识库的数仓侧工程

### 5.1 为什么数据团队要建 RAG 知识库

数据团队日常收到最多的问题是："这个指标怎么定义的？""这张表在哪里？""这个字段是什么意思？""为什么昨天的数据下降了？"——这些问题本来应该查文档，但文档散落在 wiki、飞书、学城、口头传承中，查找效率极低。

RAG 知识库的价值是：把数仓元数据（表结构、字段含义、指标口径、业务规则）结构化为 AI 可检索知识，用户用自然语言提问，系统自动检索相关知识片段并生成回答。

### 5.2 数仓侧需要产出什么

数仓侧不是"建一个向量库"就完事，而是要把现有的元数据体系**结构化为 RAG 可消费的知识源**：

**知识源一：表级知识文档**

每张表产出一份结构化的 Markdown 文档，包含：表名、用途说明、字段列表（字段名、类型、含义、是否分区键）、分区策略、更新频率、数据源、下游消费者、负责人、SLA 级别。这些信息本来就在元数据系统里，只是需要批量导出为文档格式。

**知识源二：指标口径文档**

每个指标产出一份文档，包含：指标名称、业务定义、计算公式、统计周期、适用 region、币种口径、版本变更历史（口径什么时候改过、为什么改）。这些信息在指标平台/语义层中维护，导出为文档。

**知识源三：业务规则文档**

归因口径说明、汇率折算规则、多时区切天规则、去重逻辑、A/B 实验分流规则——这些是"只存在于数据工程师脑子里"的隐性知识，需要显式文档化。

**知识源四：SQL 模板库**

高频查询的 SQL 模板（如"各 region 每日 GMV 趋势"、"某商家的漏斗转化"、"营销活动 ROI 报表"），供 Text2SQL 参考和复用。

### 5.3 文档分块策略

数仓知识文档的分块策略和通用 RAG 不同：

- **按表分块**：每张表的文档作为一个 chunk（表名 + 字段列表 + 说明），粒度适中
- **按指标分块**：每个指标的定义作为一个 chunk（指标名 + 公式 + 口径 + 适用范围）
- **按规则分块**：每条业务规则作为一个 chunk（归因规则 + 汇率规则 + 时区规则）
- **overlap 策略**：表级文档和指标文档之间保留关联（"这个指标在哪张表里算"），在 chunk metadata 中记录关联关系

### 5.4 Embedding 与检索

- **Embedding 模型**：推荐使用支持多语言的 Embedding 模型（如 `multilingual-e5`），因为数仓知识可能包含中英文混合
- **向量索引**：HNSW 即可，数仓知识量不大（通常几万到几十万 chunk），HNSW 延迟足够低
- **混合检索**：向量相似度 + 关键词 BM25（表名/字段名用精确匹配比语义匹配更准确）
- **Rerank**：对 top-20 结果用 Cross-Encoder 重排序，提升精度

### 5.5 增量更新

数仓元数据是活的——表会新增、字段会变更、指标口径会修改。需要建立增量更新机制：
- 监听元数据系统的变更事件（表新增、字段变更、指标口径修改）
- 对变更的文档重新生成 chunk 并更新向量库
- 保留版本历史（旧口径的 chunk 保留但标记 `valid_to` 时间，回答"这个指标以前是什么口径"时检索历史版本）

## 模块六：业界国际化数据团队的调研经验

Keeta 团队在建设初期对 AliExpress、Lazada、Shopee 等国际化电商数据团队做了系统调研，这些经验对国际化外卖数仓建设同样有参考价值。

### 6.1 Lazada：按国家分区、小国家合并模型

Lazada 覆盖 6 个国家、4 种语言。数据团队的做法是：底层数仓是 1 个，搜推用的表都是同一个，按国家分区。不同语言是分开的索引，单独的 query 分析、相关性和召回都是独立的。排序最初是 6 个国家 6 个模型，后来合并成 2 个模型——5 个规模小的国家共用 1 个模型，在 batch 内保证每个国家都有一定比例样本缓解小国家效果负向。

对数仓建设的启示是：DWD/DWS 层可以统一建表按 region 分区，但 DWT/ADS 层的模型和指标可以按 region 体量决定是分开还是合并——头部 region 独立，长尾 region 合并。

### 6.2 AliExpress：翻译为桥、头部语种独立评测

AliExpress 覆盖 100-200 个国家，重点关注欧洲、美国、拉美、韩日。多语言搜索的方案是：所有语种翻译成英文，用英文做相关性和召回，翻译准确率 80-90%。头部 7-8 个语种做大规模评测（1000 多个 query × top20 × 国家）。不同时区到岗时间问题和数据部署容灾是重点难点。

对数仓建设的启示是：多语言处理可以"翻译为统一中间语言"作为桥接方案，但不能完全依赖翻译——头部语种需要独立的数据分析和评测能力。搜索词在 DWD 层保留原始语言，DWS/DWT 层按需做翻译和标准化。

### 6.3 数据部署：滴滴国际化的多班车经验

滴滴国际化都部署在美东 VA 机房，不存在数据隔离问题，做了 localTime 多班车的数据层。这与 Keeta 的多时区改造方案一致——都是按各 region 本地时区做调度班车。

对数仓建设的启示是：如果数据都部署在同一机房/同一云区域，多时区改造的焦点在调度和 ETL 逻辑；如果数据需要按法规分散部署到不同国家/地区，则还要解决跨机房的数据同步和汇总问题。
