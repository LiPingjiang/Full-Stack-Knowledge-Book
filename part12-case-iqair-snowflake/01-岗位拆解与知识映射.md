# 12.1 岗位拆解与知识映射

## 不是“会用 Snowflake 的人”，而是“能把零散数据建成数据产品的人”

如果把这个岗位一句话说清楚，它招的不是“会写几条 Snowflake SQL 的开发”，而是一个能把**多源、半结构化、时序化、公开可消费**的数据体系，从零散状态推进到现代数仓状态的数据工程师 / 分析工程师 / 数据架构师。

它面对的问题不是单点的“查数”，而是一组同时成立的矛盾：

1. **源头很杂**：自有监测设备、合作方传感器、政府公开站点、天气 API、地理行政区划、历史报告数据；
2. **时效不一**：有的需要近实时刷新（站点页、城市排行），有的小时级即可（聚合分析），有的按日/月生成（历史报表、年度报告）；
3. **结构不一**：既有严格结构化表，也有 JSON payload、外部文件、参考数据；
4. **语义不一**：同样是空气质量值，既有“真实观测”，也有“预报”；既有原始污染物浓度，也有按不同标准派生的 AQI；
5. **消费面很多**：不是只有 BI 报表，还包括公开网页、开放 API、移动端、研究报告、外部合作共享。

这决定了这个岗位的核心，不是传统意义上的“离线 ETL 工程师”，而是一个更现代的画像：**Snowflake + ELT + 分层建模 + 数据质量 + 成本治理 + 领域语义建模**。

## 从公开产品页反推岗位重点

仅基于 iQAir 公开页面，就能推断出这个岗位的大部分难点。

### 线索 1：世界页展示了大规模站点与贡献者网络

世界页源码里可以直接看到类似 `35132 stations from 20844 contributors` 的公开统计。这说明平台不是单源自建系统，而是一个典型的**多源聚合网络**。

技术含义：
- 接入侧需要处理**异构数据合同**；
- 建模侧必须保留**贡献者/提供方维度**；
- 质量侧必须支持**按 source / contributor 回溯问题**；
- 消费侧需要支持“统一口径输出”，而不是把上游差异原样暴露给终端用户。

### 线索 2：城市页同时有实时、历史、小时预报、日预报、天气

城市页元信息和页面结构能直接看到：
- 实时 AQI 与 PM2.5
- Historical / forecast PM2.5 and weather data
- Hourly forecast / Daily forecast
- 城市地理位置与层级面包屑

技术含义：
- 这不是单一事实表，而是**至少两类事实**：观测事实与预报事实；
- 需要稳定支持**分钟/小时/天/月多粒度聚合**；
- 需要同时存储**污染物值、天气值、位置值、时间值**；
- 需要把**地理层级**当作一等公民，而不是普通维度随便带过。

### 线索 3：公开页面本身就是数据产品

站点页、城市页、排行榜和“historical air quality data”页面，说明下游不是“分析师自己写 SQL”这么简单，而是要给非技术用户提供稳定、可解释、可追溯的数据产品。

技术含义：
- Gold 层必须面向产品输出，而不是只服务内部 BI；
- 口径变更要非常谨慎，因为一改可能同时影响网页、API、报告、合作方；
- 数据工程团队必须有**指标语义层意识**，而不仅是跑任务。

## 这份岗位最看重的能力组合

### 第一类：现代数仓 / 分析工程硬功夫

- 分层建模：Raw / Bronze / Silver / Gold 或 ODS / DWD / DWS / ADS
- 事实表与维度表设计
- 增量模型、SCD、迟到数据处理
- 数据质量测试、数据血缘、版本控制

### 第二类：云数仓 / Snowflake 工程能力

- 半结构化数据落地与结构化提炼
- 近实时刷新 vs 任务式编排的取舍
- 成本 / 性能 / 刷新频率三者平衡
- 与外部对象存储、开放格式和共享边界的理解

### 第三类：空气质量领域理解

- AQI 不是原始值，而是按标准派生出的指数
- 观测值与预报值不能混建
- 同一城市多贡献者的数据必须保留来源并做 reconciliation
- 地理空间不是点缀，而是建模主轴之一

## 覆盖度总结

这份案例对全书的覆盖度非常高，尤其是第六章：

- **已覆盖的通用能力**：分层建模、接入、质量、调度、权限、语义层；
- **需要在本章和第六章补强的能力**：现代云数仓视角、Snowflake 取舍、IoT/地理空间/空气质量语义、多源对账。

如果说第十一章是在验证“Java 后端硬功夫能覆盖多少高并发中台岗位”，那么第十二章在验证的是：**第六章的数据工程体系，离一个真正能讲清楚的现代数仓案例，还差哪几块拼图。**
