# 12.2 空气质量数据平台与数仓架构全景

## 先从产品形态反推数据域

如果你要把 iQAir 的公开产品做成一个稳定的数据平台，至少会面对下面六类数据域：

| 数据域 | 典型内容 | 工程特征 |
|--------|----------|----------|
| 站点观测数据 | AQI、PM2.5、PM10、温湿风、上报时间 | 高频、时序、可能迟到或缺失 |
| 预报数据 | 小时预报、日预报、forecast horizon | 与观测语义不同，不能混表 |
| 地理层级数据 | 国家 / 城市 / 站点、经纬度、行政区划 | 需要地理空间建模 |
| 贡献者/提供方数据 | contributor、source、机构类型 | 多源治理与对账主轴 |
| 历史与报告数据 | 历史月表、年度报告口径 | 批处理与可追溯性更重要 |
| 前台消费模型 | 城市页、排行页、开放 API、报表 | 需要稳定且解释性强的 Gold 层 |

这决定了它更像一个**数据产品平台**，而不是单纯的数据仓库项目。

---

## 推荐的分层架构：Raw → Bronze → Silver → Gold

这类场景下我更推荐把 ODS / DWD / DWS / ADS 用更现代的语言重述为：

- **Raw / Bronze**：先把数据可靠接进来，保住原始语义；
- **Silver**：再把它变成“干净、统一、可信”的分析底座；
- **Gold**：最后围绕产品和分析场景产出稳定数据产品。

```text
数据源
  ├─ IoT/合作方站点读数
  ├─ 政府公开网络/第三方空气质量数据
  ├─ 天气 API / 预报模型输出
  ├─ 地理与行政区划参考数据
  └─ 历史文件 / 报告数据
          ↓
Raw Landing / Stage
          ↓
Bronze（原始 append-only，半结构化优先）
          ↓
Silver（类型化、标准化、去重、SCD、对账）
          ↓
Gold（城市页、站点页、排行、历史趋势、开放 API、报告）
```

### Bronze 层：先解决“来了没有、原貌还在不在”

这一层的关键不是分析，而是**保真接入**。

建议：
- 传感器 / 合作方的原始 payload 先落原始层；
- JSON 结构不稳定时，先以半结构化列保留；
- 保留 source / contributor / filename / ingest_time / batch_id 等元数据；
- 坚持 append-only，不在原始层直接改写语义。

这层的目标不是好查，而是**可回放、可审计、可重新解释**。

### Silver 层：把“能存”变成“能信”

这一层是整个平台的工程核心。建议最少建下面这些实体：

- `dim_station`：站点维度，含经纬度、城市、国家、贡献者、启停状态
- `dim_contributor`：提供方/贡献者维度
- `dim_pollution_standard`：AQI 标准维度（例如 US AQI 等）
- `fact_air_quality_observed`：观测事实表
- `fact_air_quality_forecast`：预报事实表
- `fact_weather_observed_or_forecast`：天气相关事实表

这一层做的事：
- 数据类型统一
- 单位统一
- 站点 ID / 城市 ID / 贡献者 ID 主数据统一
- 去重与迟到数据修正
- 站点维度 SCD
- 多源对账与差异标记

### Gold 层：面向产品与消费输出

这层不要停留在“分析师方便查”，而要直接贴着产品能力建：

- `mart_city_current_air_quality`
- `mart_station_current_air_quality`
- `agg_city_hourly_air_quality`
- `agg_city_daily_air_quality`
- `mart_city_ranking`
- `mart_historical_pm25`
- `mart_public_api_city_snapshot`

如果一个页面、一个 API、一个报告每次都需要再 JOIN 五六张表，说明 Gold 层还没建到位。

## 在 Snowflake 里，怎么分配各能力的职责

Snowflake 官方文档对几类能力的边界其实非常清楚，这个案例里可以直接照着用。

### 1. Snowpipe / 流式摄取：解决“进来”

适合做的事：
- 高频或持续到达的数据接入；
- 站点观测值、合作方推送、文件落地后的自动摄取；
- 把原始 payload 尽快送到落地表。

不适合做的事：
- 复杂业务转换；
- 跨多表的口径处理；
- 大量带状态的领域逻辑。

一句话：**Snowpipe 负责 ingest，不负责讲业务故事。**

### 2. Dynamic Tables：解决“增量提纯”

Snowflake 官方把 Dynamic Tables 定位为一种声明式、自动维护的增量转换能力。它特别适合：
- Raw → Silver 的清洗与结构化；
- Silver → Gold 的常规增量聚合；
- 希望以 `TARGET_LAG` 控制新鲜度，而不是手工排任务 DAG 的场景。

对这个案例来说，最适合 Dynamic Tables 的是：
- 半结构化读数表提炼成观测事实表；
- 站点级数据滚成小时 / 天级聚合；
- 城市当前值、城市历史趋势这类稳定派生层。

### 3. Streams & Tasks：解决“带副作用和程序化控制”

Snowflake 官方同时明确指出：如果你需要存储过程、外部调用、复杂控制流，还是应该用 Streams & Tasks。

对这个案例来说，Streams & Tasks 更适合：
- `MERGE` 式 upsert
- 带告警/回写的流程
- 复杂对账或补偿逻辑
- 需要调用外部程序或存储过程的场景

一句话：**Dynamic Tables 适合“声明式增量视图管道”，Streams & Tasks 适合“程序式任务编排”。**

## 这个场景最关键的五个建模决策

### 决策 1：观测事实与预报事实必须分开

这是整个案例最容易讲错的地方。

观测值回答的是“现在/过去实际发生了什么”，预报值回答的是“模型认为未来会怎么样”。如果混在一张事实表里，下游做历史统计、模型验证、页面展示、报告归因都会混乱。

所以至少要拆成：
- `fact_air_quality_observed`
- `fact_air_quality_forecast`

### 决策 2：原始污染物浓度只存一份，AQI 按标准派生

AQI 不是原始数据，而是按标准派生出来的指数。真正稳定的“底层事实”是 PM2.5 / PM10 / O₃ 等原始污染物值。

因此更稳妥的做法是：
- Silver 层保留原始浓度和基础质量状态；
- Gold 层按标准派生 AQI；
- 不把每种标准都预先膨胀成底层事实表列。

### 决策 3：事件时间优先于入仓时间

站点断连补传、合作方延迟推送、API 重试都是常态。空气质量平台如果用 ingest_time 作为主时间语义，很快就会把趋势和聚合算歪。

因此：
- 聚合主键用 `event_time`；
- `ingest_time` 只做链路审计与延迟分析；
- 迟到窗口与回补策略必须内建在 Silver / Gold 刷新逻辑里。

### 决策 4：城市统一值不能覆盖源值，必须保留 provenance

同一城市可能有多个贡献者、多个站点、不同精度和不同覆盖率。城市对外展示需要一个统一值，但统一值不能以“抹平来源差异”为代价。

所以建议：
- 保留站点级源值；
- 单独产出城市统一值；
- 对统一值记录来源、权重或合成规则；
- 对显著差异设置异常标记。

### 决策 5：把地理空间当作核心维度，而不是附带字段

站点坐标、城市边界、国家层级、最近站点、区域聚合都决定了这里不是普通业务数仓。Snowflake 文档支持 `GEOGRAPHY`，这个场景就应该把经纬度、空间关系当作核心建模能力来使用。

## 一套足够务实的落地方案

如果只给三个月，我会优先做这四件事：

### 第一步：建立最小可用 Raw / Bronze

目标不是“最优模型”，而是先把关键链路接进来：
- 站点观测值
- 天气 / 预报接口
- 站点 / 城市 / 贡献者维表

### 第二步：做一套稳定 Silver

优先保证三件事：
- 统一主键与地理层级
- 观测 / 预报分离
- 数据质量基线（完整性、迟到、重复、值域、来源差异）

### 第三步：围绕产品建 Gold

先只做最值钱的 Gold 表：
- 城市当前值
- 城市小时/天趋势
- 城市排行
- 站点详情页数据集

### 第四步：再做成本和治理优化

包括：
- Raw 层保留策略
- 刷新 lag 细分
- 外部开放共享边界
- 权限和审计
- 历史回灌机制

这套顺序的核心思想是：**先把“能稳定产出城市页和排行页”跑通，再谈更漂亮的架构。**
