# 12.5 面试准备路径与高频问题

## 准备优先级

### 第一优先级：先把“为什么这样分层”讲顺

你至少要能用 2~3 分钟讲清楚：
- 为什么这个场景不是一张大宽表；
- 为什么要 Raw / Bronze / Silver / Gold；
- 为什么观测与预报分离；
- 为什么 Gold 不只是给 BI，而是给页面/API/报告。

如果这部分讲不顺，后面讲 Snowflake 细节也很难加分。

### 第二优先级：讲清 Snowflake 能力边界，而不是堆名词

面试官不一定要听你背功能表，他更在意你会不会取舍：
- Snowpipe / 摄取链路解决什么问题？
- Dynamic Tables 适合哪些增量转换？
- Streams & Tasks 什么时候仍然不可替代？
- 为什么这个项目里既讲数仓，又讲湖仓？

### 第三优先级：补上领域语义

也就是：
- AQI 不是原始值
- 观测 vs 预报
- 多源 reconciliation
- 地理空间层级
- 迟到/缺失/降采样

这是普通数仓候选人最容易失分、但也是最能体现“我理解业务”的地方。

### 第四优先级：准备成本、质量和治理

成熟的数据工程面试很少只问“怎么建”，一定会继续追问：
- 成本怎么控？
- 数据错了怎么发现？
- 历史怎么回放？
- 对外口径怎么稳定？
- 合作方和公开访问怎么做边界？

## 高频问题与参考回答框架

### 问题 1：如果让你给 iQAir 设计一套 Snowflake 数仓，你会怎么分层？

**答题框架：**
先按职责分四层：Raw/Bronze 保原始与回放，Silver 做标准化与可信语义，Gold 面向产品和分析输出。重点说明两件事：
1. 观测事实和预报事实分开；
2. 原始污染物值和 AQI 派生分开。

最后补一句：Gold 层直接贴城市页、站点页、排行和历史 API 设计，而不是只给 BI 出宽表。

### 问题 2：为什么这个项目既像数仓，又像湖仓？

**答题框架：**
因为它同时满足湖仓的几个典型特征：
- 数据源异构且有半结构化 payload；
- 原始层需要低成本保留与可回放；
- 上层要做事务化、分层化、可治理的分析输出；
- 还可能和外部对象存储、开放表格式、共享场景发生关系。

但从团队落地视角看，核心目标仍然是“建出稳定数据产品”，所以讲“现代云数仓承载湖仓职责”比机械区分名词更重要。

### 问题 3：Dynamic Tables 和 Streams & Tasks 你会怎么选？

**答题框架：**
简单增量转换、层间派生、稳定聚合，我优先用 Dynamic Tables，因为它声明式、维护成本低、可以用 target lag 表达新鲜度目标。
如果需要复杂 `MERGE`、程序化控制、存储过程、副作用逻辑、补偿和通知，我会保留 Streams & Tasks。
一句话：Dynamic Tables 管“声明式增量管道”，Streams & Tasks 管“程序式任务编排”。

### 问题 4：同一个城市多个站点、多个贡献者，值不一致怎么办？

**答题框架：**
我不会直接覆盖。会分三层处理：
1. Silver 保留每个 source/station 的值；
2. 质量层做时间对齐、缺失标记、异常差异标记；
3. Gold 再按规则产出城市统一值，并记录 provenance 或权重逻辑。

这样既能给产品一个稳定答案，也保留了追溯和后续调参空间。

### 问题 5：你会如何定义这个项目里最关键的数据质量规则？

**答题框架：**
不要只答 not null / unique。这个场景至少要答五类：
- 完整性：关键站点/关键城市是否按 SLA 到数；
- 时效性：event_time 到 ingest_time 的延迟分布；
- 值域有效性：污染物浓度、AQI、天气值是否在合理范围；
- 多源一致性：同城多源差异是否超过阈值；
- 结构变化：合作方 payload 是否突然改字段。

再补一句：坏数据不要简单丢，最好有死信与回放机制。

### 问题 6：Snowflake 账单涨了，你先查什么？

**答题框架：**
我会先分三类看：
1. 计算是否被不必要的刷新和大 warehouse 消耗；
2. 原始层和历史层是否保留过长；
3. 是否把本应结构化下推的高频字段长期留在半结构化查询里，导致持续高成本扫描。

也就是说先看**刷新策略、存储策略、查询模式**，而不是只盯着“SQL 慢”。

### 问题 7：如果只有 90 天，你先交付什么？

**答题框架：**
第一阶段不追求完美架构，而追求最小可用闭环：
- 接进核心数据源；
- 建好观测 / 预报 / 站点 / 城市的核心 Silver；
- 跑通城市页和排行页需要的 Gold；
- 把最基本的数据质量告警和回放能力建起来。

因为对这个业务来说，能稳定支撑核心页面，比先把一切都抽象得很漂亮更重要。

## 一个 90 秒自我表达模板

> “如果把 iQAir 这类岗位抽象一下，我理解它不是单纯的 Snowflake SQL 开发，而是一个现代数据工程角色：要把多源空气质量数据——包括站点观测、天气接口、预报结果和地理维表——构建成既可分析、又可直接服务城市页/站点页/API/报告的数据产品。我会采用 Raw/Bronze/Silver/Gold 的分层方式：原始层保回放和审计，Silver 层做观测与预报分离、站点与贡献者主数据统一、事件时间建模和多源对账，Gold 层围绕城市当前值、历史趋势和排行输出稳定数据集。在 Snowflake 能力上，我会把摄取、声明式增量转换和任务式编排分开考虑，同时把成本、质量和权限共享从第一天就纳入设计。”

这个模板的重点不是“面面俱到”，而是让面试官在一分钟内听到三件事：
- 你懂业务形态；
- 你懂分层与取舍；
- 你懂工程化约束。

## 推荐反问

1. 现在最主要的数据源是自有站点、合作方站点，还是第三方公开网络？
2. 团队当前最痛的是接入混乱、口径混乱，还是成本和性能？
3. 近实时数据和历史/报告数据目前是同一套链路，还是分开的？
4. Snowflake 在团队里现在主要承担纯数仓角色，还是已经承担了原始层和外部共享职责？
5. 这个岗位更偏数据平台建设，还是更偏面向产品的数据集开发？

好的反问不是礼貌动作，而是在确认：**这家公司到底需要一个“写模型的人”，还是一个“搭平台的人”。**
