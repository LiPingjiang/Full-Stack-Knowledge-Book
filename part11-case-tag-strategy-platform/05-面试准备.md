# 11.5 面试准备路径与高频问题

## 准备优先级

根据 JD 权重和面试考察概率，按以下优先级准备。

**第一优先级（必考，占面试 35%）：高并发架构 + JVM/多线程**

这是岗位的绝对核心，面试官大概率会围绕"如何设计一个百万级 QPS 的标签查询服务"展开系统设计题，同时穿插考察并发编程和 JVM 调优的基本功。准备路径：复习 [第三章 3.1 并发体系](../part3-java-deep/01-并发体系.md)（线程池参数设计、AQS）、[3.3 JVM 运行时](../part3-java-deep/03-JVM运行时.md) 与 [3.3 JVM 运行时-实战排查](../part3-java-deep/03-JVM运行时-实战排查.md)（GC 选型、OOM/CPU 飙高排查）、[3.6 网络 IO 模型](../part3-java-deep/06-网络IO模型.md)、[3.7 高可用架构](../part3-java-deep/07-高可用架构.md)（限流熔断降级、幂等）。

**第二优先级（高概率，占面试 25%）：中间件深度（Redis/MQ/MySQL/RPC）**

面试官会问具体的中间件使用细节和踩坑经验，而不只是"知道有这些东西"。准备路径：复习 [3.8 缓存与 Redis](../part3-java-deep/08-缓存与Redis.md)（穿透击穿雪崩、一致性方案）、[3.12 消息队列](../part3-java-deep/12-消息队列.md)（Kafka ISR、RocketMQ 事务消息）、[3.9 数据库 MySQL](../part3-java-deep/09-数据库MySQL.md)（索引、分库分表）、[3.14 微服务与分布式锁](../part3-java-deep/14-微服务与分布式锁.md)（分布式锁三种实现对比），然后补充 [11.3](./03-通用知识缺口.md) 里 RPC 协议与序列化的内容。

**第三优先级（中概率，占面试 20%）：标签系统与规则引擎系统设计**

面试官会要求你白板设计一个标签/策略平台的整体架构。准备路径：吃透 [11.2 高并发中台架构全景](./02-高并发中台架构全景.md) 和 [11.4 领域知识](./04-领域知识.md)，重点理解 Bitmap 存储优化和规则引擎的三种设计模式，能画出完整的数据流架构图。

**第四优先级（加分项，占面试 15%）：Agent 研发与 Harness Engineering**

不是所有面试官都会深挖这块，但一旦问到，答得好能明显加分，因为这是候选人池里的稀缺点。准备路径：复习 [第七章 7.6 Agent 基础](../part7-ai-engineering/06-Agent基础.md)，理解 [11.3](./03-通用知识缺口.md) 里 Harness Engineering 的三层职责（执行隔离、工具调用可靠性、评测体系），能举出一个"Agent 辅助策略配置或稳定性运维"的具体应用场景。

**第五优先级（软性考察，占面试 5%）：稳定性工具自研经验**

准备一个具体的"设计一个限流组件"或"设计一个压测平台"的完整方案，展现"做过"而不只是"用过"的深度。

## 高频面试问题与参考回答

### 问题 1：如何设计一个支持百万级 QPS 的标签查询服务？

**考察点：** 高并发架构设计、缓存策略、稳定性保障

**参考回答框架：**

整体架构分接入层、缓存层、计算层、存储层。接入层用 Spring Cloud Gateway 或者自研网关做统一入口，做流量控制和路由。缓存层是核心——请求先查本地缓存（Caffeine，纳秒级但容量有限，只放最热的一小部分标签），未命中查 Redis 集群（毫秒级，容量大，覆盖大部分标签），本地缓存和 Redis 之间用较短的 TTL 加上主动失效机制保证一致性可控。对于极高频访问的布尔型标签（比如"是否新用户"），额外用 Bitmap 方案，把亿级用户的标签压缩到几 MB 常驻内存，查询直接是位运算，比查 Redis 更快。

稳定性设计上，对下游依赖（Redis、底层存储、其他微服务）都设置严格超时（毫秒级），一旦超时立刻走降级返回默认值，不能让下游的抖动传导到上游拖垮整个链路。用限流保护自身（令牌桶限制单机 QPS），用线程池隔离（不同优先级的标签查询用不同线程池，慢查询不能拖累快查询）。可观测性上建立分钟级的 QPS、延迟 P99、缓存命中率、降级次数监控大盘，异常自动告警。

容量规划上，百万级 QPS 通常不是单机能扛的，需要水平扩容多个无状态服务实例，前面挂负载均衡，Redis 也要考虑集群化分片，避免单个 Redis 实例成为瓶颈。

**关键设计决策：** 为什么要有本地缓存这一层而不是直接查 Redis——因为即使 Redis 延迟只有 1ms，百万级 QPS 下网络往返的开销累积起来依然可观，本地缓存能拦截掉大部分请求，大幅降低 Redis 集群的压力和整体延迟。代价是本地缓存有多实例数据不一致的窗口期，需要结合业务对标签新鲜度的容忍度权衡 TTL 设置。

### 问题 2：缓存穿透、击穿、雪崩在标签系统里具体怎么发生，怎么解决？

**考察点：** Redis 深度理解、结合具体业务场景分析问题

**参考回答框架：**

穿透发生在查询一个根本不存在的用户 ID 的标签（比如恶意扫号或者传入了错误的用户 ID），缓存和数据库都没有这条记录，每次请求都穿透到最底层，解决方案是对查询不到的结果也缓存一个短 TTL 的空值标记，或者在接入层用布隆过滤器提前拦截明显不存在的 ID（参考[附录 A1 布隆过滤器](../part3-java-deep/A1-核心数据结构原理.md)）。

击穿发生在某个热点标签（比如一个大促活动期间"是否参与活动"这个标签，几乎所有请求都会查）的缓存恰好过期的瞬间，大量并发请求同时穿透到底层重新计算，解决方案是用互斥锁保证只有一个请求去重新计算并回写缓存，其他请求等待或者返回旧值（逻辑过期方案——缓存永不物理过期，但标记了逻辑过期时间，发现逻辑过期后由一个请求异步重新计算，其他请求继续用旧值，避免请求阻塞等待）。

雪崩发生在大批量缓存 key 集中在同一时间过期（比如某次批量刷新标签时统一设置了相同的 TTL），瞬间大量请求全部穿透到底层，解决方案是给缓存 TTL 加上随机抖动（比如基础 TTL 加 0-300 秒的随机值），避免大批量 key 同时失效，同时做好底层存储的限流保护和降级预案，即使雪崩发生也不至于把底层存储打垮。

### 问题 3：规则引擎如何设计？为什么不直接把规则写在 Java 代码里？

**考察点：** 系统设计能力、对业务和技术权衡的理解

**参考回答框架：**

直接写在代码里的问题是变更成本高——运营每次调整策略都要走完整的开发发版流程，响应速度慢；而且规则越堆越多会变成难以维护的 if-else 地狱。规则引擎的核心思路是把规则从代码中抽取出来变成可配置的数据。

具体设计上，先明确规则的两个组成部分——条件（什么情况下触发）和动作（触发后做什么）。简单场景用决策表模式，一张表列出所有条件组合和对应结果，运营像编辑 Excel 一样配置。复杂场景（条件之间有优先级、有短路依赖）用规则链模式，把每个判断节点抽象成统一接口用责任链模式串联。表达能力要求最高的场景（复杂的逻辑组合，AND/OR/括号嵌套）用表达式引擎，比如 QLExpress 或者 Drools，把规则写成表达式字符串，运行时动态解析执行。

性能上要解决表达式解析的开销问题——规则不是每次请求都重新解析，而是配置生效时预编译一次，缓存编译后的可执行结构，后续请求直接复用。规则变更的可靠性上，新规则先小流量灰度验证，同时保留历史版本支持快速回滚，避免一次错误的规则配置直接影响全量线上流量。

架构上规则引擎和标签系统要解耦——标签系统负责计算"用户是什么样的"，规则引擎负责决定"知道了这些之后该怎么办"，两层独立演进，互不干扰。

### 问题 4：标签数据量达到百亿级别，如何设计存储和多维查询？

**考察点：** 海量数据存储选型、Bitmap 等压缩数据结构

**参考回答框架：**

分层存储思路。高频访问的核心标签（每个请求几乎都要查的，比如是否新用户、用户分层）用 KV 存储（Redis）保证毫秒级查询延迟。布尔型标签额外用 Bitmap 优化——把用户映射到位图的固定位置，一个标签对应一个位图，一亿用户的标签只需要约 12.5MB，多标签组合查询（比如营销选人"新用户 AND 北京地区 AND 近7天活跃"）直接做位图的按位与运算，性能比基于 ID 列表做集合求交高几个数量级。考虑到实际标签的分布往往是稀疏的（很多标签只有少数用户命中），用 RoaringBitmap 而不是原生 Bitmap，通过分桶自适应选择数组或位图存储，兼顾稀疏和稠密场景的空间效率。

复杂的多维分析查询（运营需要"任意维度组合"的探索性查询，不是预先定义好的固定组合）用列式存储的 OLAP 引擎（ClickHouse/Doris），把标签当作宽表的列，靠列存的高压缩率和向量化执行支持灵活的 Ad-hoc 查询，这类查询对延迟要求相对宽松（运营人员的分析场景，秒级到几秒都可接受），跟在线服务对毫秒级延迟的极致要求是不同的性能档位，所以用不同的存储引擎服务不同的查询模式。

底层的标签计算结果来自两条链路——离线批计算（Spark 每天全量刷新，保证准确性）和实时流计算（Flink 秒级增量更新，保证时效性），两条链路的结果最终都写入上述在线存储层，需要设计清晰的时间戳比较和优先级规则，避免离线任务覆盖掉更新的实时结果。

### 问题 5：如果让你负责团队的 Agent 研发和 Harness Engineering 建设，你会怎么规划？

**考察点：** 对 AI 工程化的理解、能否把新技术和已有工程经验类比

**参考回答框架：**

先明确 Agent 在标签策略平台里能解决什么问题——可以设想两个场景：一是辅助规则配置，运营用自然语言描述一个策略意图，Agent 理解后自动生成规则引擎的具体配置（决策表或表达式），降低非技术人员配置复杂规则的门槛；二是辅助稳定性运维，Agent 自动分析异常监控和日志，定位问题根因，甚至给出限流阈值调整建议，辅助值班人员快速响应。

围绕这两个场景做 Harness Engineering 建设，核心是三层保障。第一层是执行隔离——Agent 生成的规则配置不能直接生效，必须先在隔离的沙箱环境（可以是独立的测试租户或者影子环境）验证语法正确性和逻辑合理性，这跟容器化部署里 namespace/cgroup 的隔离思路是相通的，只是隔离对象从"进程"变成了"Agent 生成的配置变更"。第二层是工具调用可靠性——Agent 调用查询标签定义、查询历史规则这些内部工具时，要有统一的超时重试和降级机制，跟服务间调用的高可用设计是同一套工程套路的复用。第三层是评测体系——建立一套标准化的测试场景集（给定典型的策略配置需求），定期跑 Agent 生成结果和期望结果的对比评分，形成回归测试机制，确保每次调整 Prompt 或者升级底层模型不会导致 Agent 生成质量的整体下滑。

最终所有 Agent 生成的变更都要经过人工审核才能生效于生产环境，Harness 的价值不是让 Agent 完全自主运行，而是让"人机协同"的效率和安全性都达到最优——Agent 负责生成候选方案，Harness 保障候选方案的安全边界和质量下限，人做最终把关。
