# 11.2 高并发中台架构全景：从标签存储到策略决策

在深入具体的知识缺口（Harness Engineering、规则引擎）之前，先建立标签与策略平台的整体架构认知。这一节回答一个问题：一个支撑网约车、两轮车、国际化等所有核心业务场景、峰值 QPS 百万级的标签策略中台，长什么样？

## 1. 为什么需要一个独立的"标签策略中台"

先理解业务背景。网约车平台每天发生海量的判断请求——"这个司机是不是新手司机""这个用户是不是高价值用户""这单是不是需要人工审核""这个区域现在要不要动态调价"。如果每个业务线（网约车、两轮车、国际化）都自己写这些判断逻辑，会出现三个问题：逻辑重复建设（网约车和两轮车都需要判断"是否新用户"）、口径不一致（同一个"高价值用户"标签在不同业务线算法不同）、变更成本高（运营想调整一个策略阈值，需要各业务线分别改代码发版）。

标签策略中台的价值就是把"打标签"和"做决策"这两件事收归到一个统一平台，业务方通过标准接口查询标签、触发策略，中台负责标签的计算、存储、更新，以及策略规则的配置、执行、灰度。这是一个非常经典的**中台架构**范式——本质上和电商的"营销中台""风控中台"是同一种设计思想的不同业务实例。

用更结构化的方式理解这两个平台的分工："标签平台"回答的是"对象是什么样的"，产出的是画像和特征，是一种数据资产沉淀；"策略平台"回答的是"知道了这些特征之后该怎么做"，产出的是具体的业务动作（发券、派单、拦截），是把数据资产转化为业务收益的执行引擎。标签平台是"输入"，策略平台是"输出"，两者的组合构成了业务决策的完整闭环。

### 标签对象不只是"人"，还包括"时空"

出行/双边撮合平台有一个区别于电商中台的独特之处——它需要给**地理网格和时间片**这类时空实体打标签，而不仅仅是给用户、司机这些"人"打标签。常见的时空标签包括：某个区域（通常用 H3/Geohash 网格划分）当前的供需紧张度、是否处于早晚高峰或雨天等特殊天气窗口、区域实时拥堵指数。这类标签的计算和查询对实时性要求极高（供需关系分钟级甚至秒级变化），也是策略平台做动态调价、运力调度决策时最关键的输入之一。这提示我们，标签系统的实体维度设计需要同时覆盖"人（乘客/司机/车辆）"和"时空（区域/网格/时间窗口）"两条主线，后者容易被忽略，但恰恰是出行类中台的领域特色。

## 2. 整体架构分层

标签策略中台从下到上可以分成四层：数据层、计算层、服务层、配置层。

**数据层**负责标签的原始数据来源和存储。原始数据来自业务日志（订单、行程、支付）、用户行为埋点、第三方数据（征信、设备指纹）。存储上分两条路径：离线存储用 Hive/数据仓库（详见[第六章大数据基础](../part6-bigdata/README.md)）沉淀历史全量数据，用于计算复杂的统计类标签（比如"近30天平均单均消费"）；在线存储用 Redis 或专用 KV 存储，存放需要低延迟读取的标签结果和实时特征。

**计算层**负责把原始数据加工成标签。分两种计算模式：离线批计算，用 Spark/Flink 跑批任务，每天/每小时全量或增量刷新一批标签（详见[第六章 6.4 Spark](../part6-bigdata/04-Spark.md)、[6.5 Flink](../part6-bigdata/05-Flink.md)）；实时流计算，用 Flink 处理实时事件流，秒级更新标签（比如"用户最近一次下单时间"）。两种模式产出的结果最终都要写入在线存储层，供服务层查询。

**服务层**是业务方直接调用的接口层，用 Java + Spring 构建，这是这份 JD 里"高并发、高吞吐"能力集中体现的地方。服务层做三件事：接收查询请求（"查用户 X 的所有标签"或"查订单 Y 命中哪些策略"）、多级缓存查询（本地缓存 → 分布式缓存 → 存储层兜底）、策略规则执行（拿到标签结果后，套用配置好的规则，输出决策结果）。

**配置层**是给业务方和运营人员用的管理后台，对应 JD 里"与业务部门深度合作，提升平台能力"这一条。业务方在这里配置新标签的计算规则、配置策略的判断条件和执行动作，不需要平台方写代码——这是规则引擎和低代码能力发挥作用的地方（详见 [11.4 领域知识](./04-领域知识.md)）。

```
┌─────────────────────────────────────────────┐
│  配置层：标签配置 / 策略规则配置 / 灰度发布管理    │
├─────────────────────────────────────────────┤
│  服务层：标签查询 API / 策略决策 API             │
│  （多级缓存 + 限流熔断 + 规则引擎执行）           │
├─────────────────────────────────────────────┤
│  计算层：离线批计算(Spark/Flink) + 实时流计算(Flink) │
├─────────────────────────────────────────────┤
│  数据层：Hive 离线仓库 + Redis/KV 在线存储        │
└─────────────────────────────────────────────┘
```

## 3. 服务层的高并发设计：这份 JD 的核心战场

百万级 QPS 意味着服务层不可能每次请求都穿透到存储层，必须设计合理的多级缓存和降级链路。这里有一个更具体的性能量级值得记住：策略引擎往往要求在用户打开 App、发单、派单、支付这些高频链路的关键路径上，**10~50 毫秒内完成数万条规则的过滤并输出最终决策结果**。这个"毫秒级 + 数万条规则"的组合约束，直接决定了架构上不能用逐条规则线性扫描的朴素实现，而必须依赖 [11.4 领域知识](./04-领域知识.md) 里讲到的规则预编译、规则索引与短路这些优化手段，以及本节接下来讨论的多级缓存和 Bitmap 存储——本质上都是在跟这个极限时延要求做斗争。

**请求路径设计：** 一个典型的标签查询请求先查**本地缓存**（Caffeine/Guava Cache，纳秒级，但容量有限、多实例间不一致）；本地缓存未命中查**分布式缓存**（Redis，毫秒级，容量大，多实例共享）；分布式缓存未命中才查**底层存储**（可能是另一个数据服务，或者 HBase/TiKV 这类分布式 KV），查到后回写两级缓存。这个链路直接对应 [第三章 3.8 缓存与 Redis](../part3-java-deep/08-缓存与Redis.md) 里缓存穿透、击穿、雪崩三大问题——标签平台的热点标签（比如"是否新用户"这种几乎每个请求都要查的标签）极容易触发缓存击穿，需要用互斥锁或逻辑过期的方案保护。

**稳定性设计：** 因为标签策略平台嵌在网约车派单这样的主链路里，一旦这个中台出问题会拖垮上游业务，所以稳定性设计要求极高。核心手段直接对应 [第三章 3.7 高可用架构](../part3-java-deep/07-高可用架构.md)：对下游存储的调用要设置严格超时（比如 Redis 调用超时 5ms，一旦超时立刻走降级逻辑而不是傻等）；对整体接口做限流保护（令牌桶限制单机 QPS，防止突发流量打垮服务）；准备好降级策略（缓存和存储都不可用时，返回一个保守的默认标签值，比如"未知用户默认按普通用户处理"，而不是直接报错阻塞主链路）。

**并发处理设计：** 一个策略决策请求往往需要并行查询多个标签（比如判断"是否需要人工审核"可能要同时查"是否新用户""是否高风险地区""历史投诉次数"三个标签），用线程池并行发起多个查询，然后汇总结果，这直接对应 [第三章 3.1 并发体系](../part3-java-deep/01-并发体系.md) 里线程池设计和 CompletableFuture 编排。线程池参数设计要考虑标签查询是 IO 密集型任务（大部分时间在等 Redis/RPC 返回），核心线程数可以适当调大，同时要做好线程池隔离——避免某个慢查询的标签把整个线程池占满，拖累其他快查询的标签（可以类比熔断设计里的舱壁隔离模式）。

## 4. 策略决策的执行模型

标签查询相对简单（查询 + 缓存），策略决策更复杂，因为策略往往是"多个条件的组合判断 + 命中后执行某个动作"，比如"如果用户是新用户 AND 当前在活动城市 AND 首单未完成，则展示新客立减券"。

这种"条件组合判断"如果写死在 Java 代码里（一堆 if-else），每次业务方要新增或调整策略都要改代码发版，效率极低，而且容易出 Bug（不同策略之间的 if-else 分支互相影响）。所以成熟的策略平台都会引入某种形式的**规则引擎**——把"条件"和"动作"抽象成可配置的规则，运营人员在后台配置，引擎在运行时动态加载和执行规则，不需要每次都改代码。这是本章重点分析的领域知识缺口，详见 [11.4 领域知识](./04-领域知识.md)。

## 5. 数据量百级的存储选型

JD 里"数据量百级级"通常指标签数据总量达到百亿甚至千亿行级别（比如给几亿用户，每个用户打上几百个标签，组合起来就是百亿级的"用户-标签"关系）。这种规模下，传统的 MySQL 单表存储肯定扛不住，常见的选型思路有三种。

**KV 存储路线：** 用 Redis 或 TiKV 存储"用户ID → 标签集合"的映射，读取延迟低，但内存/存储成本高，适合频繁访问的核心标签。

**位图（Bitmap）路线：** 对于"是否命中某个标签"这种布尔型标签，用 Bitmap 存储极其节省空间——一亿用户的某个标签只需要约 12.5MB（一亿 bit）。多个标签的组合查询（比如"新用户 AND 高价值用户"）可以直接用 Bitmap 的按位与运算完成，性能极高。RoaringBitmap 是工业界的标准实现，对稀疏和稠密数据都有优化的压缩编码，Kylin、Druid 这类 OLAP 引擎都用它做多维过滤。这个思路和 [附录 A1 核心数据结构原理](../part3-java-deep/A1-核心数据结构原理.md) 里布隆过滤器"用空间换时间"的设计哲学是同一路数，只是布隆过滤器解决的是"存在性判断"，Bitmap 解决的是"精确的集合运算"。

**宽表 + 列存路线：** 对于需要复杂条件筛选的场景（营销选人："查询北京地区、近7天活跃、历史订单数大于10"这种多维查询），用列式存储的 OLAP 引擎（ClickHouse/Doris，详见 [第六章 6.11 ClickHouse](../part6-bigdata/11-ClickHouse.md)、[6.6 Doris](../part6-bigdata/06-Doris.md)）会更合适，把标签当作宽表的列，靠列存的高压缩率和向量化执行支持复杂的 Ad-hoc 查询。

三种路线在实际的标签平台里往往是共存的——高频简单标签走 KV/Bitmap 保证在线查询性能，复杂多维分析走 OLAP 宽表满足运营的探索性查询需求。
