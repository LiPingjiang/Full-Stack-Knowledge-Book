# 11.4 领域知识：标签系统与规则引擎设计

本节聚焦这份 JD 里真正的领域知识缺口——标签系统的存储计算架构、规则引擎/策略引擎的设计模式。这两块是标签策略平台区别于普通业务系统的核心技术特征，也是面试官最可能深挖系统设计能力的地方。

## 1. 标签系统：从"打标签"到"查标签"的完整链路

### 标签的分类体系

理解标签系统架构之前，先建立标签的分类认知，因为不同类型的标签，计算方式和存储方式差异很大。

**按计算时效性分**：静态标签（几乎不变，比如性别、注册城市，一次计算长期有效）、离线标签（每天/每小时批量刷新，比如"近30天订单数""月均消费"，用 Spark/Flink 跑批计算）、实时标签（秒级/分钟级更新，比如"当前是否在行程中""最近5分钟是否有异常操作"，用 Flink 流计算或者直接在服务层实时查询计算）。

**按数据类型分**：布尔型标签（是否新用户，取值只有是/否，天然适合用 Bitmap 存储）、枚举型标签（用户分层：高/中/低价值，取值是有限集合）、数值型标签（近30天消费金额，取值是连续数值，通常需要分桶后再用于规则判断）。

**按计算复杂度分**：规则型标签（基于简单条件判断产出，比如"注册时间小于7天则为新用户"）、统计型标签（基于聚合计算产出，比如"近30天平均单价"）、模型型标签（基于机器学习模型打分产出，比如"流失风险评分"，这类标签的产出依赖第七章模型部署基础里讲的推理服务化）。

### 标签系统的核心架构模式

标签系统的架构设计要同时满足两个看起来矛盾的需求：离线计算需要能处理海量历史数据算出准确的统计结果，在线服务需要毫秒级返回结果。业界的标准解法是 **Lambda 架构的标签场景实例化**——离线层负责准确性和全量计算，实时层负责时效性和增量更新，两层的结果最终都汇聚到统一的在线存储层供服务层查询。

具体链路是这样的：业务事件（下单、支付、完单）先进入消息队列（详见[第三章 3.12 消息队列](../part3-java-deep/12-消息队列.md)），一路落地到数据仓库供离线批计算使用，另一路被 Flink 实时消费用于更新时效性要求高的标签。离线批计算每天定时跑一遍全量标签计算任务，结果批量写入在线存储（这是一个典型的"大批量写、追求吞吐"场景，可以用 Redis 的 Pipeline 批量写或者 Bulk Load 到 HBase）。实时计算持续消费事件流，增量更新标签值，写入路径要求低延迟（单条更新，不能等批量攒够再写）。服务层统一查询在线存储层，业务方感知不到背后是离线更新还是实时更新的标签，只关心查询接口的延迟和准确性。

这里有一个值得深挖的工程难点——**离线和实时结果的一致性**。如果同一个用户的同一个标签，离线计算的结果是"高价值用户"，但因为一次异常大额消费触发了实时更新变成了"超高价值用户"，两条链路谁的结果更新，什么时候会被离线的全量计算重新覆盖，这里需要设计清晰的优先级规则和时间戳比较逻辑，避免离线任务跑完后把实时更新的最新结果"覆盖倒退"回旧值。

### 标签的存储优化：位图与压缩

延续 [11.2 高并发中台架构全景](./02-高并发中台架构全景.md) 提到的存储选型，这里深入 Bitmap 方案的工程细节，因为它是标签系统里最有技术含量、也最容易在面试中被追问的点。

假设有一亿用户，需要判断"新用户 AND 北京地区 AND 近7天活跃"这个组合条件命中了哪些人。如果每个标签单独存一个 KV（用户ID → 布尔值），做组合查询需要拿到三个标签各自命中的用户列表，再做集合求交，当每个列表有几千万个用户 ID 时，这个求交操作的内存和计算开销都很大。

用 Bitmap 就完全不同——把一亿用户按固定顺序映射到一个一亿位长的位图上，每个标签对应一个位图，第 i 位是 1 表示第 i 个用户命中这个标签。三个标签的组合查询直接对三个位图做按位与（AND）运算，现代 CPU 对位运算有原生指令级支持，一亿位（约 12.5MB）的按位与运算在毫秒级就能完成，比基于 ID 列表的集合求交快几个数量级。

**RoaringBitmap 的价值**在于原生 Bitmap 在数据稀疏时会浪费大量空间（比如一亿用户里只有一千个命中某个标签，用普通 Bitmap 依然要存 12.5MB，但用 ID 列表只需要几 KB）。RoaringBitmap 通过分桶（把 32 位整数的高16位作为桶号，低16位在桶内用 Bitmap 或数组存储，根据数据密度自动选择最优的桶内存储结构）实现了"稀疏时用数组、稠密时用 Bitmap"的自适应压缩，同时保留了按位运算的高性能。这是为什么 Druid、Kylin、ClickHouse 这类分析型引擎的多维过滤场景普遍采用 RoaringBitmap 作为标准实现。

## 2. 规则引擎：把策略从代码里"解耦"出来

### 为什么策略不能写死在代码里

回到 [11.2](./02-高并发中台架构全景.md) 提到的例子——"如果用户是新用户 AND 当前在活动城市 AND 首单未完成，则展示新客立减券"。如果这类策略直接写成 Java 的 if-else，会有几个致命问题：运营人员想新增一条策略（"周末且是雨天则司机端展示天气补贴提示"）必须找研发排期开发和发版，响应速度以天甚至周计；不同策略之间的判断逻辑写在同一段代码里，越堆越多，最终变成谁都不敢动的"屎山代码"；策略上线后想快速调整某个阈值（比如把"近7天"改成"近3天"）也要走完整的发版流程，无法快速试错。

规则引擎的核心价值就是把"业务规则"从"程序代码"中分离出来，变成可以在运行时动态加载、动态修改的**数据**（配置），而不是需要重新编译部署的**代码**。

### 规则引擎的三种设计模式

**决策表模式**：把规则组织成一张表，每一行是一条规则，列是条件和动作。比如一张"用户分层策略表"：条件列（注册天数、近30天订单数、近30天消费额），动作列（分层结果）。这种模式最直观，运营人员在后台像编辑 Excel 一样配置规则，适合条件相对简单、规则数量不太多的场景。

**规则链/决策树模式**：规则之间有优先级和依赖关系，用决策树或者责任链模式组织。比如判断"是否需要人工审核"，先判断"是否新用户"，如果是则进一步判断"金额是否超过500"，否则判断"是否命中风控黑名单"。这种模式适合规则之间有层级关系、需要短路优化（一旦某个条件不满足就不需要继续判断后续条件）的场景，实现上通常用组合模式（Composite Pattern，详见[第三章 3.17 设计模式](../part3-java-deep/17-设计模式.md)）把每个判断节点抽象成统一接口，树形组装。

**表达式引擎模式**：把规则写成类似代码的表达式字符串（比如 `age > 18 && city == 'Beijing' && (orderCount > 10 || vipLevel >= 3)`），用表达式解析引擎（Aviator、MVEL、QLExpress 是 Java 生态常见的轻量表达式引擎；Drools 是更重量级的完整规则引擎，支持复杂的规则冲突消解）在运行时动态解析和执行。这种模式表达能力最强，能覆盖决策表和规则链无法优雅表达的复杂逻辑组合，但对运营人员不够友好（需要理解表达式语法），通常需要在配置后台包一层可视化的条件构建器，把用户在 UI 上拖拽拼接的条件，后台转译成表达式字符串。

### 规则引擎的执行性能优化

规则引擎最大的顾虑是"配置化会不会牺牲性能"，毕竟表达式解析比直接执行编译好的 Java 代码要慢。工业界的优化思路主要有三条：**规则预编译**——规则一旦配置好，不是每次请求都重新解析表达式字符串，而是解析一次后缓存编译后的可执行结构（比如 QLExpress 会把表达式编译成字节码，Drools 会把规则编译成 Rete 算法的决策网络），后续请求直接复用编译结果；**规则索引与短路**——如果一个业务场景有几百条规则，不是每次都遍历全部规则挨个判断，而是基于规则的关键条件建立索引（比如按城市分组），请求进来先根据自身属性快速定位到可能命中的规则子集，减少无效判断；**规则灰度与版本管理**——新配置的规则不是立即对所有流量生效，而是先在小流量灰度验证效果（类比 [第三章 3.7 高可用架构](../part3-java-deep/07-高可用架构.md) 里的灰度发布思路），确认没问题再逐步放量，同时保留规则的历史版本，出问题能快速回滚到上一个版本。

### 规则引擎与标签系统的协同

在实际的策略平台里，标签和规则是紧密协同的两层——标签系统负责回答"这个用户/订单是什么样的"（是否新用户、消费层级、风险等级），规则引擎负责回答"知道了这些标签之后应该怎么做"（展示什么优惠、是否需要审核、走哪个派单策略）。架构上通常是策略决策请求先并行查询规则里用到的所有标签（这一步复用 [11.2](./02-高并发中台架构全景.md) 提到的多级缓存 + 线程池并发查询），拿到标签结果后再喂给规则引擎做判断，两层各自独立演进——运营可以只改规则不动标签定义，也可以只优化标签计算逻辑不动上层规则，这种解耦是中台架构"高内聚低耦合"设计原则的典型体现。

## 3. 一个完整的策略执行示例

把上面的概念串起来，看一个具体的策略执行过程：网约车用户打开 App 首页，请求"是否展示新客立减券"。请求进入策略服务后，服务层先解析这条策略依赖哪些标签（假设是"是否新用户""当前城市是否在活动城市列表""是否有未完成的首单"），用线程池并发查询这三个标签——"是否新用户"这种高频标签命中本地缓存直接返回，"当前城市是否活动城市"查询 Redis（活动城市列表不常变化，缓存命中率高），"是否有未完成首单"可能需要实时查询订单服务的一个轻量接口。三个标签结果汇总后，喂给规则引擎（假设用的是决策表模式），引擎按预先配置好的规则表逐行匹配，命中"新用户 AND 活动城市 AND 首单未完成"这一行，触发对应动作——返回"展示新客立减券"的决策结果，整个过程要求在几十毫秒内完成，因为这条请求还在用户打开首页的关键渲染路径上。

这个例子完整呈现了标签系统和规则引擎如何在真实的高并发中台里协同工作，也呼应了 [11.2](./02-高并发中台架构全景.md) 强调的核心设计原则：**每一层都要为极致的低延迟服务，多级缓存、并发查询、规则预编译，本质上都是在和"百万级 QPS 下毫秒级响应"这个约束做斗争**。
