# 11.1 岗位拆解：JD 逐条分析与知识映射

## 原始 JD

**岗位职责：**

1. 负责滴滴标签和策略平台建设，业务覆盖网约车、两轮车、国际化等公司所有核心业务场景，峰值 QPS 百万级，数据量百级级；
2. 负责数据和算法在线服务开发和运维，保障线上业务稳定性；
3. 与业务部门深度合作，持续提升标签和策略平台能力和用户体验。

**任职资格：**

1. 计算机或相关专业本科以上学历，3 年以上后端研发工作经验；
2. 深度掌握 Java 和 Spring 等常用的开发框架，有 C++/Python/Go 等经验加分；
3. 熟悉多线程编程和 JVM 性能调优，有高并发、高吞吐量服务开发经验者优先；
4. 熟悉 RPC、Redis、MQ、MySQL 等常用中间件，有稳定性工具开发经验加分；
5. 有 Agent 研发、Harness Engineering 实践经验加分；
6. 做事严谨踏实，责任心强；具有良好的沟通能力和团队意识。

## 先建立技术画像

在逐条拆解之前，先回答一个问题：这份 JD 到底在招一个什么样的人？

它不是招算法工程师（虽然职责里提到"算法在线服务"，但落点是"开发和运维"，不是"训练模型"），也不是招大数据平台工程师（虽然提到"数据量百级级"，但没有 Hive/Spark/Flink 这类关键词）。它招的是一个**标准的 Java 高并发中台后端工程师**——用 Spring 生态承接业务方（网约车、两轮车、国际化）对"某个用户/某个订单是否命中某个标签、应该走哪条策略"的实时查询和决策请求，QPS 峰值百万级，背后是缓存、中间件、稳定性的综合考验。

和第九章自动驾驶案例（涉及大量陌生的车端/仿真领域知识）、第十章密码安全案例（涉及国密、量子网络等高度专业化领域）相比，这份 JD 的特殊性在于：**它考察的几乎全是后端通用能力，领域知识占比很低**。这决定了这一章的覆盖度分析会呈现出和前两章完全不同的结构——大量条目直接命中已有章节，真正的缺口集中在两三个点上。

## 逐条拆解

### 职责 1：标签和策略平台 + 百万级 QPS + 百级数据量

**JD 关键词：** 标签平台、策略平台、多业务场景、峰值 QPS 百万级、数据量百级级

**技术本质：** 这是一个典型的**读多写少、强一致性要求不高、但延迟极其敏感**的中台系统。业务方（网约车派单、两轮车定价、国际化风控）在请求处理链路上需要实时查询"这个用户/司机/订单命中了哪些标签""按什么策略处理"，每次查询要求毫秒级返回，因为它嵌在主链路里。百万级 QPS 意味着不可能每次都查数据库，必须有多级缓存；百级数据量（通常指标签数据的总规模在百亿到百万亿行级别，也可能指服务的数据总量达到"百级 TB/PB"）意味着底层存储必须是分布式的，且要考虑冷热分离。

### 任职要求 5：Agent 研发 + Harness Engineering 实践

**JD 关键词：** Agent 研发、Harness Engineering

**技术本质：** 这是 JD 里最新、最容易被忽视、也最值得单独拎出来的一条。"Agent 研发"指参与过 AI Agent（智能体）系统的设计和开发；"Harness Engineering"是一个相对新的工程概念，指为 AI Agent 构建可靠的执行环境和工具调用链路——包括 Agent 运行时的沙箱隔离、工具调用的可靠性保障、评测 Harness（测试挽具/测试框架）的设计，本质上是"给 Agent 搭一套靠谱的脚手架，让它能安全、可控、可评测地执行任务"。这条要求出现在一个标签策略平台岗位里，说明团队可能在探索用 Agent 自动化标签规则配置、策略生成或者稳定性运维（比如自动分析故障日志、自动生成限流规则）。

## 覆盖度总结

全书对这份 JD 的覆盖度约 **80% 已覆盖、20% 有缺口**，是三个案例研究章节里覆盖度最高的一个。

这个结果本身就是一个重要发现：**当一份 JD 的核心是"扎实的 Java 后端功底"而不是某个垂直领域时，第三章打下的地基几乎能覆盖全部考点**。并发体系、JVM 调优、网络 IO、高可用架构、Redis、消息队列、MySQL、Spring、分布式锁——这九个知识点几乎是逐字对应 JD 的任职要求，说明这本书第三章的选题和深度，本身就是照着"一线互联网公司高并发中台后端"这个岗位画像设计的。

真正的缺口分两类。**通用知识缺口**（可以补充到现有章节或新增小节）：Harness Engineering（完全空白，AI 时代的新工程概念）、Agent 工具调用可靠性与评测体系、RPC 框架协议细节（Dubbo/gRPC）、稳定性工具自研案例、Java 到 C++ 的语言对比。详见 [11.3 通用知识缺口](./03-通用知识缺口.md)。

**领域知识缺口**（本章新增分析）：标签系统的存储与计算架构（Bitmap/RoaringBitmap、离线+实时融合）、规则引擎/策略引擎的设计模式（规则配置化、决策树/规则链、灰度与版本管理）。详见 [11.4 领域知识](./04-领域知识.md)。

值得指出的是，这两类领域知识缺口虽然在全书里目前是空白，但它们并不是孤立的新知识——规则引擎的执行模型和第八章 marimo 的 DAG 依赖分析有相通之处，标签存储的 Bitmap 方案和第三章附录 A1 的布隆过滤器属于同一类"用空间换时间的概率型/压缩型数据结构"思路。这再次印证了全书的核心方法论：**新领域的知识往往不是凭空出现的，而是已有知识在新场景下的重新组合和延伸**。
