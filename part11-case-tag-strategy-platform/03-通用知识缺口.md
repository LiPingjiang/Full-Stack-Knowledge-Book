# 11.3 通用知识缺口：Harness Engineering、Agent 工程化、RPC 框架深度

本节梳理 JD 暴露的通用技术知识缺口。和第九章、第十章不同，这份 JD 的通用知识缺口不多，因为大部分通用能力已经被第三章覆盖。真正值得展开的是三个点：Harness Engineering（完全空白的新概念）、Agent 工具调用的工程化可靠性（在已有 Agent 基础上的补充）、以及 RPC 框架的协议层细节。

## 1. Harness Engineering：给 AI Agent 搭建可靠的执行脚手架

### 为什么需要

JD 明确提到"有 Agent 研发、Harness Engineering 实践经验加分"。这是全书目前完全没有覆盖的概念，也是当前 AI 工程领域相对新的一个方向。理解它，需要先理解一个问题：一个 Agent（智能体）光有"聪明的大脑"（大模型）是不够的，它还需要一套"手脚和安全带"——能安全地执行代码、能可靠地调用工具、能在出错时被观测和纠正、能被系统性地评测好坏。这套"手脚和安全带"就是 Harness（原意是"挽具/背带"，引申为给 Agent 提供的执行环境和工具链）。

### 核心知识点

**Harness 的三层职责：** 执行环境隔离——Agent 生成的代码或指令不能直接在宿主环境跑，需要用容器/微虚拟机（gVisor、Firecracker、或者更轻量的进程沙箱）隔离，防止 Agent 跑飞（比如误删文件、跑死循环）影响宿主系统。这跟 [附录 A8 Linux 操作系统基础](../part3-java-deep/A8-Linux操作系统基础.md) 里 namespace + cgroup 的隔离思路是同一套底层机制，只是应用场景从"容器化部署应用"变成了"隔离 Agent 的执行"。工具调用可靠性——Agent 调用外部工具（搜索、代码执行、API 调用）时，工具本身可能超时、返回格式不对、或者暂时不可用，Harness 需要提供统一的重试、超时、降级机制，这和 [第三章 3.7 高可用架构](../part3-java-deep/07-高可用架构.md) 的超时重试幂等设计是完全一致的工程套路，只是调用对象从"下游微服务"变成了"Agent 工具"。结果校验与纠错——Agent 的输出不像传统程序那样确定性强，Harness 要能校验输出格式（比如强制 JSON Schema 校验）、检测明显错误的输出并触发重新生成或人工介入。

**Eval Harness（评测挽具）：** 这是 Harness Engineering 里独立且重要的一块——如何系统性地评测一个 Agent 的表现好坏。核心要素包括：标准化的测试用例集（给定输入场景，定义期望的行为或输出）、自动化的评分机制（用规则匹配、或者用另一个模型做裁判——LLM-as-Judge）、回归测试机制（每次改动 Prompt 或工具后，跑一遍完整的 Eval 集，防止改好一个场景却搞坏另一个场景）。这和传统软件工程里的单元测试、回归测试是同一套思想在 Agent 领域的延伸，只是"断言"从"结果是否等于某个确定值"变成了"结果是否满足某种质量标准"。

**沙箱与资源限制：** Agent 执行代码时需要限制 CPU、内存、网络访问、执行时长，防止失控的 Agent 消耗过多资源或者做出危险操作（比如访问不该访问的内网地址）。常见实现是用容器 + seccomp（限制系统调用）+ 网络策略（白名单出口）的组合，这部分工程实践和第三章 A8 的 cgroup 资源限制、以及第三章高可用架构里的资源隔离（舱壁模式）是相通的。

**为什么标签策略平台团队会关心这个：** 可以合理推测，团队可能在探索用 Agent 辅助规则配置（运营人员用自然语言描述一个策略，Agent 自动生成规则引擎的配置）或者辅助稳定性运维（Agent 自动分析异常日志、推荐限流阈值调整），这些场景都要求 Agent 的执行结果必须可控、可回滚、可评测——这正是 Harness Engineering 要解决的问题。

建议补充到 [第七章 7.6 Agent 基础](../part7-ai-engineering/06-Agent基础.md) 之后，新增一节专门讲 Agent 工程化落地（沙箱隔离、工具调用可靠性、Eval Harness），作为"Agent 基础"（讲清楚 Agent 怎么思考和决策）到"Agent 工程化"（讲清楚怎么让 Agent 安全可靠地跑在生产环境）的自然延伸。

## 2. Agent 工具调用的可靠性设计

### 为什么需要

第七章 7.6 已经覆盖了 Function Calling 和 MCP 协议的基础概念，但这份 JD 更强调"研发经验"，说明面试官可能会追问工程落地细节，而不只是协议层面的理解。

### 核心知识点

**工具调用的幂等性设计：** 如果 Agent 因为超时重试了同一个工具调用（比如"给用户发一条优惠券"），必须保证不会重复发放。这和 [第三章 3.7 高可用架构](../part3-java-deep/07-高可用架构.md) 幂等设计的思路完全一致——给每次工具调用生成唯一的请求 ID，下游服务基于请求 ID 去重。

**工具调用的超时分级：** 不同工具的耗时差异巨大（查天气可能 100ms，跑一段代码可能 30s），Harness 需要给不同工具设置不同的超时阈值，而不是一刀切，这也是高可用架构里"分级超时"思路的直接迁移。

**多工具并发调用的编排：** 当 Agent 一次决策需要调用多个独立工具时（比如同时查天气和查日历），可以用 [第三章 3.1 并发体系](../part3-java-deep/01-并发体系.md) 里 CompletableFuture 的编排模式并行发起，缩短整体延迟。

### 补充位置

作为 [第七章 7.6 Agent 基础](../part7-ai-engineering/06-Agent基础.md) 的工程实践补充小节，与新增的 Harness Engineering 小节合并考虑。

## 3. RPC 框架协议层细节

### 为什么需要

JD 要求"熟悉 RPC"，第三章 3.14 微服务与分布式锁覆盖了服务注册发现、配置中心、网关这些服务治理层面的内容，但没有深入 RPC 框架本身的协议设计和序列化机制，这是面试中经常被追问的细节。

### 核心知识点

**RPC 的本质：** 让远程调用像本地方法调用一样简单，核心要解决四个问题——如何表示调用（接口和参数的序列化）、如何传输（网络协议）、如何找到服务提供者（服务发现，已在 3.14 覆盖）、如何处理调用失败（超时重试，已在 3.7 覆盖）。

**序列化协议对比：** Java 原生序列化性能差、体积大，生产环境很少用。主流选择是 Protobuf（Google 出品，二进制、体积小、跨语言，需要预定义 IDL）、Hessian（Dubbo 默认，二进制、支持动态类型，不需要预定义 schema）、JSON（可读性好但体积大性能差，一般只用于调试或跨语言边界不那么敏感的场景）。序列化性能直接影响 RPC 调用的吞吐量，百万级 QPS 场景下序列化开销是不能忽视的成本。

**Dubbo vs gRPC：** Dubbo 是阿里开源的 Java RPC 框架，基于自定义协议（默认 Hessian2 序列化），深度集成 Spring，服务治理能力强（服务发现、负载均衡、限流、路由规则都内置），适合 Java 技术栈为主的团队。gRPC 是 Google 开源的跨语言 RPC 框架，基于 HTTP/2 + Protobuf，天然支持流式调用（客户端流、服务端流、双向流），适合多语言混合技术栈或者需要流式通信的场景。选型上，纯 Java 中台系统通常倾向 Dubbo 这类深度集成的框架，需要和非 Java 服务（比如算法团队的 Python 推理服务）互通时，gRPC 的跨语言优势更明显。

**长连接与连接池：** RPC 调用通常复用长连接（避免每次调用都做 TCP 三次握手），客户端维护到每个服务提供者的连接池，这跟 [附录 A2 网络协议基础](../part3-java-deep/A2-网络协议基础.md) 里 TCP 握手挥手的知识直接相关——理解为什么要用长连接，本质上是理解三次握手的开销在高频调用场景下不可接受。

### 补充位置

建议扩展到 [第三章 3.14 微服务与分布式锁](../part3-java-deep/14-微服务与分布式锁.md)，在现有的服务注册发现内容基础上，新增 RPC 协议与序列化的小节，把"服务怎么被发现"和"服务之间怎么通信"这两块拼成完整的服务治理图景。

## 4. Java 到 C++ 的语言对比

### 为什么需要

第四章已经覆盖了 Java 到 Go、Rust、Python、JS/TS 的对比，唯独没有 C++。这份 JD 把 C++ 列为加分项，通常对应"自研高性能中间件"或者"极致性能优化"场景——比如标签平台里对延迟极其敏感的核心链路，可能会用 C++ 写一个轻量级的本地缓存组件或者网络代理，通过 JNI 或者进程间通信的方式跟 Java 主服务集成。

### 核心知识点

**内存管理哲学的对立：** Java 是 GC 自动管理（体验好但有 STW 停顿风险，详见 3.3 JVM 运行时），C++ 是手动管理或 RAII 智能指针管理（无 GC 停顿但要求开发者对内存生命周期极其谨慎，一处 use-after-free 或内存泄漏就是生产事故）。这是 Java 转 C++ 工程师最大的心智负担转换。

**零成本抽象：** C++ 的设计哲学是"你不用的特性不应该有性能代价"，模板在编译期展开、内联函数消除调用开销，这跟 Java 依赖 JIT 在运行时优化的思路完全不同——C++ 把优化尽量前移到编译期，Java 把优化放在运行时根据实际执行情况动态决策。

**适用边界：** 不是所有场景都要上 C++。C++ 的价值在于极致的延迟敏感场景（比如需要亚毫秒级响应的本地缓存层）或者需要直接操作硬件资源的场景（自定义内存池、零拷贝网络库）。标签策略平台的主体业务逻辑用 Java + Spring 完全够用，C++ 只在性能瓶颈被精确定位之后才考虑引入，引入的代价（团队维护成本、调试难度上升）要和收益仔细权衡。

### 补充位置

补充到第四章，新增一节 Java 到 C++ 的对比，风格上参照 [4.4 Java 到 Rust](../part4-multilang-compare/04-Java到Rust.md) 讲所有权模型的方式，重点讲内存管理哲学的差异和零成本抽象的设计思想。

## 5. 稳定性工具自研案例

### 为什么需要

JD 提到"有稳定性工具开发经验加分"，第三章 3.7 高可用架构讲透了限流、熔断、降级的**原理**，但原理和"真正设计并实现一个限流组件/压测平台"之间还有一层工程落地的距离，这也是面试中区分"用过框架"和"做过框架"的关键点。

### 核心知识点

**从使用到自研的差距：** 使用 Sentinel/Hystrix 这类现成框架只需要会配置参数；自研一个限流组件需要考虑更多工程细节——限流规则如何热更新而不重启服务（通常接入配置中心，规则变更后推送到所有实例）、限流阈值如何支持动态调整（结合监控指标自动调整，而不是写死一个固定值）、限流组件本身的性能开销（限流逻辑要足够轻量，不能让"保护系统的组件"反而成为新的性能瓶颈）。

**压测平台的核心设计：** 一个稳定性压测平台通常包括压测流量生成（模拟真实的 QPS 曲线和请求分布，而不是简单地打固定并发）、影子链路（压测流量要能安全地打到生产环境验证真实容量，同时不能污染真实数据，需要请求打标 + 下游数据隔离）、压测报告分析（自动识别系统瓶颈——是 CPU、内存、网络、还是某个下游依赖）。
