# 10.2 密码基础设施全景：KMS、PKI、HSM 与密钥生命周期

密码基础设施的目标不是“提供一个加解密 API”，而是在不暴露根密钥的前提下，为大量租户和业务系统提供可授权、可审计、可轮换、可恢复的密码能力。

## 1. 核心组件

KMS 是控制面：创建、导入、授权、轮换、禁用和销毁密钥；HSM 是信任根：在防篡改硬件中生成和使用根密钥，私钥不以明文离开硬件；PKI/CA 负责身份凭证和证书链；业务服务使用 SDK 取得短期授权后调用 KMS。审计系统记录主体、租户、密钥 ID、用途、算法、结果、request_id 和时间，日志不得含密钥材料或明文数据。

## 2. 信封加密与密钥分层

大数据不应直接用主密钥加密。业务先请求 KMS 生成 DEK（数据加密密钥），本地用 DEK 加密文件；KMS 用 KEK（密钥加密密钥）包裹 DEK，保存“密文数据 + 加密后的 DEK”。KEK 再受 HSM 中 MK（主密钥）保护。读取时只有获授权主体可让 KMS 解包 DEK。该设计减少 HSM/KMS 数据面压力，也让轮换 KEK 时只需重包 DEK，不必重加密全部数据。

## 3. 生命周期与可靠性

生命周期为：生成/导入 → 激活 → 使用 → 轮换 → 禁用 → 归档 → 销毁。密钥 ID 必须稳定且版本化；密文保存 `key_id + key_version + algorithm`，否则轮换后无法解密历史数据。删除应先进入 scheduled deletion 等待期，防止误操作造成不可逆数据丢失。

异地多活的难点是密钥元数据、授权策略、审计与密钥版本的一致性。根密钥/HSM 通常不能简单跨地域复制，应采用同城双活 HSM 集群、异地灾备域、明确的主写和故障切换流程。安全系统宁可短时拒绝高风险写入，也不能因脑裂产生同一密钥 ID 的冲突版本。

## 4. KMS API 设计要点

API 按“资源管理”和“密码操作”分层：前者如 CreateKey、RotateKey、PutPolicy；后者如 Encrypt、Decrypt、GenerateDataKey、Sign、Verify。授权策略需同时校验身份、租户、资源、操作、用途、环境条件；Decrypt 和 Sign 是高风险操作，应限流、强审计、支持幂等 request token。SDK 只持有凭证和密钥引用，不能缓存或返回主密钥明文。
