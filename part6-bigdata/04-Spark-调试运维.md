# 6.4 Spark 调试运维

> 适用场景：任务挂了、秒退、UI 正常但作业失败、日志找不到、同样报错在不同运行环境下排查入口完全不同  
> 阅读前提：已了解 Spark 基本执行模型，以及 Driver / Executor / Cluster Manager 的角色  
> 相关阅读：  
> - [Spark 错误排查与兼容性](./04-Spark-错误排查与兼容性.md)  
> - [Spark 部署与云原生运行](./04-Spark-部署与云原生运行.md)

## 一、先明确：这篇不是错误百科，而是“先去哪里看”的文档

Spark 出问题时，很多人第一反应是：

- 先搜异常栈；
- 先调一个参数；
- 先盯着 Spark UI 看半天；
- 或者干脆先去翻 SQL。

这几种做法都可能有效，但最大的问题是：**没有入口顺序。**

这篇文档要解决的不是“所有错误是什么”，而是更前一步的问题：

> **当 Spark 出问题时，你应该先去哪里取证，怎样判断问题属于哪一层，再决定跳到哪个专题深挖。**

所以它的核心任务是：

1. 帮你区分 **提交失败 / 运行失败 / 结果异常**；
2. 帮你知道日志和 UI 分别能证明什么；
3. 帮你区分 YARN 和 Kubernetes 下的排障入口差异；
4. 帮你建立一条从“现象”到“证据”再到“根因专题”的路径。

## 二、第一步永远不是看栈，而是先给问题分入口

### 2.1 提交失败：任务刚出去就挂

提交失败的典型特征是：

- 任务刚提交就退出；
- Spark UI 可能根本没完整起来；
- 连 stage / task 痕迹都看不到；
- 常见于主类错误、依赖缺失、提交参数问题、环境变量问题、AM / Driver 初始化失败。

这类问题最重要的判断是：**它还没真正进入“执行期”。**

所以此时排障入口通常不该先看 Stage 页面，而应先看：

- 提交端输出；
- Driver / AM 初始化日志；
- 资源管理器给出的启动失败信号。

### 2.2 运行失败：作业已经跑起来了，但半路挂掉

运行失败的典型特征是：

- UI 能打开；
- 已经有 stage / task 运行痕迹；
- 失败常出现在某个执行阶段；
- 日志通常能看到较明确的 Executor / task / shuffle / 数据源异常。

这类问题的主入口就从“启动链路”切换为：

- 异常 stage；
- 失败 task；
- 对应 Executor / Pod / Container 日志；
- 外部系统交互阶段。

### 2.3 结果异常：任务成功了，但产出不对

这是最容易被忽视的一类，因为表面上“任务成功”。但常见问题包括：

- 数据量不对；
- 分区不对；
- 结果重复或缺失；
- 过滤位置错导致语义偏差；
- 版本行为变化导致结果边界变化。

这类问题和“挂了”不是一套排障思路。它更强调：

- UI 只是辅助；
- 日志未必直接报错；
- 需要回到 SQL 语义、执行计划、结果校验路径。

### 2.4 为什么先分入口，比先看栈更重要

因为“同样一句异常”，在不同入口下意义完全不同。

例如：

- Driver 启动期抛异常，和 Executor 执行中抛异常，不是一类问题；
- UI 起不来时看 Stage 页面没有意义；
- 任务成功但结果异常时，盯资源参数往往完全跑偏。

所以 Spark 调试运维的第一原则不是“先搜报错”，而是：

> **先确认问题发生在启动链路、执行链路，还是结果校验链路。**

## 三、第二步：日志和 UI 各自证明什么

### 3.1 日志证明“谁出错、在哪层出错”

日志最重要的价值是：

- 告诉你异常栈；
- 告诉你是 Driver、Executor、AM、Client、Pod 还是外部系统先报错；
- 告诉你失败发生在初始化、运行、写出还是回收阶段。

没有日志，你很容易只看到症状，不知道哪个组件先出问题。

### 3.2 UI 证明“执行过程哪里表现异常”

Spark UI 更擅长回答这些问题：

- 哪个 stage 慢；
- 哪类 task 拖尾；
- 哪段计划出现明显瓶颈；
- 有没有明显倾斜、Spill、Shuffle 异常；
- 任务是压根没开始，还是已经跑进执行期。

所以 UI 更像“表现层证据”，日志更像“根因层证据”。

### 3.3 为什么只看 UI 容易误判

只看 UI 容易得出这种不完整结论：

- “这个 stage 很慢，所以应该调并行度”；
- “这个 executor 消失了，所以应该是代码 bug”；
- “UI 没异常图形，所以问题应该不在 Spark。”

这些判断都可能错，因为 UI 本身通常不告诉你：

- 为什么 executor 消失；
- 本地文件为什么丢；
- Driver 初始化到底在哪一步炸掉；
- Pod / Container 是被谁杀的。

### 3.4 为什么只看日志也不够

只看日志又容易遇到另一类问题：

- 知道某个异常栈，但不知道它在整条执行链上的位置；
- 看见 OOM，却不知道是偶发单 task 还是系统性分区过粗；
- 看见 FetchFailed，却不知道它是不是只发生在极少数异常分区上。

所以更成熟的方式是：

> **先用 UI 找异常执行位置，再回日志确认技术根因。**

## 四、先把日志来源分清：你到底该去哪儿找证据

### 4.1 Driver、Executor、AM、Client 日志分别回答什么

至少要分清四类日志：

- **Driver 日志**：初始化、SparkContext 建立、全局控制流、最终失败汇总；
- **Executor 日志**：task 执行、数据读取、Shuffle 拉取、OOM、序列化、写出异常；
- **AM 日志**：YARN 语境下应用启动、资源申请、启动链路问题；
- **Client 日志**：client 模式下提交端最早看到的报错，尤其适合排查“刚提交就失败”。

很多 Spark 排障之所以绕路，就是因为没先区分“谁的日志最该先看”。

### 4.2 stdout、stderr、syslog 不是一回事

一般可以这样理解：

- `stdout`：程序主动 print 的内容；
- `stderr`：程序错误输出；
- `syslog`：框架日志、log4j / slf4j 体系输出，通常最有结构性。

真实生产排障里，**syslog 往往最有价值**，因为它更可能留下：

- Spark 框架日志；
- 组件级别报错；
- 初始化链路信息；
- 更完整的上下文。

### 4.3 运行中日志和已结束日志的入口经常不同

同一个作业，运行中和结束后的取证路径可能完全不同：

- 运行中更常从资源管理器或 Pod 日志入口看；
- 已结束后可能转向聚合日志、History Server、调度平台归档日志。

如果你不知道这点，就容易在“作业已经结束”的情况下还去找实时日志入口，结果误以为日志丢了。

## 五、YARN 下怎么排：先围绕 Application ID 建立路径

### 5.1 YARN 下最关键的索引是 Application ID

YARN 环境下，很多排障的真正起点不是 Spark UI，而是：

- Application ID；
- tracking URL；
- 对应的 Container / AM 记录。

因为它们把“这次运行实例”稳定标识出来了。

### 5.2 YARN 的典型排障入口

YARN 语境下，通常优先围绕这些东西排：

- ApplicationMaster；
- Container exit code；
- NodeManager 视角；
- 聚合日志；
- ResourceManager 页面。

如果作业已经结束，官方常用入口就是：

```bash
yarn logs -applicationId <app ID>
```

这条命令很实用，因为它能把该应用相关容器日志整体拉出来，适合做第一轮取证。

### 5.3 哪些场景先看 AM / Driver，而不是 Executor

以下情况通常先看 AM / Driver：

- 任务秒退；
- UI 根本没起来；
- SparkContext 没初始化成功；
- 提交参数、主类、依赖明显可疑。

这时如果你一上来就找 Executor 日志，往往会发现根本没有有效内容。

### 5.4 哪些场景再转向 Executor

如果已经有 stage / task 痕迹，再转向 Executor 更合理，典型包括：

- OOM；
- FetchFailed；
- 读写异常；
- 某个 stage 半路失败；
- 极少数 executor 或节点反复异常。

## 六、Kubernetes 下怎么排：先围绕 Driver Pod 建立路径

### 6.1 K8s 下最关键的起点通常是 Driver Pod

Kubernetes 下，排障入口经常不再是 Application ID，而是：

- Driver Pod 是否成功起来；
- Driver Pod 日志里有没有初始化失败；
- Executor Pod 是否被调度成功；
- Pod 事件里有没有驱逐、调度失败、镜像或卷问题。

所以 K8s 上的第一视角更像“看 Pod 生命周期”，而不是“看应用容器编号”。

### 6.2 K8s 下除了日志，还要看事件

这是和传统 YARN 语境很不一样的一点。K8s 上很多关键证据不只在日志里，还在：

- Pod event；
- 调度失败原因；
- 驱逐记录；
- 节点资源压力信息；
- 卷挂载或本地存储相关事件。

如果你只看日志，很可能漏掉“Pod 根本没成功落位”这种更早的失败原因。

### 6.3 为什么同样是 executor 消失，在 K8s 下解释框架不同

同样是 executor 丢了：

- 在 YARN 下，你更容易先想到容器被 kill、节点异常、资源超限；
- 在 K8s 下，你还必须想到 Pod 驱逐、节点回收、本地卷、PVC、调度和生命周期语义。

也就是说：**同一个表面现象，在不同运行环境下，先验怀疑对象是不一样的。**

## 七、Spark UI 该怎么用，才不会沦为“看着很忙”的页面

### 7.1 SQL / Stage / Executor 页面分别回答什么

- **SQL 页面**：查询结构、物理计划路径、哪个节点最重；
- **Stage 页面**：task 分布、输入输出量、Shuffle、拖尾、失败重试；
- **Executor 页面**：executor 存活、资源消耗、失败节点、黑名单等信息。

所以 UI 不是“看哪个数字红了”，而是用来回答：**问题更像发生在计划层、执行层，还是资源层。**

### 7.2 UI 正常出现，说明了什么，不说明什么

如果 UI 能正常打开，通常说明：

- Driver 至少完成了基本启动；
- SparkContext 基本建立；
- 作业已经进入执行语境。

但它不说明：

- 运行环境没问题；
- 本地盘没问题；
- 某个 executor 为什么丢；
- 外部系统为什么拒绝写入。

所以“UI 能打开”只能帮你排除“完全没启动”，不能证明“剩下都正常”。

### 7.3 UI 与日志怎么互证

推荐顺序非常固定：

1. 在 UI 找到异常 stage / task / executor；
2. 记下它落在哪个组件、哪个节点或哪个 Pod 上；
3. 回到对应日志或事件里找具体异常栈；
4. 再判断是 Spark 内部问题、运行环境问题还是外部系统问题。

这条路径几乎适用于绝大多数运行失败问题。

## 八、几类高频运维现场，第一反应该看什么

### 8.1 任务秒退

先看：

- client 模式下的提交端日志；
- cluster 模式下的 Driver / AM 初始化日志；
- 主类、参数、依赖、环境变量。

不要先去找 Stage 页面，因为这类问题通常还没到那一步。

### 8.2 UI 正常但作业失败

这通常意味着：

- 不是纯提交失败；
- 问题大概率已经进入执行期；
- 应该先定位失败 stage / task，再找对应 Executor / Pod 日志。

### 8.3 Executor 反复丢失

先问：

- 是业务逻辑打挂了 executor，还是运行环境回收了它？
- 是否伴随 OOM、容器 kill、Pod 驱逐、本地盘异常？
- 是否集中在少数节点？

这类问题最怕的就是直接下结论“代码有 bug”或“平台有问题”，而不看证据。

### 8.4 日志缺失

如果连日志都拿不到，优先怀疑：

- 日志聚合没开或失败；
- 作业已结束且实时入口不可用；
- Pod / 容器生命周期太短；
- 历史保留策略不够；
- 你找错了运行环境入口。

### 8.5 同样错误在 YARN 和 K8s 上为什么排法不同

因为它们的运行模型不同：

- YARN 更强调应用生命周期、Container、NodeManager；
- K8s 更强调 Pod、事件、卷、节点回收与调度。

所以“报错文本相同”不代表“第一排查入口相同”。

## 九、一条可复用的现场取证流程

如果你想要一条通用的 Spark 取证路径，可以按下面顺序：

1. **先分入口**：提交失败、运行失败、结果异常；
2. **再分组件**：Driver、Executor、AM、Client、Pod、外部系统；
3. **看 UI 判断位置**：有没有进入执行期、哪个 stage / task 异常；
4. **回日志 / 事件确认根因**：是代码、资源、网络、存储还是环境问题；
5. **最后再跳专题**：
   - 资源与 Spill → [Spark 资源内存与 Spill 调优](./04-Spark-资源内存与Spill调优.md)
   - 兼容性 / 错误分型 → [Spark 错误排查与兼容性](./04-Spark-错误排查与兼容性.md)
   - 运行环境差异 → [Spark 部署与云原生运行](./04-Spark-部署与云原生运行.md)

这条流程最重要的作用，是避免你一上来就“先调参数”。

## 十、最后总结：这篇调试运维文真正要教会你的是什么

这篇文档的核心不是告诉你每一种报错是什么意思，而是让你建立下面这套习惯：

- **先分问题入口，再看异常文本；**
- **先找最有证据价值的组件日志，再谈参数；**
- **先用 UI 定位异常执行位置，再回日志确认根因；**
- **在 YARN 和 Kubernetes 下，使用不同的排障入口与解释框架。**

如果你建立了这套路径，那么面对 Spark 任务失败时，你第一反应就不会再是：

> “先搜这个错误是什么意思。”

而会变成：

> “它是在哪条链路、哪个组件、哪个运行环境里先出问题的，我现在最该去看哪份证据？”
