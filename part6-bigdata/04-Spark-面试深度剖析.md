## 一、先建立 Spark 面试的答题框架

很多人 Spark 面试答不差知识点，差的是答题结构。一个成熟回答通常按下面顺序展开：

1. **先给结论**：用 1~2 句话让面试官知道你抓住了主问题；
2. **再讲机制**：说明它为什么这样工作，而不是只背术语；
3. **补边界条件**：告诉面试官你知道它不是万能的；
4. **落到排障或调优语境**：说明你在真实任务里怎么判断、怎么验证。

如果你只会“定义题”，回答会显得像背书；如果你只有经验、没有结构，回答又容易散。下面这篇文档按“**短答 → 展开答 → 面试官为什么问这个 → 常见追问 → 容易答偏的点**”来组织，目的就是把这件事练出来。

## 二、高频必答题

### 2.1 为什么 Spark 比 MapReduce 快

**短答：**  
因为 Spark 尽量减少中间结果落盘，能把多步计算按 DAG 串起来连续执行；同时在 Spark SQL 路径里还有 Catalyst、CBO、AQE 这类优化能力，所以整体吞吐和交互性通常都比传统 MapReduce 更好。

**展开答：**  
这个问题不能只回答“因为 Spark 基于内存”。更完整的说法是：

- **第一，执行模型更连续。** MapReduce 天然按 map / reduce 阶段组织，阶段边界重、落盘多；Spark 则把一串转换操作组织成 DAG，只在宽依赖、Shuffle 等必要位置切 stage。
- **第二，中间结果处理更灵活。** Spark 不是永不落盘，而是尽量少做不必要落盘；当内存不足、发生 Spill、遇到 Shuffle 时依然会落盘，只是默认路径更轻。
- **第三，统一引擎做得更好。** Spark 不是只有 RDD API，还把 SQL、机器学习、流式处理放在同一执行引擎上，很多优化能共用。
- **第四，现代 Spark SQL 优化能力更强。** 今天真正拉开差距的，往往不是“内存”三个字，而是 Catalyst 优化、统计信息、AQE、DPP、Broadcast Join 等机制叠加后的综合效果。

所以更准确的结论是：**Spark 快，不是因为它神奇地把磁盘变没了，而是因为它把不必要的阶段边界、中间落盘和低效执行路径尽量减少了。**

**面试官为什么问这个：**  
这题看起来基础，实际上是在判断你是不是还停留在“Spark = 内存计算”这种过时口号层面。

**常见追问：**  
- Spark 一定比 MapReduce 快吗？
- Spark 什么时候也会大量落盘？
- Spark SQL 的优化和 RDD 时代最大的差别是什么？

**容易答偏的点：**  
- 只会说“因为放内存里”；
- 暗示 Spark 完全不落盘；
- 完全忽略 SQL 优化和运行时优化带来的收益。

### 2.2 RDD 怎么容错

**短答：**  
RDD 主要靠 **lineage（血缘）重算** 来容错，不是默认靠数据副本恢复；当血缘过长或重算代价过高时，可以用 checkpoint 截断血缘。

**展开答：**  
RDD 的核心思想是：每个分区怎么从上游算出来，Spark 都知道。所以分区丢了时，可以根据依赖链重新计算它，而不是必须把每份中间结果都做副本。

这件事的关键点有三个：

- **RDD 记录的是“怎么得到”，不是“每步都存一份副本”。** 这让容错成本在很多场景下更低。
- **窄依赖重算代价通常较可控。** 但一旦血缘很长、依赖复杂、上游又贵，重算成本会明显上升。
- **checkpoint 的意义是截断血缘。** 它不是默认第一选择，因为它本身也有开销；通常在迭代计算、长链路或需要稳定恢复点时更有价值。

所以这题真正想表达的是：**Spark 的容错不是“副本优先”，而是“血缘优先，必要时再物化恢复点”。**

**面试官为什么问这个：**  
它能快速区分“知道 Spark 这个词”和“理解 Spark 设计哲学”的候选人。

**常见追问：**  
- checkpoint 和 cache / persist 有什么区别？
- 如果上游数据源变了，lineage 重算会怎样？
- 血缘太长为什么会成为问题？

**容易答偏的点：**  
- 把 cache 当成容错手段本身；
- 说成 Spark 像 HDFS 一样靠副本恢复 RDD；
- 没有提到 checkpoint 的使用边界。

### 2.3 Job、Stage、Task 是怎么划分的

**短答：**  
Action 触发 Job，宽依赖通常切出 Stage，分区数决定 Task 数量；可以把它理解为：**Job 是一次计算目标，Stage 是被 Shuffle 等边界切开的执行段，Task 是具体落到分区上的最小执行单元。**

**展开答：**  
这题经常被答成定义题，但更好的回答是把三个层次串起来：

- **Job**：由一次 action 触发，例如 `count`、`collect`、`save`；
- **Stage**：DAGScheduler 按依赖关系切出来的执行阶段，最常见的切分点是宽依赖 / Shuffle；
- **Task**：某个 stage 在具体分区上的执行实例，分区数通常直接决定 task 数量。

面试里如果只说“action 产生 job，宽依赖切 stage，分区对应 task”，基本及格；如果能继续补一句：

> “所以调优时看到 stage 很慢，不能只盯 stage 名字，要继续看这个 stage 是被什么算子切出来的、任务是不是分区不均、是不是某几个 task 拖尾。”

这时回答就更像做过真实排障的人。

**面试官为什么问这个：**  
看你能否把抽象概念落到 UI、Shuffle、并行度和调优语境里。

**常见追问：**  
- DAGScheduler 和 TaskScheduler 分别负责什么？
- 为什么窄依赖通常可以流水线执行？
- 分区太多、太少分别会发生什么？

**容易答偏的点：**  
- 只会背定义，不会联系实际调优；
- 说“一个 stage 就是一个算子”；
- 把 task 数量完全等同于 executor 数量。

### 2.4 AQE 解决了什么问题

**短答：**  
AQE（Adaptive Query Execution）解决的是：Spark 在编译期做完计划后，到了运行时还能基于真实统计信息继续优化后续执行计划，例如自动合并过小分区、动态调整部分 Join 策略、缓解部分倾斜 Join 问题。

**展开答：**  
AQE 的价值，不是“又多了几个参数”，而是把 Spark SQL 从“只靠事前估算”推进到“运行时还能修正”。这对真实生产场景特别重要，因为很多问题恰恰出在：

- 统计信息不准；
- 过滤后数据量和预估差很多；
- 上游数据分布和预期不一样；
- 默认 `shuffle.partitions` 很难一次拍准。

AQE 常见收益主要有三类：

- **自动合并 post-shuffle 小分区**，减少很多碎 task；
- **动态切换部分 Join 策略**，例如运行时发现一边比预估小很多，可能从 SortMergeJoin 调整为更合适的路径；
- **处理部分倾斜 Join 场景**，把过大的分区拆开或重新组织。

今天谈 Spark SQL 优化，如果完全不提 AQE，基本说明认知停留在较旧版本经验里。

**面试官为什么问这个：**  
想看你是否理解现代 Spark SQL 的主线，而不是只会调 `spark.sql.shuffle.partitions`。

**常见追问：**  
- AQE 默认开吗？
- AQE 和 CBO、Hint 分别解决什么问题？
- 你怎么判断 AQE 到底有没有帮上忙？

**容易答偏的点：**  
- 把 AQE 说成“自动把所有 SQL 都优化好”；
- 只记住它能“自动合并分区”，却说不出它对 Join 和倾斜的影响；
- 完全不知道它属于 Spark SQL 路径，而不是所有问题都能接管。

### 2.5 AQE 为什么不是万能的

**短答：**  
因为 AQE 只能在执行过程中某些已经物化、拿到真实统计信息的节点之后再优化；它解决不了读取阶段的错误写法、业务写出目标、很多非 SQL 侧问题，也不保证自动重分区一定符合你的最终目标。

**展开答：**  
这题现在很重要，因为不少人把 AQE 讲得像“开了就行”。更成熟的回答应该包括四层边界：

- **第一，它只能处理自己能看到的运行时信息。** 如果问题出在分区裁剪没生效、上游 SQL 写法本身就错、Join 条件设计有问题，AQE 并不会替你重写业务语义。
- **第二，它不是业务目标感知型系统。** 例如你最终想控制输出文件大小和数量，AQE 的自动合并只是在运行时做启发式调整，不等于“自动给你产出最理想文件分布”。
- **第三，它有启发式而不是全局最优。** 官方文档就明确说明了 post-shuffle coalesce 的一些配置是“advisory”而不是强保证。尤其默认 `spark.sql.adaptive.coalescePartitions.parallelismFirst=true` 时，Spark 会优先考虑并行度，不严格服从 `advisoryPartitionSizeInBytes` 目标大小。所以它可能减少小分区，但不代表一定得到你想要的最终分区形态。
- **第四，它覆盖不到所有类型的问题。** 内存模型、Driver OOM、数据源读取问题、非 SQL RDD 逻辑、输出热点等，都不是 AQE 单独能解决的。

所以一句成熟总结是：**AQE 很重要，但它是“运行时纠偏器”，不是“全栈自动驾驶”。**

**面试官为什么问这个：**  
这题是区分“知道新名词”和“知道新名词边界”的关键题。

**常见追问：**  
- AQE 自动合并分区为什么有时会不符合预期？
- 什么情况下你会把 `parallelismFirst` 调成 `false`？
- AQE 能解决数据倾斜吗，能解决到什么程度？

**容易答偏的点：**  
- 说成“有 AQE 就不用管分区了”；
- 完全不知道 advisory size 不是强保证；
- 把 AQE 误讲成资源调度器。

### 2.6 DPP 和传统分区裁剪有什么区别

**短答：**  
传统分区裁剪依赖你在 SQL 里直接写出能命中分区字段的过滤条件；DPP（Dynamic Partition Pruning）则是在维表先被过滤后，把过滤出来的 key 动态传回事实表扫描阶段，从而减少事实表分区读取。

**展开答：**  
这题的关键不是背全称，而是讲清“静态”和“动态”的区别：

- **静态分区裁剪**：你写了 `dt = '2026-08-25'` 这种条件，优化器直接知道应该只读哪些分区；
- **DPP**：过滤条件不直接写在事实表分区字段上，而是先作用于维表，Spark 再把维表过滤结果作为动态裁剪条件回传给事实表扫描。

所以 DPP 最适合的语境通常是：

- 星型模型；
- 维表过滤明显缩小候选 key 集；
- 事实表按相关字段分区。

如果你还想答得更工程化，可以补一句：

> “判断 DPP 有没有生效，不能靠猜，要去看 `EXPLAIN` / 物理计划里的 `PartitionFilters` 和 `dynamicpruningexpression(...)`。”

这句话通常会让回答明显加分。

**面试官为什么问这个：**  
面试官在看你是否理解今天 Spark SQL 优化的“少扫数据”主线。

**常见追问：**  
- DPP 默认开吗？
- 为什么有 Join 也不一定触发 DPP？
- DPP 和 Broadcast 有什么关系？

**容易答偏的点：**  
- 把 DPP 说成普通谓词下推；
- 只会说“它能少读数据”，却说不出怎么验证；
- 暗示所有 Join 都能自然触发。

### 2.7 Shuffle 为什么慢

**短答：**  
因为 Shuffle 往往同时叠加了网络传输、磁盘 IO、序列化/反序列化、排序/聚合以及跨节点数据重分布等多种成本，它通常是 Spark 作业里最重的阶段边界之一。

**展开答：**  
很多人会答“因为要走网络”，这不算错，但太浅。更完整的理解是：

- **上游要先把数据按 key 或目标分区重新组织；**
- **中间可能发生排序、聚合、Spill；**
- **下游再去远端拉取对应分区数据；**
- **整个过程对磁盘、本地盘稳定性、网络、序列化格式都敏感。**

所以 Shuffle 慢，往往不只是“网络慢”，而是系统性成本叠加。它也解释了为什么下列优化收益通常很大：

- 少做不必要 Shuffle；
- 尽量提前过滤、提前聚合；
- 让 Join 策略更合理；
- 降低数据倾斜和过度 Spill。

**面试官为什么问这个：**  
想确认你知不知道 Spark 性能瓶颈的主战场在哪里。

**常见追问：**  
- Shuffle Read / Write 过大通常意味着什么？
- 哪些 API 或 SQL 写法更容易放大 Shuffle？
- 本地 Shuffle 文件丢失时通常看什么日志？

**容易答偏的点：**  
- 只会说网络；
- 完全不提排序、Spill、序列化；
- 把所有慢任务都归因于 Shuffle。

### 2.8 数据倾斜怎么处理

**短答：**  
先确认是不是“真倾斜”，再区分是 Join 倾斜还是聚合倾斜；处理优先级通常是 **AQE / Broadcast / 分区修正 → SQL 改写 → 加盐或分流兜底**，而不是一上来就手工加盐。

**展开答：**  
这题最容易暴露候选人的真实经验。成熟回答一般包括三步：

**第一步：确认是不是倾斜。**  
慢 task 不等于倾斜，可能是机器异常、Spill 太重、写出慢、下游存储瓶颈。要先看 Spark UI：

- 最大 task 时间和中位数差多少；
- 最大输入量和中位数差多少；
- 是否只有极少数 task 拖慢尾部。

**第二步：给问题分型。**  
- Join 倾斜：热点 key 在 Join 两边聚集；
- 聚合倾斜：热点 key 在 group by 时集中；
- 写出热点：最终分区或业务 key 导致输出极不均匀。

**第三步：按侵入性从低到高治理。**  
- 先看 AQE skew join、Broadcast Join、分区策略是否已经足够；
- 再看两阶段聚合、热点 key 单独处理、上游预聚合；
- 最后才是加盐打散、分流、拆表等高侵入方案。

一句真正像实战的总结是：**倾斜治理首先是诊断题，其次才是技巧题。**

**面试官为什么问这个：**  
因为这是 Spark 实战里最常见、也最能看出有没有真做过优化的题。

**常见追问：**  
- AQE skew join 适合哪些场景，不适合哪些场景？
- 热点 key 已知和未知时，策略有什么不同？
- 为什么不要先上加盐？

**容易答偏的点：**  
- 看到“倾斜”两个字就背加盐；
- 不区分 Join 倾斜和聚合倾斜；
- 完全不提验证证据。

### 2.9 OOM 怎么分型

**短答：**  
Spark OOM 先分三大类：**Driver OOM、Executor OOM、容器超限被 kill**。这三类根因和处理路径完全不同，不能笼统说“加内存”。

**展开答：**  
这是非常典型的“看排障思路”的题。一个成熟回答应该先分层：

- **Driver OOM**：常见于 `collect`、`toPandas`、结果集过大、广播构建、计划或元数据太重等场景；
- **Executor OOM**：更常见于单 task 数据过重、聚合/排序/Join 压力过大、缓存过多、数据倾斜等；
- **容器被 kill**：常见于 YARN / Kubernetes 等资源管理层面超限，不一定是 JVM 主动抛 OOM，也可能是容器外部被杀。

所以排查顺序通常是：

1. 先看失败日志到底来自 Driver、Executor 还是容器层；
2. 再看发生在读、Join、聚合、写出哪个阶段；
3. 再决定是先改逻辑、改分区、减数据量，还是最后再调资源参数。

如果你直接说“把 `executor.memory` 调大”，通常只能拿到比较浅的印象分。

**面试官为什么问这个：**  
因为它最能看出你遇到问题时是“按层定位”还是“靠经验拍参数”。

**常见追问：**  
- `collect` 为什么容易把问题带到 Driver？
- YARN kill 和 JVM OOM 有什么区别？
- Spill 很多时一定会 OOM 吗？

**容易答偏的点：**  
- 不分 Driver / Executor / 容器层；
- 把所有内存问题都归为 JVM 堆不够；
- 不提数据倾斜、分区不均、逻辑膨胀这些更常见的根因。

### 2.10 Spark Connect 是什么

**短答：**  
Spark Connect 是 Spark 3.4 引入的 **client-server 解耦架构**。客户端不再必须和传统 Spark 驱动方式强耦合，而是通过 DataFrame API 和未解析逻辑计划（unresolved logical plans）与远端 Spark 服务端通信，更适合 IDE、Notebook、平台化和多语言客户端场景。

**展开答：**  
这题很容易被答成“Spark 多了个远程接口”，但更准确的理解是：**Spark 的使用方式在变化。**

传统模式下，很多客户端能力和 Spark runtime 耦合较紧；Spark Connect 的意义在于：

- **把客户端和服务端解耦，** 更容易远程连接集群；
- **让 Spark 更像平台能力，** 而不是每个客户端都把完整运行环境背在本地；
- **更适合嵌入 IDE、Notebook、数据平台、交互式应用。**

它体现的不是一个孤立新功能，而是 Spark 正在往更服务化、平台化的使用模型演进。

当然，这也不等于说传统提交模式立刻失效。对很多批处理任务、已有平台和成熟提交链路来说，传统模式仍然重要。面试里答到这里，通常会显得比较稳。

**面试官为什么问这个：**  
想看你是否知道现代 Spark 的使用模型已经和早期不完全一样。

**常见追问：**  
- Spark Connect 解决了什么旧问题？
- 它和“只是多了个协议”有什么区别？
- 它适合哪些场景，不适合哪些场景？

**容易答偏的点：**  
- 只说“远程连接”；
- 没有提 client-server 解耦；
- 把它说成所有 Spark 作业未来唯一模式。

## 三、中频题快答

### 3.1 宽依赖和窄依赖怎么理解

**短答：**  
窄依赖通常意味着上游分区和下游分区关系更局部、更容易流水线执行；宽依赖通常意味着数据要跨分区重分布，因此常常对应 Shuffle 和 stage 边界。

### 3.2 广播变量与累加器有什么区别

**短答：**  
广播变量解决“共享只读输入”，累加器解决“汇总执行侧指标或计数”。前者关注数据分发，后者关注结果归并。

### 3.3 DAGScheduler 和 TaskScheduler 分别做什么

**短答：**  
DAGScheduler 更偏“切图”和 stage 组织，TaskScheduler 更偏“派工”和资源层面的 task 调度。

### 3.4 YARN 和 Kubernetes 的差别只在部署方式吗

**短答：**  
不是。它们还影响日志入口、资源治理方式、本地盘生命周期、节点回收语义、故障取证路径，所以排障思路也会不同。

### 3.5 如果让你设计 Spark 调优顺序，你会怎么答

**短答：**  
先减数据量，再修 SQL 与分布，再看资源与内存，最后才调细参数；全程以 Spark UI、执行计划和日志证据为依据。

## 四、面试收尾建议

如果你准备的是中高级岗位，Spark 面试不要只背“名词解释”，而要重点练下面三种能力：

1. **把基础题答出结构感**：例如“为什么 Spark 快”“RDD 怎么容错”；
2. **把现代主题答出边界感**：例如 AQE、DPP、Spark Connect；
3. **把实战题答出诊断感**：例如数据倾斜、OOM、Shuffle 慢。

真正能拉开差距的不是你背了多少参数，而是你能不能让面试官相信：**你知道问题该怎么想、证据该怎么看、方案该按什么顺序落。**
