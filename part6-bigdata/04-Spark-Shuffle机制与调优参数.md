## 一、先明确：Shuffle 文档不该只是参数表

很多人学习 Shuffle，最后只记住了一串参数：

- `spark.sql.shuffle.partitions`
- `spark.default.parallelism`
- AQE 的一些 coalesce 配置
- 若干 fetch / buffer / retry 相关参数

但这类记忆方式很容易失效。因为 Shuffle 真正难的地方，不在于“参数太多”，而在于你要先判断：

1. **问题究竟发生在 Shuffle Write 还是 Shuffle Read；**
2. **主矛盾是分区不合理、倾斜、Spill、网络拉取，还是输出分布；**
3. **今天这个场景可以相信 AQE 自动纠偏到什么程度；**
4. **什么时候必须显式控制分区与写出分布。**

所以这篇文档的目标不是给你一张参数大全，而是帮你建立：

> **面对 Shuffle 问题时，如何先做工程判断，再决定该调什么。**

## 二、为什么 Shuffle 往往是 Spark 里最贵的一段

### 2.1 它不是一个点成本，而是一串成本叠加

Shuffle 贵，不是因为某个 API 名字不好，而是因为它经常同时引入：

- 重新分区；
- 排序或聚合；
- 磁盘写中间结果；
- 远程节点网络拉取；
- 反序列化与再次合并；
- 内存不足时的 Spill。

所以当你说“这个 stage 是 Shuffle 瓶颈”时，实际上是在说：**一串跨节点、跨磁盘、跨内存边界的成本叠在了一起。**

### 2.2 Shuffle Write 和 Shuffle Read 是两种不同问题

同样叫 Shuffle 慢，根因可能完全不同。

**Shuffle Write 偏重时，常见信号是：**

- 上游排序 / 聚合很重；
- map 端 Spill 多；
- 磁盘写中间结果压力大；
- task 本身在写阶段就已经很慢。

**Shuffle Read 偏重时，常见信号是：**

- reduce 端远程拉取很慢；
- FetchFailed、超时、文件缺失反复出现；
- 网络与本地盘稳定性成为主矛盾；
- 少数 reduce task 因拉取超大分区而拖尾明显。

这就是为什么“Shuffle 慢”不能只靠一个参数统一解决。

### 2.3 为什么一个普通 `group by` 也可能很贵

很多看起来只是“做个聚合”的 SQL，背后实际可能包含：

- 先重分区；
- 再排序或局部聚合；
- 写出中间文件；
- 下游再拉取并合并；
- 最后若分区不均，还会出现明显尾拖。

所以 `group by` 慢，往往不是“聚合函数慢”，而是 Shuffle 链路整体贵。

## 三、先看底层心智：Shuffle 到底在做什么

### 3.1 它本质上是在重建数据分布

Spark 里的很多宽依赖操作，本质都在做同一件事：

> **把原先按上游分区组织的数据，重新分发成下游算子需要的数据分布。**

这件事一旦发生，就意味着：

- 上游和下游的分区边界不再一致；
- 跨节点数据传输几乎不可避免；
- 分区设计优劣会直接影响 task 粒度与尾拖；
- 本地盘、中间文件和网络稳定性开始进入主战场。

### 3.2 SortShuffleManager 为什么是工程上更稳的默认方案

Shuffle 机制的演进，本质是 Spark 在做工程折中：

- 如何减少中间文件数量；
- 如何兼顾性能和稳定性；
- 如何让通用场景下的成本更可控；
- 如何避免极端方案在大规模场景下失稳。

SortShuffleManager 之所以成为默认主线，不是因为它在所有场景都“理论最快”，而是因为它在文件组织、通用稳定性和工程复杂度之间做了更现实的平衡。

### 3.3 文件组织方式为什么会影响后续一切

很多人把 Shuffle 看成“中间过程”，但实际生产里，很多问题都直接和中间结果组织方式有关：

- 本地盘压力；
- 中间文件数量；
- FetchFailed；
- 节点丢失后的恢复代价；
- K8s 环境下本地盘生命周期问题。

所以 Shuffle 不是抽象概念，它和运行环境高度耦合。

## 四、分区数怎么理解：初始值、运行时值、最终写出值不是一回事

### 4.1 `spark.sql.shuffle.partitions`：它首先是“初始计划输入”，不是最终真理

这是 Spark SQL / DataFrame 路径里最常见的 Shuffle 分区配置。它会直接影响：

- 初始并行度；
- 单 task 压力；
- 调度开销；
- 中间分区粒度。

但在今天的 Spark 语境里，它不该再被理解为“最后一定就是这么多分区”。更准确的说法是：

> **它通常是 AQE 进一步调整之前的起点。**

### 4.2 `spark.default.parallelism`：不要把它和 SQL 分区数当成同一件事

这个参数更偏 RDD 路径和默认并行度推断语境。它和 `spark.sql.shuffle.partitions` 不是“同义词两种写法”，而是：

- API 层次不同；
- 生效路径不同；
- 影响方式也不同。

如果把两者混成一个东西，后面很多调优判断都会跑偏。

### 4.3 三个很容易混淆的概念

实际工程里，至少要分清下面三件事：

1. **初始 Shuffle 分区数**：计划一开始准备怎么切；
2. **AQE 介入后的运行时分区数**：执行中是否被自动合并或重组；
3. **最终写出文件分布**：最后输出给下游的文件数量和大小是否合理。

这三件事经常相关，但绝不是同一个指标。

### 4.4 为什么“分区数正确”不等于“输出结果合理”

哪怕 AQE 已经把运行时 task 数调得比较顺了，你仍然可能遇到：

- 最终文件太碎；
- 输出分布不均；
- 某些业务 key 过热；
- 下游读取体验很差。

因为运行时分区优化和最终业务写出目标，不是同一个优化目标。

## 五、AQE 与 Shuffle：今天最容易被讲对，也最容易被讲歪的部分

### 5.1 AQE auto-coalesce 解决了什么

AQE 的 post-shuffle coalesce 很有价值，因为它解决的是非常常见的一类问题：

- 你前面为了安全或通用性，把初始分区数设得比较大；
- 运行时发现数据量并没有那么大；
- 如果不合并，后面会出现很多过碎 task。

这时 AQE 可以在拿到真实统计信息后，把过小的 post-shuffle 分区做自动合并。

所以在很多“默认 200 个分区太碎”“过滤后数据变小很多”的场景下，它确实很好用。

### 5.2 AQE auto-coalesce 不是“自动重分区万能器”

这点必须讲得非常明确。AQE auto-coalesce 是启发式运行时优化，不是业务目标感知型系统。它不能替你自动完成下面这些事情：

- 根据业务写出目标精确控制文件数；
- 保证输出 key 分布均匀；
- 修复前面 SQL 写法、扫描裁剪、Join 选择的问题；
- 让所有 busy cluster 都达到最优资源效率。

所以更准确的理解应该是：

> **AQE auto-coalesce 擅长纠正“分区过碎”，但不负责替你完成“输出设计”。**

### 5.3 `advisoryPartitionSizeInBytes`：是建议目标，不是硬承诺

这也是最容易被误读的地方。`spark.sql.adaptive.advisoryPartitionSizeInBytes` 名字里就写着 advisory，它更像目标参考值，而不是“Spark 必须把分区精确做成这个大小”。

它的意义是：

- 给 AQE 一个倾向性的目标；
- 让自动合并和倾斜拆分有一个大小尺度；
- 作为运行时优化的参考，而不是最终业务 SLA。

所以如果你拿它当“最终文件大小承诺”，往往会失望。

### 5.4 `parallelismFirst` 为什么会让自动结果看起来“不听话”

Spark 官方文档明确说明：默认 `spark.sql.adaptive.coalescePartitions.parallelismFirst=true` 时，Spark 会优先考虑并行度，**不严格遵守** advisory target size。

这背后的思路是：

- 避免 AQE 开启后并行度掉得太狠；
- 降低自动合并带来的性能回退风险；
- 让通用场景下更保守。

但副作用也很现实：

- 会保留更多偏小 task；
- 资源利用不一定最省；
- 在 busy cluster 上不一定是最优；
- 结果可能和“我明明设了 advisory size”直觉不一致。

所以当你发现 AQE 自动合并“好像没合到你想要的程度”时，第一反应不该是怀疑 Spark 坏了，而是要想到：**它可能是刻意优先保并行度。**

### 5.5 什么场景可以放心把 AQE 当主力

以下场景通常可以比较放心地依赖 AQE auto-coalesce 作为主力方案：

- 通用 SQL 分析任务；
- 初始分区偏保守、偏大；
- 运行时数据量波动较大；
- 目标是减少碎 task，而不是精确控制最终文件布局；
- 你更在意“足够好且维护成本低”，而不是“每次都手工精确控形”。

### 5.6 什么场景不该把 AQE 当唯一答案

以下场景通常不该只靠 AQE：

- 你需要明确控制最终写出文件数与文件大小；
- 你需要按业务 key 或范围重新均衡输出；
- 集群繁忙、资源效率比极限并行度更重要；
- 你已经知道某个阶段必须显式重分布；
- 问题根因其实是倾斜、写法、裁剪失效，而不是分区过碎。

这类场景里，显式 `repartition`、`repartitionByRange`、`REBALANCE` 等手段通常更值得进入视野。

## 六、对比理解：AQE auto-coalesce、手工 repartition、REBALANCE 分别在解决什么

### 6.1 AQE auto-coalesce vs 手工 repartition

它们最大的区别，不在“一个自动一个手工”，而在控制目标不同。

**AQE auto-coalesce 更像：**

- 运行时自动纠偏；
- 重点缓解过碎分区；
- 低维护成本；
- 结果带启发式，不强调强控制。

**手工 repartition 更像：**

- 显式要求重新分布；
- 你知道自己想把数据重新切成什么形态；
- 控制力更强；
- 代价和侵入性也更高。

一句话概括：

> **AQE 更适合“自动收口”，repartition 更适合“明确重塑”。**

### 6.2 AQE auto-coalesce vs `REBALANCE`

这也是现代 Spark 很值得单独讲清的一个对比。

**AQE auto-coalesce** 的核心目标是：

- 少一点碎 task；
- 让 post-shuffle 分区别过小；
- 降低执行期的小分区开销。

**`REBALANCE`** 更偏向：

- 写出前重新整理分布；
- 避免个别分区过大或过小；
- 让输出布局更均衡。

所以它们并不是竞争同一职责：

- AQE auto-coalesce 更偏“执行中纠偏”；
- `REBALANCE` 更偏“写出前整形”。

也因此，如果你的问题是“最终输出给下游的文件布局不理想”，那就不该只盯 AQE auto-coalesce。

### 6.3 `shuffle.partitions` 初始值 vs 最终运行分区数

今天理解这件事的正确方式应该是：

- 初始值很重要，因为它决定起点；
- 但它不必总是最终答案；
- AQE 会尝试修正它；
- 最终能否得到理想结果，还取决于你的目标是不是“执行足够顺”，还是“输出足够漂亮”。

如果你只记“200 太多 / 50 更合理”，这类经验在现代 Spark 里很容易失效。

## 七、Shuffle 调优顺序：先判断瓶颈归属，再决定动哪里

### 7.1 第一步：先判断主矛盾在写端、读端还是分布

推荐先问三个问题：

1. 慢主要发生在 Shuffle Write 还是 Shuffle Read？
2. 是所有 task 都偏重，还是少数 task 拖尾？
3. 问题更像分区过碎、分区过粗、倾斜，还是网络 / 本地盘 / 中间文件稳定性问题？

没有这一步，后面的参数动作很容易瞎。

### 7.2 第二步：先看分区是否离谱

调 Shuffle，最先该看的通常不是细参数，而是分区粒度是否明显失真：

- 太碎：task 很多但都很小；
- 太粗：单 task 太重、Spill 高、尾部慢；
- 太不均：少数 task 极重、疑似倾斜。

很多所谓“Shuffle 参数问题”，其实首先是分区设计问题。

### 7.3 第三步：再看 AQE 是否已经足够

如果你处在 Spark SQL 路径里，下一步通常应该看：

- AQE 是否开启；
- AQE 是否真的介入；
- auto-coalesce 是否已经帮你解决碎分区；
- 现有场景是否适合继续相信它。

只有在 AQE 的能力和边界都想清楚之后，再决定要不要手工重分布。

### 7.4 第四步：最后才看细节参数

fetch retry、buffer、batch size、其他细粒度参数，不是没用，而是它们更适合在下面这种场景出场：

- 主问题已经确定在拉取链路或特定子系统；
- 分区、倾斜、AQE 边界都已经看清；
- 你是在优化已知瓶颈，而不是盲调。

这一步放最后，是为了防止“主矛盾没动，边角参数调了一堆”。

## 八、常见 Shuffle 症状应该怎么分流

### 8.1 过多小 task

常见原因包括：

- 初始分区数过大；
- 过滤后数据量大幅缩小；
- AQE 没触发或受限；
- 输出前又做了额外重分布。

优先顺序通常是：

1. 先看 AQE auto-coalesce 是否该发挥作用；
2. 再看初始分区是否明显拍得太大；
3. 如果你关心最终输出布局，再考虑 `REBALANCE` / `repartition`。

### 8.2 分区过少导致单 task 过重

如果分区过少，常见表现是：

- 单 task 输入量大；
- 排序 / 聚合压力高；
- Spill 明显增加；
- 尾部拖得很长。

这类问题通常不该靠“把内存再加一点”糊过去，而应先回到分区粒度本身。

### 8.3 少数 task 极慢：先怀疑倾斜，不要先怀疑参数

如果只是极少数 task 特别慢，尤其伴随超高 Shuffle Read / Write，那么优先要想的是：

- 有没有热点 key；
- 是 Join 倾斜还是聚合倾斜；
- AQE skew join 是否能缓解；
- 是否需要热点拆分。

这类问题如果直接调 `shuffle.partitions`，常常只能缓解表面。

### 8.4 FetchFailed、超时、文件缺失

这类问题说明你已经从“分区数像不像”进入了“Shuffle 链路稳定性”语境。此时要一起看：

- Executor / 节点是否稳定；
- 本地盘是否可靠；
- 中间文件生命周期是否被破坏；
- 网络拉取链路是否异常；
- 在不同运行环境下，Shuffle 服务保留机制是否一致。

这类问题和部署环境、日志路径、本地存储策略强相关，不能只当作一个 SQL 参数问题。

## 九、哪些参数值得知道，哪些参数不要先碰

### 9.1 最值得先建立正确理解的参数

优先级更高的是这些“决定形态”的参数与能力：

- `spark.sql.shuffle.partitions`
- `spark.default.parallelism`
- AQE 相关开关
- `spark.sql.adaptive.advisoryPartitionSizeInBytes`
- `spark.sql.adaptive.coalescePartitions.parallelismFirst`

因为它们决定的是你怎样理解“初始粒度、运行时纠偏和并行度优先级”。

### 9.2 Read 侧进阶参数什么时候才值得看

fetch、retry、buffer 等参数通常更适合以下场景：

- 集群规模较大；
- 网络复杂；
- 拉取稳定性问题明确；
- 已经能证明确实是 Shuffle Read 链路问题。

### 9.3 为什么不建议把这篇文章学成“参数背诵题”

因为 Shuffle 真正拉开差距的，不是你会不会背 20 个参数，而是你是否知道：

- 什么时候问题首先是分区；
- 什么时候问题首先是 AQE 边界；
- 什么时候问题已经进入存储 / 网络 / 运行环境语境；
- 什么时候该显式重分布，什么时候让自动机制收口就够了。

## 十、最后总结：Shuffle 文档真正要教会你的是什么

读完这篇文章，最重要的不是记住某个默认值，而是建立下面这套判断：

1. **Shuffle 问题先分型：** 写端、读端、分布、稳定性；
2. **分区数先理解为起点，而不是最终真理；**
3. **AQE auto-coalesce 很重要，但它不是输出布局设计器；**
4. **手工 repartition / `REBALANCE` 不是 AQE 的替代品，而是显式控制工具；**
5. **细节参数永远排在工程判断之后。**

如果你建立了这套心智，那么面对一个 Shuffle 很慢的任务时，你就不会只会问：

> “这个参数应该改成多少？”

而会先问：

> “这个任务到底在 Shuffle 的哪一层出了问题，我该信自动机制，还是该显式控制它？”
