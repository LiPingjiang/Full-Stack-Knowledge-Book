## 一、为什么 Shuffle 是 Spark 最贵的操作

### 1.1 磁盘 IO、网络传输、序列化三重开销

Shuffle 慢，不是因为某个 API 名字不好，而是因为它经常同时涉及：

- 写磁盘
- 拉网络
- 做序列化 / 反序列化

### 1.2 Shuffle Write 与 Shuffle Read

可以把 Shuffle 分成两个阶段理解：

- **Shuffle Write**：Map 端把数据按规则写成后续可读的中间结果
- **Shuffle Read**：Reduce 端再去拉这些中间结果

优化时要分清是写端太重，还是读端太慢。

### 1.3 为什么“只是一个 group by”也可能很慢

因为 group by 往往意味着：

- 重分区
- 聚合
- 排序 / 合并
- 网络传输

所以很多看起来“只是一个聚合”的 SQL，背后其实是完整的 Shuffle 链路。

## 二、Shuffle 底层机制

### 2.1 ShuffleManager 演进

ShuffleManager 的演进可以看成 Spark 在做一个工程折中：如何在性能、文件数量、稳定性、实现复杂度之间找到平衡。

### 2.2 SortShuffleManager 为什么成为默认方案

SortShuffleManager 的工程价值在于：即使它不是所有场景下最极致的快，它通常能更稳地控制中间文件数量，并在大多数场景下给出更可接受的综合成本。

### 2.3 文件数量与中间结果组织方式

理解 Shuffle 的文件组织方式很重要，因为很多后续问题——小文件、FetchFailed、节点本地盘压力——都和中间结果如何被组织、如何被读取直接相关。

## 三、Shuffle 分区数怎么理解

### 3.1 spark.sql.shuffle.partitions

这是 Spark SQL / DataFrame 里最常见的 Shuffle 分区控制参数。它不是“越大越好”，也不是“越小越省资源”，而是直接影响：

- 并行度
- 单 task 压力
- 调度开销
- 输出文件数

### 3.2 spark.default.parallelism

这个参数更多和 RDD 场景、默认并行度推断相关。它和 `spark.sql.shuffle.partitions` 不是替代关系，而是作用层次不同。

### 3.3 两者的边界与常见误解

最常见误解是：把两个参数当成“一个东西的两个写法”。实际上它们在不同 API 层、不同执行路径上的影响并不完全一样。

### 3.4 AQE 介入后这两个参数如何重新理解

进入 AQE 时代后，一个更好的理解方式是：

- 初始分区数仍然重要
- 但它更像是 AQE 的起点，而不是最终答案
- 最终效果还要看 AQE 是否真的被触发，以及是否允许它合并 / 重写

## 四、AQE 与 Shuffle

### 4.1 Shuffle 后自动合并分区

AQE 会在 Shuffle 后根据真实数据统计信息，尝试把过小分区合并，减少过多小 task。这个能力非常实用，能覆盖很多“默认 200 个分区太碎”的场景。

### 4.2 AQE 自动合并不是万能

这点要讲得非常明确：**AQE 自动合并是启发式优化，不是全局最优。**

它的限制包括：

- 它不理解你的业务写出目标
- 它不能保证文件数、分布均匀性、资源效率同时最优
- 它只能在合适物化点后介入
- 它解决不了前面 SQL 写法和扫描层的问题

### 4.3 advisoryPartitionSizeInBytes 与实际结果的关系

`advisoryPartitionSizeInBytes` 更像是“建议目标”，而不是“Spark 一定照这个值输出最终分区”。实际结果还会受到运行时统计、默认并行度策略和具体执行路径影响。

### 4.4 parallelismFirst 的意义与副作用

`parallelismFirst` 的思路是：默认更偏向避免并行度掉得太狠，从而减少 AQE 打开后带来的性能回退风险。副作用是：

- 它不一定最省资源
- 它可能保留更多小 task
- 它不一定最符合 busy cluster 的资源效率目标

### 4.5 Busy cluster / 资源敏感场景如何约束 AQE

在繁忙集群中，你可能仍然需要：

- 手工约束初始分区数
- 显式选择 `REBALANCE` / `repartitionByRange`
- 把 AQE 看成兜底，而不是唯一控制器

## 五、Shuffle 调优参数

### 5.1 基础参数

基础参数的核心不是背名字，而是先问清：

- 我是在控制并行度，还是在控制单 task 压力？
- 我是在让 Shuffle 更细，还是更粗？
- 我是在优化吞吐，还是在保稳定？

### 5.2 Shuffle Read 进阶参数

这类参数通常在以下场景更值得看：

- 大规模集群
- 网络较复杂
- 任务存在明显拉取不稳定
- FetchFailed 反复出现

### 5.3 spill.batchSize 等细节参数

细节参数只有在你已经确认根因接近这里时才值得动。否则很容易变成“在边角上微调，却没动主矛盾”。

### 5.4 参数不是越多越好

参数越多，交互越复杂，回归越难解释。真正稳定的做法还是：先解决结构性问题，再动少量关键参数。

## 六、常见 Shuffle 问题

### 过多小 task

典型原因包括：

- 初始分区数设得过大
- AQE 没触发或没按预期工作
- 输出前又做了一次不必要的重分布

### 分区过少导致单 task 过重

反过来，如果分区太少，就会出现：

- 单 task 读太多数据
- 排序 / 聚合压力太大
- Spill 激增
- stage 尾部特别慢

### 拉取失败、超时、文件缺失

这类问题通常不是“单个参数没调好”这么简单，而是要一起看：

- Executor 稳定性
- 本地盘与中间文件生命周期
- 网络与容器环境
- External Shuffle Service / Shuffle Tracking 路径

### Shuffle 与小文件问题的关系

小文件问题的根子很多时候就在最后几个 Shuffle 阶段：分区太碎、分布不均、写出前没做合适控制。也因此，小文件治理本质上不是“文件系统问题”，而是执行计划与分区策略问题。
