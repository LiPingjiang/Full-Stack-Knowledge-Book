# 6.4 Spark 性能优化

## 一、先明确：这篇文档的角色是“调优决策树”

Spark 性能优化最常见的误区，是把它学成：

- 参数大全；
- 零散技巧清单；
- “哪个慢就加资源”的经验主义。

这篇文档的目标不是把所有技巧都堆在一起，而是给你一条更稳定的判断顺序：

> **遇到慢任务时，先判断主矛盾在哪一层，再决定去哪个专题深挖，而不是一上来就改参数。**

所以这篇文档最重要的不是某个数字，而是调优顺序。

## 二、总决策树：Spark 任务慢，先按这条顺序判断

推荐顺序是：

1. **先看是不是扫太多；**
2. **再看是不是算得不合理；**
3. **再看是不是分布失控；**
4. **再看是不是资源承载不住；**
5. **最后才看细节参数。**

这个顺序几乎决定了你会不会走弯路。

### 2.1 为什么先减数据量，再谈算力

如果任务本身：

- 扫了太多分区；
- 读了太多列；
- 中间数据被膨胀得过大；
- 本来只该读 5%，却读了 100%。

那么后面的资源调优，大概率只是让错误路径跑得更快一点，而不是把路径修对。

### 2.2 为什么先修 SQL 与分布，再调资源

大多数 Spark SQL 任务真正的主矛盾往往是：

- 扫描量过大；
- Join 策略不合理；
- 数据倾斜；
- Shuffle 分区设计失衡；
- 输出文件与写出分布失控。

这些问题如果不先动，单纯加内存、加 executor、调并行度，常常只是把成本抬高。

### 2.3 为什么先看证据，再动参数

调优前至少先看：

- Spark UI 的 SQL / Stage / Executor 页面；
- 关键 stage 的 input size / shuffle read / shuffle write；
- task 最大值和中位数的差异；
- spill、GC、失败重试等信号。

没有证据就动参数，往往只是在制造更多变量。

## 三、第一层：当你怀疑“扫描量太大”时，先看这里

### 3.1 哪些信号说明主矛盾在“读太多”

以下信号通常说明你该优先看扫描层：

- input size 明显超出业务预期；
- CPU 并没打满，但任务就是慢；
- 时间主要耗在 scan 前段或 scan + early shuffle；
- 明明业务只关心少量数据，却像全表扫描。

### 3.2 这一层最值得优先检查什么

先看三件事：

- 分区裁剪是否生效；
- 列裁剪是否生效；
- 谓词是否尽量推到数据源。

如果这三件事有一项明显失效，往往就已经找到主矛盾了。

### 3.3 DPP 在这一层的意义是什么

动态分区裁剪（DPP）之所以重要，是因为它把“少扫数据”这件事推进到了更现代的阶段：

- 不只是静态写死分区条件；
- 还能把维表过滤动态传回事实表扫描阶段。

但它不是所有 Join 都会自动触发，所以不能只凭“我写了 Join”就假定它已经生效。你要看执行计划里的 `PartitionFilters` 和 `dynamicpruningexpression(...)`。

如果你在这一层遇到瓶颈，应该跳去：

- [Spark SQL 与算子优化详解](./04-Spark-SQL与算子优化详解.md) —— 当你想判断 DPP、Explain、分区裁剪失效时看这篇。

## 四、第二层：当你怀疑“算得不合理”时，先看这里

### 4.1 哪些信号说明主矛盾在 SQL / 算子路径

以下情况更像“计算逻辑本身过重”：

- Join 明显选错策略；
- 窗口函数过重；
- CTE / 子查询让计划重复计算；
- 聚合、排序、去重阶段代价异常大；
- Explain 看起来就不像一条健康路径。

### 4.2 JOIN 优化为什么不该只是背物理 Join 名字

真正的 Join 优化顺序通常是：

1. 统计信息是否靠谱；
2. Spark 自动机制能否已经选到合理策略；
3. 是否该提前过滤、减少输入规模；
4. 最后才考虑 Hint 兜底。

如果你一上来就强行 Hint，很多时候只是在掩盖统计信息、SQL 写法或输入结构的问题。

### 4.3 窗口、CTE、重复计算为什么经常被低估

这类问题之所以难，是因为它们表面上很“合理”，但代价可能非常高：

- 窗口会引入排序和重分布；
- CTE 不一定真的复用；
- 子查询可能让过滤和计划理解都变差；
- 一些看似优雅的 SQL 写法，会把中间数据膨胀放大。

### 4.4 这一层什么时候必须看 EXPLAIN

以下情况建议直接看 `EXPLAIN`，不要靠猜：

- Join 策略不符合预期；
- Hint 是否生效拿不准；
- DPP 有没有触发；
- 分区裁剪是否真的落进物理计划；
- 写出前是不是还发生了额外重分布。

如果你在这一层遇到瓶颈，应该跳去：

- [Spark SQL 与算子优化详解](./04-Spark-SQL与算子优化详解.md) —— 当你需要系统判断 Join、窗口、CTE、EXPLAIN 路径时看这篇。

## 五、第三层：当你怀疑“分布失控”时，先看这里

### 5.1 哪些信号说明问题在分布，而不是在算力

以下信号说明问题更像分布问题：

- 少数 task 极慢；
- 最大 task 和中位数差距极大；
- 某个 stage 尾拖严重；
- shuffle read / write 很大；
- 最终写出文件碎且不均匀。

### 5.2 先区分三类分布问题

你至少要分清：

1. **分区太碎**：task 太多但都很小；
2. **分区太粗**：单 task 太重、Spill 高；
3. **数据倾斜**：少数 task 异常重、热点 key 拖尾。

这三类问题不能用同一种办法修。

### 5.3 AQE 在这一层能帮什么，不能帮什么

AQE 在分布问题上非常重要，但边界也必须讲清：

它能帮你：

- 自动合并过碎的 post-shuffle 分区；
- 运行时切换部分 Join 策略；
- 处理一部分倾斜 Join。

它不能替你：

- 设计业务输出布局；
- 保证文件数、分布均匀性和资源效率三者同时最优；
- 修掉扫描层和 SQL 写法的根因；
- 理解你的业务写出目标。

### 5.4 小文件治理为什么要按“先 AQE，再 REBALANCE，再手工控制”理解

现代 Spark 语境下，小文件治理不该再只剩一句 `coalesce(1)`。更合理的顺序通常是：

1. **先看 AQE 是否已经足够缓解过碎分区；**
2. **如果目标是写出前重新整形，就看 `REBALANCE` 是否更合适；**
3. **如果业务目标非常明确，再用手工 repartition / repartitionByRange 显式控制。**

也就是说：

- AQE 更像自动收口；
- `REBALANCE` 更像写出前整形；
- 手工控制更像明确重塑。

### 5.5 倾斜为什么不要一上来就加盐

加盐是兜底，不是第一反应。更合理的顺序通常是：

1. 先确认是不是真倾斜；
2. 先看 AQE skew join、Broadcast、分区策略是否已足够；
3. 再看两阶段聚合、热点 key 单独处理；
4. 最后才是加盐、分流、拆表。

如果你在这一层遇到瓶颈，应该跳去：

- [Spark Shuffle 机制与调优参数](./04-Spark-Shuffle机制与调优参数.md) —— 当你卡在 AQE、分区粒度、REBALANCE、Shuffle 工程判断时看这篇。
- [Spark 数据倾斜治理](./04-Spark-数据倾斜治理.md) —— 当你怀疑热点 key、慢 task、Join / 聚合倾斜时看这篇。

## 六、第四层：当你怀疑“资源承载不住”时，先看这里

### 6.1 哪些信号说明该看资源层

以下情况更像资源层问题：

- OOM 稳定发生；
- spill 很重且持续；
- container / pod 被 kill；
- executor 丢失伴随明显资源压力；
- 并发不足、整体吞吐明显受 executor 数量和 cores 限制。

### 6.2 为什么资源问题不能只看一个参数

资源问题至少要联动看：

- 分区数；
- executor 个数；
- executor.cores；
- executor.memory；
- memoryOverhead；
- 单 task 实际压力。

所以“task 慢”不一定是 CPU 不够，“OOM”也不一定只是 memory 太小。

### 6.3 Dynamic Allocation 解决的是什么，不解决什么

Dynamic Allocation 解决的是资源弹性，不是执行计划。它更像：

- 让工人数量跟任务积压动态变化；
- 提高资源利用率；
- 让高峰和低峰更弹性。

它不负责修：

- 错误的 Join 路径；
- 分区裁剪失效；
- 倾斜；
- SQL 逻辑膨胀。

### 6.4 为什么调资源常常不如先改分区和逻辑

这是非常关键的一点。很多资源问题表面上像：

- executor 内存不够；
- executor 太少；
- cores 没配对。

但根因可能是：

- 分区太少导致单 task 太重；
- 倾斜让少数 task 爆炸；
- collect / toPandas / 广播把问题带回 Driver；
- SQL 写法让中间数据无意义膨胀。

这也是为什么成熟的调优顺序里，资源层永远排在分布和逻辑之后。

如果你在这一层遇到瓶颈，应该跳去：

- [Spark 资源内存与 Spill 调优](./04-Spark-资源内存与Spill调优.md) —— 当你需要分 Driver / Executor / 容器，看 Spill 到底代表什么时看这篇。

## 七、Spark UI：为什么它是调优入口，而不是补充页面

### 7.1 UI 最重要的用途，不是“看一眼总耗时”

Spark UI 的真正价值是帮助你先判断主矛盾在哪一层：

- Jobs：总体路径是不是太碎；
- Stages：哪个 Shuffle 边界最贵；
- SQL：哪个计划节点最重；
- Executors：是否有资源层异常、executor 丢失或节点问题。

### 7.2 UI 里最值得优先看的证据

优先看：

- input size；
- shuffle read / write；
- task 最大值和中位数差异；
- spill；
- 失败重试；
- 尾拖是否集中在少量 task。

这些指标最能帮助你决定下一步该往哪篇专题文跳。

### 7.3 UI 怎么和其他专题联动

你可以把它理解为跳转入口：

- 扫描量异常 → SQL 专题；
- 分区与 AQE 边界 → Shuffle 专题；
- 少数 task 拖尾 → 倾斜专题；
- OOM / Spill / 容器 kill → 资源专题；
- 日志与组件归属不清 → 调试运维专题。

所以 UI 在这篇文档里，不是补充阅读，而是整条调优路径的起点。

## 八、最后一层：为什么细节参数永远放最后

### 8.1 参数很多，不代表参数是主线

Spark 的参数很多，但这不意味着你应该先学成“参数工程师”。

原因很简单：

- 参数之间会互相影响；
- 很多参数只是缓解症状；
- 你一旦在主矛盾没看清时改参数，很难解释回归结果。

### 8.2 什么情况下才值得进入细节参数层

只有当下面这些事已经看清后，才值得深挖参数：

- 扫描层和 SQL 层问题已经基本定位；
- 分区与倾斜问题已经判断清楚；
- AQE 能力和边界已经想明白；
- 你知道自己是在优化哪个确定的瓶颈。

## 九、最后总结：这篇性能文真正要教会你的是什么

这篇文档最重要的，不是告诉你“哪个参数应该调成多少”，而是让你建立一条稳定的调优顺序：

1. **先看是不是扫太多；**
2. **再看是不是算得不合理；**
3. **再看是不是分布失控；**
4. **再看是不是资源承载不住；**
5. **最后才动参数。**

如果你建立了这条决策树，那么面对一个慢任务时，你就不会再只问：

> “我要不要加内存？”

而会先问：

> “这个任务真正慢在哪一层，我现在应该跳到哪篇专题去解决主矛盾？”
