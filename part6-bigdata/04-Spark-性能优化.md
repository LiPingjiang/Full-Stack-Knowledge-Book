# 6.4 Spark 性能优化

> 适用场景：想建立完整 Spark 调优方法论，而不是只背零散参数

## 一、先建立正确的调优顺序

### 1.1 先减数据量，再谈算力

Spark 调优最容易犯的错误，是一上来调 `executor.memory`、`shuffle.partitions`、`executor.instances`。如果任务本身扫了太多数据、Join 写法不合理、窗口函数过重，这些参数即使调对了，也只是让错误路径跑得稍微快一点。

### 1.2 先修 SQL 与分布，再调资源参数

大多数 Spark SQL 任务的主矛盾通常是：

- 扫描量过大
- Join 策略不合理
- 数据倾斜
- Shuffle 分区不合理
- 小文件与输出分布失控

这些问题如果不先处理，资源调大往往只是把成本抬高。

### 1.3 先看证据，再动参数

推荐先看：

- Spark UI 的 SQL / Stage 页面
- 关键 stage 的 input size / shuffle read / shuffle write
- task 的耗时分布与最大值 / 中位数差距
- spill 指标与 GC 情况

没有证据就改参数，通常只会制造更多变量。

### 1.4 先解决主矛盾，不要同时改十几个参数

Spark 不是“参数多就更可控”，而是“参数多更容易互相干扰”。每次只改一类问题：

- 先处理扫描量
- 再处理 Join / 窗口 / 倾斜
- 再处理分区与资源
- 最后才看边缘参数

## 二、减少数据量

### 2.1 分区裁剪、列裁剪、谓词下推

“少扫数据”往往是收益最高、风险最低的优化。重点看三件事：

- 分区裁剪有没有生效
- 列裁剪有没有生效
- 谓词有没有尽量下推到数据源侧

如果一个任务本来只该读 5% 的数据，却实际扫了全表，那后面的所有资源调优都会很被动。

### 2.2 静态分区裁剪 vs 动态分区裁剪（DPP）

静态分区裁剪依赖你在 SQL 中直接写出能命中分区字段的过滤条件；动态分区裁剪（DPP）则是 Spark 3.x 的重要增强：当维表先被过滤后，Spark 可以把过滤得到的 key 动态传给事实表扫描阶段，从而减少事实表分区读取。

可以把它理解成：**把“维表过滤条件”真正传到了事实表读入阶段。**

DPP 适合星型模型和典型维表过滤场景，但并不是所有 Join 都能触发它。详见：

- [Spark SQL 与算子优化详解](./04-Spark-SQL与算子优化详解.md)

### 2.3 中间数据膨胀的典型来源

中间数据膨胀常见来源包括：

- 宽表 Join 带来行数或列数急剧扩大
- 提前做明细级窗口计算
- 不必要的 explode / 多次展开
- 聚合前缺少预过滤

经验上，很多“Spark 很慢”的任务，真正问题不是算得慢，而是中间数据被放大得太夸张。

### 2.4 什么时候“少扫数据”比“加资源”更有效

如果你看到的是：

- input 很大
- 但 CPU 并没有打满
- task 时间主要耗在 scan / shuffle 前段

那优先级通常应该是“少扫数据”，而不是“加资源”。

## 三、优化计算逻辑

### 3.1 JOIN 优化的决策顺序

Join 优化不应该只是背五种物理 Join，而应该按这个顺序判断：

1. 统计信息是否靠谱
2. 能否让 Spark 自动选到更优策略
3. 过滤条件是否能前推到更早阶段
4. 是否应该显式给 Hint 兜底

如果一上来就强行 Hint，往往是在掩盖上游信息不准或 SQL 写法不合理的问题。

### 3.2 窗口函数与聚合的常见瓶颈

窗口函数常见瓶颈在于：

- 分区键不合理，导致单分区过重
- 排序列过多，排序代价大
- 多个窗口定义重复扫描 / 重复排序

如果业务上允许，把一部分窗口逻辑改写成聚合或 Join，往往能显著降低代价。

### 3.3 CTE、重复计算与缓存策略

WITH / CTE 写法能提升可读性，但不等于一定会被 Spark 物化复用。某些情况下，它只是“把同一段逻辑写了两遍的更优雅写法”。

所以遇到复杂 CTE 时，要判断：

- 它是否真的被复用
- 是否适合中间结果缓存
- 是否应该拆开成更清晰的阶段

### 3.4 什么时候该看 EXPLAIN

以下情况建议直接看 `EXPLAIN`：

- 你怀疑 Join 策略不对
- 你怀疑分区裁剪失效
- 你怀疑 DPP 没触发
- 你怀疑 Hint 没被采纳

Spark 调优里，很多争论只要看一次计划就能结束。

详见：

- [Spark SQL 与算子优化详解](./04-Spark-SQL与算子优化详解.md)

## 四、调整计算资源

### 4.1 并行度、分区数、资源配置之间的关系

并行度不是一个独立开关，它同时受以下因素影响：

- 输入分区数
- Shuffle 分区数
- Executor 数量
- 每个 Executor 能并发跑多少 task

所以“task 太慢”可能是：

- 分区太少，导致单 task 过重
- 分区太多，调度开销太高
- Executor 太少，整体并发不够
- 内存太紧，spill 太多

### 4.2 Dynamic Allocation：解决的是资源弹性，不是执行计划

Dynamic Allocation 的职责是：根据 task 积压情况动态增减 Executor。它解决的是资源使用效率问题，而不是 SQL 执行逻辑问题。也就是说，它并不能替你修复：

- 错误的 Join 策略
- 无效的分区裁剪
- 严重的数据倾斜
- 不合理的窗口计算

### 4.3 AQE：能解决什么，不能解决什么

AQE 能解决的问题主要集中在运行时已经拿到真实统计信息之后，例如：

- 自动合并过小分区
- 某些 Join 策略动态切换
- 一部分倾斜 Join 场景自动处理

但 AQE 管不了：

- 数据读取阶段的错误写法
- 分区字段被函数包裹导致的裁剪失效
- CTE 重复计算
- 内存模型与 JVM 级资源分配
- 业务写出目标下的文件分布控制

### 4.4 memory、cores、partitions 为什么要一起看

资源问题很少是单参数问题。比如：

- 分区太少时，单 task 压力太大，再加内存也可能只是缓解
- 分区太多时，CPU 不一定更忙，反而可能被调度开销吞掉
- cores 调高后，单 Executor 并发增加，但内存竞争也可能更强

更深入的资源与内存问题请看：

- [Spark Shuffle 机制与调优参数](./04-Spark-Shuffle机制与调优参数.md)

## 五、Spark UI：优化从哪里开始看

### 5.1 Jobs / Stages / SQL 页面分别看什么

- **Jobs**：看 action 级别的总体路径
- **Stages**：看 Shuffle 边界、task 分布与输入输出规模
- **SQL**：看查询计划、节点耗时、是否有明显异常算子

### 5.2 如何识别扫描过大、Shuffle 过重、Spill 过多

常见信号包括：

- 扫描量远超业务预期
- Shuffle read / write 远高于输入量
- spill 持续出现且量级明显偏大
- 某一两个 stage 占据绝大多数耗时

### 5.3 如何识别倾斜、OOM 与小文件问题

- 倾斜：少数 task 极慢、输入远高于中位数
- OOM：某一类 stage 或写出阶段稳定报内存问题
- 小文件：最后阶段分区过碎，输出文件数量异常多

UI 是调优入口，不是全部答案。它告诉你“问题像什么”，然后你再去对应专题做深入判断。

## 六、数据倾斜治理总览

### 如何判断是真倾斜

不是所有慢 task 都是倾斜。真正的倾斜通常表现为：

- 个别 task 的输入数据量远高于其他 task
- 某个 key 或某几个 key 过热
- 只有少数分区拖慢 stage 尾部

### 处理优先级：AQE → Broadcast → SQL 改写 → 加盐

建议优先级是：

1. 先看 AQE 是否能低成本解决
2. 能广播小表就先考虑 Broadcast
3. 再考虑两阶段聚合、热点 key 单独处理等 SQL 改写
4. 最后才考虑加盐打散

### 为什么不要一上来就手工加盐

加盐是兜底方案，不是首选。它的问题在于：

- 改写侵入性大
- 增加理解与维护成本
- 可能把局部问题扩散成更复杂的全局写法

完整诊断与方案分层请看：

- [Spark 数据倾斜治理](./04-Spark-数据倾斜治理.md)

## 七、小文件与输出控制

### AQE 自动合并不是万能

AQE 自动合并分区确实能解决很多“小 task 过多”的问题，但它不是全局最优器。几个关键边界要明确：

- 它是运行时启发式优化，不保证满足所有输出目标
- `advisoryPartitionSizeInBytes` 是建议值，不是硬目标
- 默认策略往往优先避免回归，而不是替你做到最省资源
- 它不会自动理解你的业务写出分布目标

也就是说，**AQE 自动合并更像“默认兜底修正”，不是“彻底替代分区设计”。**

### 什么时候用 COALESCE / REPARTITION / REBALANCE

可以这样理解：

- **COALESCE**：减少分区，适合已知只想温和收缩
- **REPARTITION**：显式重分布，适合需要更均匀的并行度或写出控制
- **REBALANCE**：更适合把输出前的数据重新平衡，兼顾文件数与分布均匀性

如果目标是“写出前重新把分区打匀”，`REBALANCE` 往往比简单 `coalesce` 更贴近业务目标。

### 输出文件数、业务分布、资源效率之间如何取舍

这三件事经常互相冲突：

- 文件数少，不代表执行效率最高
- 执行效率高，不代表业务分布最均匀
- 分布均匀，也不代表文件数正好满足下游要求

因此输出控制不该只看“文件少不少”，还要看：

- 下游读取方式
- 是否有分桶 / 分区字段要求
- 是否需要兼顾热点 key 分布

### Busy cluster 上为什么还要手动约束

在繁忙集群里，默认 AQE 策略未必总是最符合资源效率目标。你可能仍然需要：

- 更明确地控制初始分区数
- 显式使用 `REBALANCE` 或 `repartitionByRange`
- 根据业务写出目标手工约束最后阶段分布

## 八、优化效果评估

### 看总耗时、Stage 耗时与 Task 分布

不要只看“任务整体快了没有”，还要看：

- 主要耗时 stage 是否真的下降
- tail task 是否被缩短
- 是否只是把时间从一个 stage 挪到了另一个 stage

### 看扫描量、Shuffle 量、Spill 量

真正有解释力的指标通常是：

- input size 是否下降
- shuffle read / write 是否下降
- spill 是否减少
- task 分布是否更均衡

### 如何避免“调了很多参数但收益不清楚”

建议一次只改一类问题，并记录：

- 改了什么
- 预期改善什么指标
- 实际改善了哪些指标
- 有没有副作用

这样才能把 Spark 调优从“经验拍脑袋”变成“证据驱动的迭代”。
