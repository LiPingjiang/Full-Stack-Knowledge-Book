# 6.4 Spark 数据倾斜治理

> 适用场景：总有几个 task 特别慢、单个分区极重、JOIN 或聚合阶段卡住  
> 阅读前提：已了解 Spark UI 与 Shuffle 基本概念  
> 相关阅读：  
> - [Spark 性能优化](./04-Spark-性能优化.md)  
> - [Spark Shuffle 机制与调优参数](./04-Spark-Shuffle机制与调优参数.md)

## 一、什么是真正的数据倾斜

### 1.1 慢 task 不等于倾斜

一个 task 慢，可能是因为：

- 数据量真的大
- 机器状态差
- Spill 太多
- 下游写出慢

只有当少数分区的输入规模或热点 key 明显异常时，才更接近真正的数据倾斜。

### 1.2 如何从 Spark UI 判断倾斜

推荐先看：

- 最大 task 耗时 vs 中位数 task 耗时
- 最大输入量 vs 中位数输入量
- 是否只有极少数 task 拖慢尾部

### 1.3 JOIN 倾斜与聚合倾斜的区别

- **JOIN 倾斜**：通常是某些 key 在 Join 两边特别热
- **聚合倾斜**：通常是某些 key 在 group by 时集中到少数分区

两者的修法不完全一样。

## 二、治理优先级

### 2.1 先识别，再修复

不要一看到慢 task 就立刻上加盐。先判断：

- 是倾斜还是单纯分区不合理
- 是 Join 倾斜还是聚合倾斜
- 是输入问题还是输出问题

### 2.2 优先纯参数方案

如果 Spark 版本够新，先看看 AQE 能不能低成本缓解；这类方案侵入最小，最适合做第一优先级尝试。

### 2.3 再考虑 SQL 改写

当纯参数方案不够时，再考虑：

- Broadcast Join
- 两阶段聚合
- 热点 key 单独处理
- 上游预聚合

### 2.4 最后才用侵入式方案

加盐、分流、特判 key 都属于维护成本更高的路径，应该放在最后。

## 三、低侵入修复方案

### 3.1 AQE Skew Join

AQE 的 skew join 处理是 Spark 3.x 值得优先尝试的能力，因为它可以在部分场景下自动识别过大的分区并拆分处理，成本最低。

### 3.2 Broadcast Join

如果一边够小，把它广播掉，往往能直接避开一次高成本 Shuffle，也能绕开一部分热点 key 问题。

### 3.3 调整分区与并行度

有时问题不在 key 热点，而在分区策略本身过粗或过细。先修分区策略，可能就不需要更激进的改写。

## 四、中等侵入修复方案

### 4.1 两阶段聚合

先局部聚合再全局聚合，通常可以降低热点 key 直接打爆单个分区的风险。

### 4.2 热点 key 单独处理

如果热点 key 已知且数量不多，把它们单独拎出来走专门路径，往往比全局重写更划算。

### 4.3 上游 ETL 预聚合

如果倾斜是长期结构性问题，上游先做预处理比在下游每次作业里临时补丁更稳定。

## 五、高侵入兜底方案

### 5.1 加盐打散

加盐能解决一部分热点 key 过于集中的问题，但代价是：

- SQL 更复杂
- 下游要做去盐 / 再聚合
- 可维护性下降

### 5.2 拆表 / 分流 / 分层处理

如果热点非常极端、业务语义也允许，把热点数据和普通数据拆开处理，有时是更干净的方式。

### 5.3 什么时候不值得继续修 Spark，而该重设数据模型

如果倾斜根因来自业务建模本身，例如长期存在超级热点主体，那么仅靠 Spark 层修补通常只能缓解，不能根治。这时要回到数据模型或上游事件设计。

## 六、实战判断框架

### 先看输入分布

看是否真的有超热 key、超大分区、极端偏斜的维度。

### 再看 task 分布

看问题有没有真实投射到 stage / task 运行层。

### 最后选方案

推荐顺序：

1. AQE / Broadcast / 分区策略
2. 两阶段聚合 / 热点 key 单独处理
3. 加盐 / 分流 / 模型调整
