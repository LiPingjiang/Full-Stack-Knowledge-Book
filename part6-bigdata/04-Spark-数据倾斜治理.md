# 6.4 Spark 数据倾斜治理

> 适用场景：总有少数 task 极慢、某些 Join / 聚合阶段拖尾明显、单个分区异常重、热点 key 长期打不平

## 一、先明确：数据倾斜首先是诊断题，不是技巧题

很多人一提 Spark 倾斜，第一反应就是“加盐”。这几乎是最典型的经验主义误区。

真正成熟的处理顺序应该是：

1. **先确认是不是“真倾斜”；**
2. **再判断是哪一类倾斜；**
3. **再决定用低侵入还是高侵入方案；**
4. **最后评估这是不是 Spark 层就该解决的问题。**

也就是说，数据倾斜不是“你记住几招就能通杀”的问题，而是一个要靠证据、分型和治理优先级来处理的问题。

## 二、什么才算真正的数据倾斜

### 2.1 慢 task 不等于数据倾斜

少数 task 很慢，当然可能是倾斜，但也可能根本不是。常见混淆项包括：

- 某台机器状态异常；
- 某个 Executor 频繁 GC；
- Spill 特别重；
- 下游写出到存储层很慢；
- 某个 stage 本身并行度过低，导致 task 天生偏重。

所以“看见慢 task 就判倾斜”是很危险的。真正更接近倾斜的信号，是：

- 少数 task 的输入数据量远大于其他 task；
- 某些 key 明显是超热点；
- stage 尾部只被极少数 task 长时间拖住。

### 2.2 倾斜的本质：数据分布极不均匀

倾斜的核心不是“有些任务慢”，而是：

> **本该被均匀分摊到多个分区 / task 的工作量，异常集中到了极少数分区或极少数 key 上。**

这会带来两个直接后果：

- 并行度名义上很高，实际上被少数重分区拖死；
- 局部内存、排序、Spill、网络拉取压力被放大。

也因此，倾斜问题往往和 Join、聚合、写出分布紧密相关。

### 2.3 先从 Spark UI 找证据，而不是靠感觉

判断是否倾斜，建议优先看 Spark UI 中某个可疑 stage 的：

- 最大 task 耗时 vs 中位数 task 耗时；
- 最大输入量 / Shuffle Read vs 中位数；
- 是否只有极少数 task 明显拖尾；
- Spill、GC、失败重试是否集中在少量 task 上。

如果只是整体都慢，而不是极少数 task 特别异常，那更可能是“全局都重”，不一定是倾斜。

## 三、先给问题分型：你面对的是哪一种倾斜

### 3.1 Join 倾斜

Join 倾斜通常表现为：

- 某些 key 在 Join 两边都非常热；
- Join 后某些分区异常大；
- SortMergeJoin / Shuffle Hash Join 阶段少数 task 极慢。

它的本质是：**热点 key 让本该均匀分布的匹配工作异常集中。**

### 3.2 聚合倾斜

聚合倾斜通常出现在：

- `group by` 某些 key 极热；
- 某些分组聚合状态特别大；
- 聚合后少数 task 既慢又容易 Spill / OOM。

它和 Join 倾斜很像，但治理思路不完全一样。Join 倾斜更常考虑广播、Join 改写；聚合倾斜更常考虑两阶段聚合、预聚合、热点 key 单独处理。

### 3.3 写出倾斜 / 输出热点

还有一类很容易漏掉：计算过程未必明显倾斜，但**写出阶段**出现热点，例如：

- 按某个业务键写出，某些分区特别大；
- 小文件与大文件并存，分布很差；
- 下游表分区严重不均。

这类问题不能简单按 Join / 聚合套路处理，往往要回到输出分区设计、REBALANCE、业务分桶或上游建模上看。

### 3.4 分区不合理 ≠ 热点 key 倾斜

还有一种常见误判，是把“分区策略不好”直接叫成“倾斜”。例如：

- 分区数太少，单 task 天生很重；
- 范围分区划得不合理；
- 上游文件大小差异极大，读入阶段天然不均。

这类问题确实表现为“task 很不均匀”，但根因不一定是热点 key，而可能只是分区策略本身不合理。修法自然也不同。

## 四、诊断流程：别急着修，先按流程判断

### 4.1 第一步：确认问题真的集中在少数 task

先回答两个问题：

1. 是整个 stage 普遍慢，还是只有少数 task 特别慢？
2. 慢 task 的输入量、Shuffle Read、Spill 是否明显高于中位数？

如果答案是否定的，先别急着叫它倾斜。

### 4.2 第二步：判断热点出现在 Join、聚合还是写出阶段

看物理计划和 stage 位置：

- 如果问题主要在 Join 相关 stage，优先按 Join 倾斜看；
- 如果问题主要在聚合 / 窗口聚合阶段，优先按聚合倾斜看；
- 如果执行阶段都还好，最后写出特别不均，优先按输出热点看。

### 4.3 第三步：判断是“热点 key”还是“分区策略问题”

这一步很关键。因为两类问题的修法差很多：

- **热点 key 问题**：常见手段是 Broadcast、热点拆分、两阶段聚合、加盐；
- **分区策略问题**：常见手段是重设分区、调整并行度、重做写出分布、改输入组织。

### 4.4 第四步：再决定是否使用侵入式方案

只有在以下低侵入手段都不足时，才建议走高侵入方案：

- AQE skew join / 自动分区纠偏；
- Broadcast Join；
- 调整分区策略；
- 两阶段聚合；
- 热点 key 单独处理。

如果这些还不够，再考虑加盐、分流、拆表等维护成本更高的方案。

## 五、治理决策表：按症状选方案，而不是背招式

| 现象 / 证据 | 更可能的根因 | 优先方案 | 侵入性 |
| --- | --- | --- | --- |
| 少数 Join task 极慢，且对应分区 Shuffle Read 特别高 | Join 热点 key | AQE skew join、Broadcast、热点 key 单独处理 | 低到中 |
| `group by` 后少数 task 明显拖尾，并伴随 Spill | 聚合热点 key | 两阶段聚合、预聚合、热点 key 单独处理 | 中 |
| 最终写出文件极不均匀 | 输出分区设计不合理、业务 key 热点 | REBALANCE、重设写出分区策略、业务分流 | 低到中 |
| 所有 task 都偏重，但没有明显极端值 | 整体数据量大、分区数不合理 | 先调分区与并行度，再看逻辑是否过重 | 低 |
| 某些分区极大，但热点 key 不明显 | 上游文件 / 范围分区 / 输入组织不均 | 重设输入与分区策略 | 低到中 |
| 只有已知少量超级热点 key 造成问题 | 结构性热点 | 热点 key 单独处理、分流、必要时加盐 | 中到高 |

这张表的意义是提醒你：**先按症状归因，再按侵入性选方案。**

## 六、低侵入方案：先试“对系统最友好”的路

### 6.1 AQE skew join：现代 Spark 应优先考虑的低成本缓解手段

如果你在 Spark 3.x 的 SQL 路径里，AQE skew join 往往应该是第一批要检查的能力。它的价值是：

- 不需要先大改 SQL；
- 能在部分 Join 倾斜场景下自动识别过大的分区并做拆分或重组；
- 维护成本最低。

但这里一定要讲清边界：

- 它主要更适合 **Join 倾斜**，不是所有聚合倾斜都能靠它解决；
- 它只能处理自己在运行时观察到、且规则能覆盖的场景；
- 它缓解的是“部分倾斜”，不是把数据分布问题彻底消灭。

所以 AQE skew join 应该被理解为：**低侵入首选，不是一次性根治器。**

### 6.2 Broadcast Join：能不 Shuffle 就尽量别让两边都 Shuffle

如果 Join 的一边足够小，Broadcast 往往是最干净的绕行方式。它的收益通常有两层：

- 避免两边都做高成本 Shuffle；
- 让热点 key 的一部分分布压力不再以同样方式集中到下游。

但 Broadcast 也不是“看到小表就一定广播”，你还要看：

- 小表是否真的足够小；
- 过滤后是否明显变小；
- Driver / Executor 内存是否能稳妥承受广播代价。

### 6.3 先修分区策略，而不是直接修热点

有时你看到的是“极少数 task 很重”，但根因其实是：

- 分区数太少；
- 初始文件大小差异太大；
- 写出前没有重新均衡；
- 范围分区方式天然不均。

这类问题如果先去加盐，往往是绕远路。更好的顺序是：

1. 先确认是不是热点 key；
2. 如果不是，就先修分区策略；
3. 看修完后是否还存在真正热点。

## 七、中侵入方案：开始改 SQL 和处理路径

### 7.1 两阶段聚合：聚合倾斜的经典主线

当问题出在聚合热点时，两阶段聚合通常是最常见的中侵入方案。它的思路是：

- 先在更细粒度局部聚合；
- 让数据量先缩一轮；
- 再进入全局聚合。

这样做的价值在于：**尽量别让所有原始明细直接在最终热点 key 上汇聚。**

它特别适合：

- 可交换、可组合的聚合；
- 原始明细很多、热点 key 很热；
- 上游预收缩空间明显的场景。

### 7.2 热点 key 单独处理：比全局改写更有针对性

如果热点 key 已知，而且数量不多，那么把它们单独拎出来处理，往往比改全量逻辑更划算。典型思路包括：

- 热点 key 走专门分支；
- 普通 key 走原有主路径；
- 最后再把结果合并。

它的优势是：

- 对普通数据影响较小；
- 更容易精确控制热点；
- 可维护性通常优于“大面积无差别加盐”。

### 7.3 上游预聚合 / 预处理：比每次作业内临时补丁更稳

如果倾斜长期稳定存在，而且根因明确来自上游数据结构，那么最成熟的解法常常不是“每个 Spark 作业都打一层补丁”，而是：

- 上游先做预聚合；
- 先把超级热点分流；
- 或者在入仓阶段就调整模型。

这类方案短期改动可能更大，但长期往往更稳。

## 八、高侵入方案：最后才用的兜底手段

### 8.1 加盐打散：有效，但维护成本高

加盐能解决一部分热点 key 过度集中的问题，思路是把同一个热点 key 临时拆成多个子 key，再在后面去盐或再聚合。它为什么有效？因为它确实把单点热点打散了。

但它的代价也很明确：

- SQL / 处理逻辑更复杂；
- 上下游都要知道盐值逻辑；
- 结果恢复和二次聚合成本增加；
- 长期维护可读性会下降。

所以它适合作为：

- 低侵入手段无效后的兜底；
- 热点明确且足够极端；
- 业务允许增加一层复杂度的场景。

### 8.2 分流 / 拆表 / 分层处理：适合结构性极端热点

如果热点不是偶发，而是长期结构性存在，例如：

- 极少数主体天然占绝大多数数据；
- 某些超级商家 / 超级城市 / 超级渠道常年热；
- 同一类热点反复出现在多条任务链路里。

这时简单在单条 SQL 上修补，通常只能缓解不能根治。更彻底的路径往往是：

- 热点数据单独建路；
- 普通数据走主链；
- 在模型层显式承认“它们不是一类数据”。

这已经不只是 Spark 技巧，而是数据建模与处理架构问题。

### 8.3 什么信号说明你该停止“继续修 Spark 参数”

当你看到下面这些信号时，往往说明问题已经不该继续停留在 Spark 层补丁：

- 同一类热点在多条任务里反复出现；
- 每次都要靠特判 SQL 才能勉强跑过；
- 调分区、调资源、AQE、Broadcast 都只能局部缓解；
- 热点来自稳定业务结构，而不是偶发分布异常。

这时更应该回到：

- 上游数据模型；
- 分层分流设计；
- 离线链路拆分；
- 业务主键或事件组织方式。

## 九、实战治理顺序：一套可复用的落地流程

如果线上任务出现疑似倾斜，推荐按下面顺序处理：

1. **看 UI 证据**：确认是不是少数 task 拖尾；
2. **看 stage 类型**：判断问题主要在 Join、聚合还是写出；
3. **看输入分布**：确认是热点 key 还是分区策略问题；
4. **先试低侵入方案**：AQE、Broadcast、重设分区；
5. **再试中侵入方案**：两阶段聚合、热点 key 单独处理、上游预聚合；
6. **最后才用高侵入方案**：加盐、分流、拆表；
7. **复盘根因**：判断是否应该上升到数据模型层解决。

这套顺序的价值，在于它能帮你避免两个最常见错误：

- **把不是倾斜的问题按倾斜修；**
- **把本该低侵入解决的问题，一上来就做成长期技术债。**

## 十、最后总结：Spark 倾斜治理真正考验的是什么

数据倾斜治理最能拉开差距的，不是你记住了多少“技巧名词”，而是你是否具备下面三种能力：

1. **证据意识**：先证明是倾斜，再动手；
2. **分型意识**：Join 倾斜、聚合倾斜、写出热点、分区不均要分开看；
3. **治理顺序意识**：先低侵入，后高侵入，最后必要时回到模型层。

所以真正成熟的一句话总结应该是：

> **Spark 倾斜治理不是“加盐技巧大全”，而是一套基于证据、分型和治理优先级的诊断与处置方法。**
