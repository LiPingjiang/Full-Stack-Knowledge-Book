# 6.4 Spark 错误排查与兼容性

> 适用场景：报错很多但不知道如何分型、同一类问题反复踩坑、跨引擎读写时总有兼容性意外  
> 阅读前提：建议先看调试运维专题，建立日志与 UI 的基本取证路径  
> 相关阅读：  
> - [Spark 调试运维](./04-Spark-调试运维.md)  
> - [Spark 资源内存与 Spill 调优](./04-Spark-资源内存与Spill调优.md)  
> - [Spark Shuffle 机制与调优参数](./04-Spark-Shuffle机制与调优参数.md)

## 一、先明确：这篇不是“错误列表”，而是错误模式库

很多 Spark 错误文档会写成：

- 报错 A 是什么；
- 报错 B 怎么改参数；
- 报错 C 可能是什么原因。

这样的问题是：你遇到线上问题时，很难快速判断它属于哪一类根因。

这篇文档的目标不是穷举所有错误，而是帮你建立一条更可复用的路径：

> **报错 → 先分型 → 再判断根因落在哪一类系统边界上 → 再决定排查方向。**

所以这篇文档更像“错误模式库”，而不是“异常名词百科”。

## 二、第一层分型：先按问题落点，而不是按报错字符串

### 2.1 提交期错误：应用还没真正进入执行期

典型特征：

- 刚提交就失败；
- UI 可能没完整建立；
- 多见于主类、参数、依赖、环境初始化、Driver / AM 启动链路问题。

这类错误最容易被误判成“Spark 跑挂了”，其实它常常还没真正开始跑。

### 2.2 执行期错误：已经有 stage / task 痕迹

典型特征：

- UI 能看到执行过程；
- 某个 stage / task 失败；
- 常见于 OOM、Shuffle 拉取失败、序列化、读写异常、外部系统写入失败。

这类错误通常才真正进入“Spark 执行问题”主战场。

### 2.3 数据读写错误：不一定是计算坏了，可能是边界错了

常见表现：

- 读不到数据；
- 写出失败；
- schema 不兼容；
- 文件存在但逻辑上不可见；
- 元数据与真实文件状态不一致。

这类问题最容易暴露“Spark 和存储 / 元数据 / 外部系统之间的边界不一致”。

### 2.4 结果正确性错误：最难，因为任务看起来成功了

表面上任务可能没报错，但结果却不对。常见根因包括：

- SQL 语义理解错；
- Join 位置或过滤条件放错；
- 版本行为变化；
- 跨引擎读写后边界语义改变；
- 分区 / 元数据 / null 行为差异。

这类问题不是传统意义上的“运行报错”，但它在生产里往往更贵。

## 三、第二层分型：先看根因更像哪一类系统问题

### 3.1 资源与内存类

典型代表：

- Driver OOM；
- Executor OOM；
- 容器超限被 kill；
- Spill 过重引发执行退化。

这类问题的核心不是“堆不够”四个字，而是：

- 哪一层在吃内存；
- 是单 task 过重还是整体资源不合理；
- 是逻辑膨胀还是资源配置偏小。

### 3.2 Shuffle 与运行时链路类

典型代表：

- FetchFailed；
- 本地中间文件缺失；
- 网络拉取异常；
- Executor 丢失导致下游无法继续拉取。

这类问题的核心是：**执行链路中间状态还能不能稳定被后续阶段消费。**

### 3.3 序列化与对象边界类

典型代表：

- `NotSerializableException`；
- Kryo 相关报错；
- 广播对象过大；
- 闭包里捕获不该捕获的对象。

这类问题说明的不是“Spark 坏了”，而是：**你把不适合跨节点、跨进程传递的对象放进了分布式执行边界。**

### 3.4 数据源与兼容性类

典型代表：

- Parquet / Hive 读写差异；
- schema 演进不兼容；
- 元数据感知不同步；
- 目标路径和提交协议不一致。

这类问题真正难的地方在于：**错误往往不发生在单一系统内部，而发生在系统交界处。**

## 四、资源与内存类错误：先分 Driver、Executor、容器三层

### 4.1 Driver OOM：很多时候是“把分布式结果硬拉回中心节点”

Driver OOM 常见于：

- `collect()` 拉太多数据；
- `toPandas()` 规模失控；
- 广播构建过大；
- Driver 端做了本该分布式完成的组装逻辑。

所以 Driver OOM 的核心问题通常不是“Spark 内存模型神秘”，而是：

> **你把不该回到 Driver 的东西回到了 Driver。**

### 4.2 Executor OOM：常常是单 task 太重，而不是集群总内存太少

Executor OOM 更常见的根因包括：

- 单分区太大；
- 倾斜导致少数 task 极重；
- 排序 / 聚合 / Join 状态过大；
- 缓存过多；
- 广播 / 反序列化后对象膨胀。

这类问题最怕的误判是：直接加 executor memory，而不先看分区、倾斜、SQL 写法。

### 4.3 容器被 kill：它不一定等于 JVM 主动抛 OOM

如果你看到的是 YARN kill、容器超限、Pod 被系统终止，这类问题要优先想到：

- memoryOverhead；
- 堆外内存；
- Python / 本地库额外消耗；
- 容器资源边界比 JVM 堆更早触顶。

这也是为什么“容器被 kill”和“Java heap space”不能当成同一类问题来排。

### 4.4 Spill 很重：它不一定直接报错，但常常是更大问题的前兆

Spill 重的意义不在于“磁盘用多了点”，而在于它经常意味着：

- 分区粒度过粗；
- 排序 / 聚合压力过大；
- 内存空间竞争激烈；
- 执行路径已经在退化。

所以 Spill 更像一个“执行压力报警器”。

## 五、Shuffle 与运行时错误：先判断是文件生命周期问题，还是链路稳定性问题

### 5.1 FetchFailed：它通常不是“随手调个超时”就能解决

FetchFailed 的核心含义是：

> **下游 task 需要拉取上游 shuffle 数据时，拉不到、拉不全，或者拉取链路失效了。**

这背后常见的怀疑方向包括：

- 上游 executor 或节点不稳定；
- 中间文件已经不可用；
- 本地盘或网络异常；
- 运行环境下 Shuffle 服务保留机制有差异；
- 极端倾斜导致少数拉取请求异常重。

所以这类问题的第一反应不应该是“把 timeout 调大一点”，而是先问：**中间结果为什么不稳定了。**

### 5.2 FileNotFoundException：第一分流是看“丢的是哪种文件”

FileNotFoundException 至少要先分两类：

**第一类：业务数据文件找不到**  
如果路径指向：

- HDFS / warehouse；
- 表目录；
- 上游业务文件；
- 分区目录。

那更应怀疑：

- 上游数据被覆盖、清理或尚未准备好；
- 元数据与真实文件状态不一致；
- 调度时序问题；
- 分区感知没同步。

**第二类：本地临时文件或中间文件找不到**  
如果路径更像：

- executor 本地目录；
- shuffle 中间文件；
- spill 文件；
- 节点本地临时路径。

那更应怀疑：

- executor / 节点生命周期变化；
- 本地盘策略问题；
- shuffle 文件被提前清理；
- 运行环境导致中间结果无法保留。

这就是为什么 FileNotFoundException 不能只看异常名，而必须先看路径归属。

### 5.3 为什么 FetchFailed 和本地文件丢失经常要一起看

因为它们常常不是独立事件，而是同一条链路上的前后症状：

- 文件丢了；
- 下游拉不到；
- 于是出现 FetchFailed 或重试放大。

所以遇到其中一个时，通常都应该顺带检查另一个方向。

## 六、序列化类错误：它暴露的是“对象边界设计”问题

### 6.1 `NotSerializableException` 的根因通常不在 Spark 本身

这类错误常见于：

- 闭包里捕获了外部大对象；
- 把数据库连接、线程池、复杂上下文对象带进 executor；
- 某些自定义类天然不可序列化。

它真正说明的是：**你把不适合跨节点传输的对象，放进了分布式执行边界。**

### 6.2 Kryo 比 Java Serialization 更高效，但不是“打开即治百病”

官方文档一直强调 Kryo 更快、更省空间，但真正重要的是：

- 你序列化的对象是什么；
- 是否做了类注册；
- 是否理解对象图本身就很复杂；
- 是不是本来就不该把这些对象带入 executor。

所以 Kryo 是优化工具，不是对象边界设计错误的免死金牌。

### 6.3 广播超时、大对象广播为什么也属于这类问题

广播超时很多时候不是“网络太慢”这么简单，而是：

- 广播对象过大；
- 广播内容本就不适合广播；
- Driver 端构造方式有问题；
- 节点间传递成本被严重低估。

从根上说，这仍然是“你选择了怎样的跨节点对象边界”问题。

## 七、数据源与兼容性：真正难在跨系统边界，而不是单个参数

### 7.1 Parquet / Hive 兼容性问题，真正要问的是“谁写的、谁读的、按什么规则解释”

跨引擎读写时最容易出错的，不是“文件格式名字一样”，而是：

- schema 推断规则是否一致；
- 分区字段是否按相同语义处理；
- null、大小写、类型转换边界是否一致；
- 写端和读端对元数据的理解是否一致。

所以兼容性问题的核心不是“某个参数没配”，而是：

> **写入语义和读取语义是不是站在同一套规则上。**

### 7.2 Schema 演进为什么会在跨任务、跨引擎环境里变得危险

字段新增、字段顺序变化、类型变化，单看某个系统内部也许还能工作，但一旦经过：

- 多个 Spark 作业；
- Hive 表元数据；
- 外部查询引擎；
- 历史文件混读。

就很容易出现“表名一样、字段看着也差不多，但读取解释已经不一样”的问题。

### 7.3 为什么“数据在那却读不到”常常不是文件没写，而是元数据和感知没对齐

很多现场里，文件其实已经存在，但依然会出现：

- 查不到分区；
- 新数据不生效；
- 表结构和真实文件不一致；
- Spark 和外部系统读取结果不同。

这类问题往往说明：

- metastore 没同步；
- 分区没修复；
- 缓存元数据没刷新；
- 读取端仍在按旧 schema / 旧分区感知解释数据。

### 7.4 HDFS 写入稳定性为什么不能只看“有没有权限”

写入问题常见根因还包括：

- 小文件过多；
- 提交协议与 rename / commit 语义交互复杂；
- 重试后残留脏文件；
- 目标路径已有异常状态。

所以“写失败”不一定只是权限问题，也可能是提交语义和目标存储边界没对齐。

## 八、版本与参数差异：真正要防的是“行为变化”，不是“参数名变化”

### 8.1 `driver.maxResultSize` 是安全阀，不是行为借口

它的意义是防止 Driver 收太大结果集，但如果你总是在靠它兜底，那真正的问题应该是：

- 为什么要 collect 这么多；
- 为什么结果必须集中回 Driver；
- 能不能改成分布式写出或分批处理。

### 8.2 版本升级后最危险的是“默认行为悄悄变了”

升级后常见风险包括：

- 默认参数变化；
- SQL 语义更严格；
- AQE / Hint / Join 选择不同；
- 数据源读取行为变化。

所以版本问题不该只理解为“API 变不变”，更要理解为：**执行与解释规则可能在变。**

### 8.3 如何区分“代码问题”与“平台问题”

至少问三个问题：

1. 同样逻辑是否在别的环境稳定复现？
2. 问题是否和节点、时间窗口、资源状态强相关？
3. 日志更指向业务逻辑、对象边界，还是更指向环境与基础设施？

这三个问题非常适合做第一轮分流。

## 九、错误速查表：让你先把问题送到正确方向，而不是直接下结论

| 现象 / 关键词 | 第一分型 | 优先怀疑方向 | 第一动作 |
| --- | --- | --- | --- |
| 任务刚提交就秒退 | 提交期错误 | 主类、依赖、参数、Driver / AM 初始化 | 先看提交端与 Driver / AM 日志 |
| `Java heap space` / OOM | 资源类错误 | Driver / Executor / 容器三层之一 | 先分层，不要直接加内存 |
| FetchFailed | Shuffle 运行时错误 | 中间文件不可用、节点 / 本地盘 / 网络异常 | 先看上游 executor 和 shuffle 文件生命周期 |
| FileNotFoundException | 文件边界错误 | 业务文件缺失 或 本地中间文件丢失 | 先看路径归属 |
| `NotSerializableException` | 序列化边界错误 | 闭包捕获对象不当、对象不可序列化 | 先看闭包与对象边界 |
| 广播超时 / 广播过大 | 对象边界 / 资源类 | 广播对象过大、Driver 构造不合理 | 先看广播对象本身 |
| 数据在目录里但查不到 | 元数据 / 分区感知错误 | metastore、分区、缓存未同步 | 先查元数据和分区感知 |
| 升级后 SQL 结果变化 | 行为变化 / 兼容性 | 默认语义、Hint / AQE / 读取规则变化 | 先做版本行为对比 |

这张表最重要的价值，是让你先去对的方向，而不是直接拿一个参数硬试。

## 十、最后总结：这篇错误文真正要教会你的是什么

真正成熟的 Spark 错误排查，不是看到异常名就背答案，而是建立下面这套顺序：

1. **先分入口：** 提交期、执行期、读写期、结果正确性；
2. **再分系统边界：** 资源、Shuffle、对象序列化、数据源兼容性；
3. **再看具体异常名：** FetchFailed、FileNotFoundException、NotSerializableException、OOM；
4. **最后再决定行动：** 去看哪份日志、哪个系统、哪类配置或哪段逻辑。

所以这篇文档最重要的结论可以概括成一句话：

> **Spark 里的大多数“复杂错误”，真正难点都不在异常字符串本身，而在于你是否先找对了它所属的系统边界。**
