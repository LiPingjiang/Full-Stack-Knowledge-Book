# 6.4 Spark 错误排查与兼容性

> 适用场景：报错很多但不知道如何分型、兼容性问题反复踩坑  
> 阅读前提：建议先看调试运维专题  
> 相关阅读：  
> - [Spark 调试运维](./04-Spark-调试运维.md)  
> - [Spark 资源内存与 Spill 调优](./04-Spark-资源内存与Spill调优.md)

## 一、先做错误分型

### 1.1 提交期错误

特点是：

- 任务刚提交就失败
- UI 很可能没完全建立
- 常见于主类错误、依赖包缺失、提交参数错误

### 1.2 执行期错误

特点是：

- 作业已经开始跑
- 某个 stage 或 task 失败
- 往往有比较明确的异常栈或 Executor 日志

### 1.3 数据读写错误

常见于：

- 数据源 schema 不一致
- 文件缺失
- 兼容性配置不匹配
- 写出阶段目标路径或权限有问题

### 1.4 结果正确性错误

这类问题最隐蔽，因为作业表面上可能成功了，但结果不对。典型原因包括：

- SQL 语义理解错
- 过滤条件位置不当
- Join 逻辑不符合业务语义
- 版本行为差异

## 二、内存与资源类错误

### 2.1 Executor OOM

这类问题通常和以下因素有关：

- 单 task 压力过大
- 分区太少
- Spill 压力高
- 大对象过多

### 2.2 Driver OOM

Driver OOM 常见于：

- `collect()` 拉太多数据
- `toPandas()` 过大
- 广播对象太大
- Driver 侧做了不适合放在 Driver 的聚合 / 组装逻辑

### 2.3 YARN kill / 容器超限

如果是容器超限，排障方向应该转向：

- memoryOverhead
- 堆外内存
- Python / 本地库等附加消耗

### 2.4 Spill 过重

Spill 重不一定报错，但经常意味着：

- 分区过大
- 排序 / 聚合压力大
- 内存模型不合适

## 三、Shuffle 与运行时错误

### 3.1 FetchFailed

FetchFailed 往往不是“某个参数需要随手调一下”这么简单，而要一起看：

- 上游 Executor 是否稳定
- 中间文件是否仍可用
- 网络与磁盘是否有异常

### 3.2 FileNotFoundException

这类错误至少要先区分两类：

- 指向仓库 / HDFS / warehouse 中的业务文件：更像上游数据被改写或清理
- 指向本地临时目录或中间文件：更像 Shuffle 文件生命周期出了问题

### 3.3 序列化错误

常见根因包括：

- 对象不可序列化
- 类版本不一致
- Kryo 配置不合理
- 闭包里捕获了不该捕获的大对象或复杂对象

### 3.4 广播超时与大对象问题

广播超时很多时候不是“超时时间太小”，而是广播对象本身太大、网络太慢、或者对象构造方式不合理。

## 四、数据源与兼容性问题

### 4.1 Parquet / Hive 兼容性

跨引擎读写时要特别注意：

- schema 推断差异
- 分区字段处理差异
- null / 类型转换差异
- 写入格式与读取端预期不一致

### 4.2 Schema 演进与读写不一致

字段新增、顺序变化、类型变化，都会在跨任务、跨引擎读写中带来问题。不能只看“表名一样”，还要看 schema 是否真的兼容。

### 4.3 HDFS 写入稳定性

写入稳定性问题通常和：

- 目标路径状态
- 小文件过多
- 下游 rename / commit 机制
- 上游失败重试后残留文件

有关。

### 4.4 元数据与分区感知问题

很多“明明数据在那却读不到”的问题，本质不是文件没写出来，而是 metastore、分区感知、缓存元数据没有同步好。

## 五、参数与版本差异带来的问题

### 5.1 Kryo vs Java Serialization

Kryo 通常更高效，但不是“打开就一定万事大吉”。真正重要的是：

- 你序列化的对象是什么
- 是否存在复杂闭包
- 类型注册与兼容性是否清楚

### 5.2 driver.maxResultSize

这个参数更像是 Driver 侧结果收集的安全阀。它能保护 Driver，但不应该被拿来掩盖“为什么你要 collect 这么多数据”的根因。

### 5.3 版本升级后的行为变化

升级后常见变化包括：

- 默认参数变化
- SQL 语义更严格
- AQE / Hint / Join 行为差异
- 数据源兼容性差异

### 5.4 如何区分“代码问题”与“平台问题”

推荐问三个问题：

1. 同样 SQL 在别的环境是否稳定复现？
2. 问题是否与资源、节点、时间窗口相关？
3. 日志是更指向业务逻辑，还是更指向环境基础设施？

## 六、错误速查表

### 按关键词定位

- OOM：先分 Driver / Executor / 容器
- FetchFailed：先看 Shuffle 文件与 Executor 稳定性
- FileNotFound：先看文件路径归属
- timeout：先看对象大小、网络、下游依赖

### 按症状定位

- 提交秒退：优先看 AM / Driver 初始化
- 跑到一半挂：优先看 stage / task / Executor
- 结果不对：优先看 SQL 语义与数据分布

### 按组件定位

- Driver 问题：主逻辑、提交、collect、广播
- Executor 问题：task、Shuffle、OOM、数据读写
- 资源管理器问题：容器、Pod、节点、调度
