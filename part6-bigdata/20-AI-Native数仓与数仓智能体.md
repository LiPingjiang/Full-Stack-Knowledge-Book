# 6.20 AI Native 数仓与数仓智能体：把三条线拼成一张图

> **一句话定位**：本节不引入新的技术点，而是把 [6.10 语义层与指标平台](./10-语义层与指标平台.md)、[6.19 元数据管理与智能数据治理](./19-元数据管理与智能数据治理.md)、[7.8 AgentBI 智能分析](../part7-ai-engineering/08-AgentBI智能分析.md) 这三篇分别讲透的内容，按照"一次自然语言提问从进来到出去经过了哪些系统"这条主线串成一张完整的架构图，解决的是"知道每个零件是什么，但讲不清楚整机怎么运转"这个问题。

---

## 一、为什么需要这一节

数仓岗位的 JD 越来越多地出现这样的表述——"建设数仓智能体（Data Agent）"、"自然语言驱动的数据查询、指标解读、异常归因"、"AI 赋能体系：智能 ETL 开发辅助、数据质量智能巡检、元数据智能管理"。这些能力不是三个孤立的功能点，而是同一套系统在三个不同环节的体现——元数据管理是"系统怎么理解数仓里有什么"，语义层是"系统怎么统一地解释业务口径"，AgentBI 是"系统怎么和人对话"。三者顺序衔接、缺一不可：没有元数据，语义层不知道该怎么定义指标背后对应哪些物理表；没有语义层，AgentBI 生成的 SQL 各说各话、口径混乱；没有 AgentBI，元数据和语义层再完善也只是后台的静态资产，用户感知不到。

面试中最容易暴露知识碎片化的地方就是这里——能单独讲清楚"血缘怎么用图数据库存"，也能单独讲清楚"Text2SQL 有哪几种技术路线"，但被追问一句"这两个东西是什么关系，一次查询请求先经过谁后经过谁"时卡住。这一节就是补这个"关系"和"顺序"。

---

## 二、整体架构：一次自然语言提问的完整旅程

```
用户："上个月华东区活跃用户的环比波动，帮我分析下原因"
   │
   ▼
┌─────────────────────────────────────────────────────────┐
│  第一层：AgentBI 交互层（对应 7.8）                        │
│  - 意图识别：这是一个"指标查询 + 归因分析"复合请求          │
│  - 任务拆解：① 查询"活跃用户"环比数据 ② 下钻定位波动来源     │
└─────────────────────────────────────────────────────────┘
   │ 拆解出的子任务需要知道"活跃用户"到底怎么算
   ▼
┌─────────────────────────────────────────────────────────┐
│  第二层：语义层（对应 6.10）                                │
│  - 查找指标定义："活跃用户" = 已注册且当日有行为埋点的用户数  │
│  - 确定关联的维度：地区、日期                               │
│  - 生成标准化的查询请求（不是裸 SQL，是"指标+维度"的结构化查询）│
└─────────────────────────────────────────────────────────┘
   │ 语义层要把"指标+维度"翻译成可执行 SQL，需要知道物理表在哪
   ▼
┌─────────────────────────────────────────────────────────┐
│  第三层：元数据与治理层（对应 6.19）                         │
│  - 表搜索：这个指标的物理实现在哪张 DWS 表                   │
│  - 血缘定位：如果数据异常，从这张表反查上游 ETL 链路          │
│  - 口径校验：确认没有其他团队用不同口径定义过"活跃用户"       │
└─────────────────────────────────────────────────────────┘
   │ 拿到确定的表结构和血缘关系后，回到语义层生成最终 SQL
   ▼
计算引擎执行（Spark/Flink/Doris/ClickHouse，对应 6.4/6.5/6.6/6.11）
   │
   ▼
结果回传 AgentBI 层，生成图表 + 自然语言归因结论（如果发现某个环节血缘上的任务失败，直接把这个信号带入归因摘要）
```

这张图的关键信息不是每个方框里的内容（那些在各自小节里已经讲透了），而是**箭头的方向和依赖关系**——AgentBI 依赖语义层才能保证"口径统一"，语义层依赖元数据层才能知道"物理表在哪、血缘怎么走"。反过来说，如果面试官问"能不能跳过语义层，让 Agent 直接读表生成 SQL"，标准的回答思路是：技术上可行（纯 LLM 路线，[6.10](./10-语义层与指标平台.md) 里提到的 Vanna 模式），但会失去语义层统一口径、行列权限过滤这两个核心价值，只适合个人探索性场景，不适合企业级、多团队共用的场景——这正是 [6.10](./10-语义层与指标平台.md) 对比表里"纯 LLM"一列评分低的原因。

## 三、三层各自的职责边界（避免混淆）

**元数据与治理层回答"有什么、从哪来"。** 它是静态资产层，回答"这个数仓里有哪些表、字段什么含义、数据从哪张表加工而来、现在数据质量是否正常"，本身不涉及"用户这次想问什么"。这一层的 AI 赋能（[6.19](./19-元数据管理与智能数据治理.md) 第三节）主要是把这些静态资产的维护成本降下来——自动生成字段描述、自动发现口径不一致、自动巡检异常，全部是"背后默默运转"的能力，不直接面向最终用户对话。

**语义层回答"怎么统一地算"。** 它是翻译层，把元数据层暴露出来的物理表结构，包装成业务人员能理解的指标和维度，并且保证不管是 BI 报表、API 还是 Agent 在查询，用的都是同一份指标定义。这一层不负责"理解用户的自然语言意图"，它假设上游已经把意图转化成了明确的"要看哪个指标、哪些维度、什么条件"，它的工作是把这个明确的请求转成正确、高效、带权限过滤的 SQL。

**AgentBI 层回答"用户到底想问什么、怎么跟人解释结果"。** 它是唯一直接面向最终用户的一层，负责把模糊的自然语言拆解成语义层能理解的结构化请求，并且在拿到结果后做进一步的归因、总结、可视化推荐。它是三层里离用户最近、也是最容易被误认为"就是全部"的一层——但实际上它能不能给出准确、可信的答案，完全取决于背后语义层和元数据层是否扎实。这也是为什么 JD 里把"建设数仓智能体"和"元数据智能管理""语义层"分开列成不同的职责条目，而不是一句话带过——因为它们是分工不同、但必须协同的三个系统。

## 四、面对"AI+Data"类 JD，怎么组织回答

被问到"你怎么理解 AI 和数仓结合"这类开放性问题时，容易犯的错误是罗列关键词——"我们可以用 Text2SQL，还可以用大模型做数据治理，还可以做智能巡检"，这种回答听起来知道很多概念，但听不出结构。更好的组织方式是按照上面这张架构图的顺序讲：先讲清楚"AI 赋能数仓"不是一个单点技术，而是分布在数据资产层（元数据治理）、翻译层（语义层）、交互层（AgentBI）三个环节的组合能力；再讲清楚这三层是自下而上的依赖关系，越底层的能力越基础但越不直接可见，越上层的能力越直接面向用户但越依赖底层是否扎实；最后可以补一句这三层里"AI 生效的边界"是一致的——都是辅助生成候选、由人工审核确认后生效，这是 [6.19 第 3.5 节](./19-元数据管理与智能数据治理.md) 里已经强调过的原则，也是任何一层被追问"会不会出错、出错了怎么办"时的标准回答框架。

如果被进一步追问某一层的具体技术细节（比如"语义层的 SQL 生成引擎具体怎么做权限过滤"），再切回对应的原始小节展开，不需要在这一节的框架里重复展开细节。

## 五、面试深度剖析

### Q1：数仓智能体（Data Agent）和 AgentBI 是一回事吗？

**答**：本质上是同一套系统的不同叫法，"数仓智能体"更强调它是数仓的能力延伸（治理、ETL、质量），"AgentBI"更强调面向业务用户的查询分析场景，两者共享同一套底层依赖——元数据和语义层。在具体项目里通常不会真的拆成两个系统，而是同一套 Agent 能力，只是暴露给不同用户群体（数据开发者 vs 业务分析师）时的产品形态不同。

### Q2：为什么不能让大模型直接连数据库、跳过语义层和元数据层？

**答**：技术上能跑通一个 Demo，但生产环境会遇到三个问题——口径不统一（不同人问出的"活跃用户"背后 SQL 逻辑可能不一致）、权限失控（大模型生成的 SQL 不经过语义层的行列权限过滤，可能查到不该查的数据）、可维护性差（表结构一变所有 Prompt 都要跟着改，而语义层的抽象可以让物理表变更对上层查询无感）。这也是企业级方案普遍采用"语义层 + LLM"混合模式而不是纯 LLM 直连的核心原因。

### Q3：如果 AgentBI 给出的归因结论是错的，问题可能出在哪一层？

**答**：按照架构图自上而下排查——先看 AgentBI 层的意图识别和任务拆解有没有理解偏差（比如把"环比"理解成了"同比"）；再看语义层的指标口径定义是否和业务预期一致（比如"活跃用户"到底该不该包含测试账号）；最后看元数据层的血缘是否准确（如果归因结论指向了错误的上游表，可能是血缘采集本身有误，参考 [6.19](./19-元数据管理与智能数据治理.md) 里静态解析和运行时采集各自的准确率局限）。这个排查顺序本身也是回答"怎么设计可观测性"这类追问时的一个好素材。
