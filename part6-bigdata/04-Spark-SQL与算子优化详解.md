## 一、先看懂 Spark SQL 的优化链路

### 1.1 逻辑优化、物理优化、运行时优化

Spark SQL 的优化链路可以粗略分成三层：

- **逻辑优化**：重写表达式与语义等价变换
- **物理优化**：选择更合适的物理算子
- **运行时优化**：执行过程中根据真实数据再次调整计划

这三层共同决定最终代价。

### 1.2 CBO、AQE、Hint 分别解决什么问题

- **CBO**：依赖统计信息，在编译期做更合理的代价估算
- **AQE**：在运行时拿到真实统计信息后再优化
- **Hint**：在自动优化不够可靠时给出显式偏好

正确顺序通常是：**先让自动机制尽量发挥，再用 Hint 兜底**。

### 1.3 什么情况下必须看 EXPLAIN

当你怀疑以下问题时，直接看 `EXPLAIN` 更有效：

- Join 策略不符合预期
- 分区裁剪失效
- DPP 没触发
- Hint 没生效
- 写出前分区分布不合理

## 二、JOIN 优化详解

### 2.1 五种物理 JOIN 的适用场景

常见物理 Join 可以按“是否广播、是否依赖排序、是否依赖 hash”来理解。真正实战里不需要死记 API 名称，而要记住它们在数据规模、排序成本、内存占用上的差异。

### 2.2 Broadcast Join 什么时候最值

Broadcast Join 的核心优势是：把小表广播到各 Executor，本地完成匹配，避免大表再次 Shuffle。它通常适合：

- 一边明显很小
- 小表过滤后变得更小
- 网络广播成本远低于两边 Shuffle 成本

### 2.3 SortMergeJoin 为什么常见

SortMergeJoin 很常见，不是因为它永远最快，而是因为它在大表 Join 场景下通常更稳、更通用。代价是需要排序与 Shuffle，因此一旦排序代价过大或分布不均，就容易成为瓶颈。

### 2.4 AQE 如何动态切换 JOIN 策略

AQE 的典型收益之一，就是在运行时发现一边比预估小得多时，把原先的 SortMergeJoin 改成 Broadcast Join。这个变化对性能帮助经常很大，但前提是：Spark 必须在合适的物化点拿到足够可信的真实数据量。

### 2.5 Hint 什么时候是兜底，什么时候会适得其反

Hint 适合在以下场景使用：

- 统计信息不准
- 计划稳定性优先
- 已经明确知道某种 Join 更合适

Hint 不适合在“根因还没看清”时乱用，否则你可能只是把错误计划强行固定下来。

### 2.6 统计信息不准时会发生什么

统计信息不准会直接影响：

- Join 策略选择
- 分区数预估
- CBO 的重排能力

所以很多“Spark 没自动优化好”的场景，根因并不是 Spark 太笨，而是它拿到的信息本来就不靠谱。

## 三、分区裁剪与过滤下推

### 3.1 分区裁剪、列裁剪、谓词下推的区别

三者都在做“少读数据”，但作用点不同：

- **分区裁剪**：少读哪些分区
- **列裁剪**：少读哪些列
- **谓词下推**：把过滤尽量下沉到数据源

### 3.2 静态分区裁剪失效的典型场景

常见失效场景包括：

- 分区字段被函数包裹
- 隐式类型转换
- 过滤条件写法让优化器难以识别
- 查询层太深导致物理分区字段没有自然透出

### 3.3 动态分区裁剪（DPP）的原理与收益

DPP（Dynamic Partition Pruning）是 Spark 3.x 很值得单独掌握的能力。它解决的问题是：维表先过滤后，能否把这些过滤结果动态传回事实表扫描阶段，从而减少事实表分区读取。

它最适合：

- 星型模型
- 维表过滤明显缩小候选 key 集合
- 事实表按相关字段分区

### 3.4 如何从 EXPLAIN / PartitionFilters 判断是否生效

建议重点看：

- `PartitionFilters`
- `dynamicpruningexpression`
- 物理计划里是否真的出现了动态裁剪表达式

如果计划里没有这些痕迹，那就不要假设 DPP 已经帮你做了优化。

## 四、窗口函数与聚合优化

### 4.1 窗口函数的语义与执行代价

窗口函数最大的价值是“既保留明细，又做分组内计算”，但代价往往来自：

- 分区内排序
- 大量明细保留
- 多个窗口定义带来的重复扫描

### 4.2 常见窗口函数与典型误用

常见误用包括：

- 只是想要聚合结果，却用了窗口函数
- 分区键选择不合理，造成超大分区
- 对多列排序但业务上其实没必要

### 4.3 窗口优化的思路

优化顺序通常是：

1. 先看是否能改写成聚合或 Join
2. 再看窗口定义是否能合并
3. 再看分区键和排序列是否过重

### 4.4 什么时候可以改写成聚合或 JOIN

如果业务上不需要保留每一行的上下文，只需要组级结果，那么很多窗口逻辑都可以改写成聚合；如果只是要把组级指标补回明细，也可以考虑先聚合再 Join 回去。

## 五、CTE、子查询与重复计算

### 5.1 WITH / CTE 为什么可能不会复用

CTE 的主要作用是可读性，而不是天然的执行优化。某些查询里，同一个 CTE 被引用多次，并不意味着 Spark 一定帮你复用中间结果。

### 5.2 子查询的常见代价

子查询的问题通常不在“它是子查询”，而在：

- 让过滤难以下推
- 让计划层次过深
- 让重复计算更不容易被发现

### 5.3 中间结果缓存的适用条件

缓存适合在“中间结果足够贵、被复用足够多次、体量又可控”的场景。如果只是单次使用，或者缓存后反而增加内存压力，那收益往往不明显。

## 六、算子级优化

### 6.1 reduceByKey vs groupByKey

这是 Spark 面试和实战里都很经典的一个点。核心不在“一个 API 好、一个 API 坏”，而在：

- `reduceByKey` 可以更早做 map-side combine
- `groupByKey` 更容易把大量数据原样推到下游

只要业务允许提前聚合，通常就优先考虑 `reduceByKey` 类路径。

### 6.2 map-side combine 的意义

map-side combine 的本质就是：**尽量在数据还没真正跨网络之前，就先把能缩的缩掉。**

### 6.3 聚合、排序、去重的代价差异

这三类操作都可能引发 Shuffle，但代价侧重点不一样：

- 聚合看分布与聚合函数
- 排序看数据规模和排序键
- 去重看基数与分区数

### 6.4 cache vs persist 的正确姿势

缓存不是越早越好，而是要看：

- 是否真的复用
- 复用次数是否足够多
- 选择的存储级别是否适合当前资源条件

## 七、小文件与输出分布控制

### 7.1 coalesce / repartition / repartitionByRange 的区别

- `coalesce`：更偏向减少分区，代价较小，但不保证全局均匀
- `repartition`：显式重分布，代价更高，但通常更均匀
- `repartitionByRange`：更适合需要范围有序或按值域分布的场景

### 7.2 REBALANCE 的适用场景

`REBALANCE` 更适合“写出前最后一公里”的重新均衡：

- 你不只是想减少文件数
- 还想避免个别分区过大或过小
- 你关心输出文件与业务分布的平衡

### 7.3 AQE 自动合并为什么不总是够用

AQE 自动合并解决的是“过多小分区”的一部分问题，但它不理解你的业务写出目标，也不保证文件大小、业务 key 分布、资源效率三者同时满足。

### 7.4 输出文件数与分区分布如何统一考虑

最终要同时考虑三件事：

- 下游想读多少文件
- 上游数据是否均匀
- 当前集群资源是否允许你显式再做一次重分布

这也是为什么在现代 Spark 里，“小文件治理”不该只剩一句 `coalesce(1)`。
