# 6.4 Spark SQL 与算子优化详解

> 适用场景：想系统理解 Spark SQL 的执行代价，而不是只记优化口诀；需要知道 Explain、Join、DPP、输出分布该怎么判断

## 一、先明确：这篇文档的角色是“看懂执行计划，判断 SQL 是否走对路”

Spark SQL 优化最容易学成两种极端：

- 只背概念，不会看计划；
- 只背参数，不会判断主矛盾。

这篇文档的任务不是把所有算子都介绍一遍，而是教你建立一条更有实践性的路径：

> **先看逻辑计划和物理计划，再判断 Join、DPP、窗口、CTE、输出分布到底有没有走对路。**

所以这篇文档里，最重要的关键词不是“某个函数名”，而是：

- Explain；
- Join 选择；
- DPP 验证；
- REBALANCE 的工程语境；
- 哪些 SQL 写法会把计划带偏。

## 二、先建立 Spark SQL 的优化链路脑图

### 2.1 逻辑优化、物理优化、运行时优化分别在做什么

Spark SQL 的优化链路可以粗略分成三层：

- **逻辑优化**：在语义等价前提下重写表达式和查询结构；
- **物理优化**：选择更合适的执行算子和分布方式；
- **运行时优化**：执行过程中根据真实统计信息继续纠偏。

这三层共同决定最终代价，所以“SQL 写得出来”和“SQL 跑得对”中间隔着完整的一套执行系统。

### 2.2 CBO、AQE、Hint 分别在解决什么问题

这三个词很容易混，但职责不同：

- **CBO**：用统计信息在编译期做更合理的代价估算；
- **AQE**：执行中拿到真实统计信息后继续调整计划；
- **Hint**：当自动机制不够稳定时，显式给出偏好。

一个更成熟的顺序应该是：

> **先让自动机制尽量发挥，再在必要时用 Hint 兜底。**

### 2.3 为什么 Explain 是这篇文档的真正入口

很多 Spark SQL 争论，如果不看 Explain，本质上都是猜：

- Join 到底选成了什么；
- 分区裁剪到底有没有发生；
- DPP 到底有没有触发；
- 写出前到底有没有重新分布；
- Hint 到底有没有被采纳。

所以这篇文档的第一原则是：

> **当你怀疑 SQL 没走对路时，先去看计划，而不是先调参数。**

## 三、Explain 该怎么用：不是为了“看着高级”，而是为了判断有没有走偏

### 3.1 哪些问题必须先看 Explain

以下情况建议直接看 Explain：

- Join 策略和你预期不一致；
- 分区裁剪效果存疑；
- DPP 是否生效拿不准；
- Hint 怀疑没生效；
- 写出前分区分布为什么这么奇怪。

这类问题如果不看计划，往往就会在错误层面盲调。

### 3.2 看 Explain 时最值得优先盯什么

对大多数实战问题，优先看这些信息：

- 是否有 `Exchange`；
- Join 被选成了什么；
- `PartitionFilters` 是否存在；
- 有没有 `dynamicpruningexpression(...)`；
- 写出前有没有额外重分布；
- Hint 有没有体现在最终物理计划里。

你不需要一开始就把整棵树全部背下来，但至少要抓住这些“是否走偏”的关键证据。

### 3.3 Explain 真正帮助你判断的是什么

它不是为了炫技，而是为了回答下面几个关键问题：

- Spark 有没有少扫数据；
- Spark 有没有少做无效 Shuffle；
- Spark 有没有选对 Join 路径；
- Spark 有没有在写出前把分布整理好；
- 你手工给的 Hint 是不是正在掩盖更早层的问题。

## 四、Join 优化：真正要学的是判断流程，而不是物理 Join 名词列表

### 4.1 Join 优化的更合理顺序

很多人学 Join，只记住了几个物理 Join 名字。但真正实战里，更合理的顺序通常是：

1. 统计信息是否可信；
2. 一边是否足够小到可以广播；
3. 过滤能否进一步前推，减少 Join 输入；
4. 是否已经发生不必要的 Shuffle；
5. 最后才考虑是否用 Hint 兜底。

也就是说，**Join 优化首先是“判断流程”，其次才是“算子名词”。**

### 4.2 Broadcast Join 什么时候最有价值

Broadcast Join 的核心收益在于：

- 把小表广播到各 Executor；
- 避免大表再次做高成本双边 Shuffle；
- 让很多本来会变成重型 Join 的路径直接变轻。

它通常更适合：

- 一边明显很小；
- 小表经过过滤后更小；
- 广播成本远低于双边 Shuffle 成本。

### 4.3 SortMergeJoin 为什么常见，但不该被神化

SortMergeJoin 很常见，不是因为它永远最快，而是因为它对大表 Join 通常更稳、更通用。它的问题也同样明显：

- 需要排序；
- 需要 Shuffle；
- 一旦分布不均或排序代价过大，就很容易成为主瓶颈。

所以看到 SortMergeJoin，不应该自动高兴，也不该自动恐慌，而要看：它是不是当前输入规模下合理的折中。

### 4.4 AQE 动态切换 Join 策略，真正说明了什么

AQE 能在运行时根据真实统计信息，把某些原本估错的 Join 调整成更合适路径。例如：

- 原先以为一边不小；
- 跑起来才发现其实已经小到适合广播；
- 于是 Join 路径动态变轻。

这说明现代 Spark SQL 的主线，已经不再只是“编译期拍一次板”，而是“运行时继续纠偏”。

### 4.5 Hint 什么时候值得用，什么时候会适得其反

Hint 适合：

- 统计信息不准；
- 计划稳定性优先；
- 你已经很确定某种 Join 更合适。

Hint 不适合：

- 根因还没搞清；
- 只是想把 Explain 里不喜欢的节点“压掉”；
- 本来是扫描层、裁剪层、输入结构层的问题，却强行在 Join 层救火。

## 五、少扫数据：这才是很多 Spark SQL 优化最该优先看的主线

### 5.1 分区裁剪、列裁剪、谓词下推的区别

三者都在做“少读数据”，但层次不同：

- **分区裁剪**：少读哪些分区；
- **列裁剪**：少读哪些列；
- **谓词下推**：把过滤尽量下沉到数据源。

真正成熟的 SQL 优化，往往首先体现在这三层是否起作用。

### 5.2 静态分区裁剪为什么经常意外失效

常见失效场景包括：

- 分区字段被函数包裹；
- 隐式类型转换；
- 查询层次过深，让物理分区字段不容易透出；
- 过滤写法让优化器难以识别。

所以“我明明写了 where 条件”不等于“Spark 就一定少读了数据”。

### 5.3 DPP 的真正价值是什么

动态分区裁剪（DPP）的价值，不是“多了个高级特性”这么简单，而是：

> **维表已经过滤得很小了，Spark 能不能把这个信息动态传回事实表扫描阶段。**

这件事一旦成立，少扫数据的收益往往会很直接。

### 5.4 DPP 最适合什么场景

通常更适合：

- 星型模型；
- 维表过滤明显收缩候选 key；
- 事实表按相关字段分区；
- 你真的想减少事实表分区扫描。

### 5.5 DPP 的验证路径应该怎么走

这部分必须讲得非常实用。判断 DPP 是否生效，优先按下面顺序看：

1. **看 `PartitionFilters`** —— 是否出现了动态裁剪相关过滤；
2. **看 `dynamicpruningexpression(...)`** —— 这是非常关键的直接证据；
3. **看过滤后的维表是否真的成为裁剪输入；**
4. **看事实表扫描是否真的因此被约束。**

也就是说，DPP 不能靠“感觉像触发了”来判断。

### 5.6 为什么有 Join 也不一定触发 DPP

这点很关键。以下情况都可能让 DPP 不能自然发挥：

- Join 结构不适合；
- 分区设计和 Join key 不匹配；
- 过滤选择性不够；
- 广播复用条件不足；
- 计划最终没形成适合动态裁剪的路径。

所以更成熟的说法不是“有 Join 就有 DPP”，而是：

> **有 Join 只是前提之一，是否触发还取决于计划形态、分区设计和过滤条件。**

## 六、窗口函数、CTE、重复计算：这些不是语法问题，而是代价问题

### 6.1 窗口函数真正贵在哪里

窗口函数的价值是“既保留明细，又做分组内计算”，但代价往往来自：

- 分区内排序；
- 大量明细保留；
- 多个窗口定义重复扫描 / 重复排序。

这类问题最容易被误判成“机器不够”，其实很多时候是 SQL 路径本身就很重。

### 6.2 窗口优化的更合理顺序

通常先按下面顺序判断：

1. 是否其实可以改写成聚合；
2. 是否只是想把组级指标回填，可以先聚合再 Join；
3. 分区键是不是导致超大分区；
4. 排序列是不是明显过重。

### 6.3 CTE 为什么经常给人“看起来复用了，其实没有”的错觉

CTE 的主要价值是可读性，不等于天然物化复用。也就是说：

- 同一个 CTE 被写了多次引用；
- 不代表 Spark 一定帮你缓存或复用它；
- 很多时候它只是把重复逻辑写得更优雅。

所以当计划很重时，CTE 不是自动减负器，而是你必须再次确认是否真的复用了中间结果。

### 6.4 子查询和深层嵌套为什么也值得警惕

问题不在“它是子查询”，而在：

- 过滤更难下推；
- 计划层次更难看懂；
- 重复计算更不容易被发现；
- 物理路径更容易偏离你的直觉。

## 七、输出分布控制：为什么现代 Spark 不该只剩一句 `coalesce(1)`

### 7.1 `coalesce`、`repartition`、`repartitionByRange` 解决的是不同问题

可以这样理解：

- `coalesce`：偏向减少分区，成本较低，但不保证全局均匀；
- `repartition`：显式重分布，成本更高，但控制更强；
- `repartitionByRange`：更适合需要范围有序或按值域重整分布的场景。

所以这几个 API 不是“一个强一个弱”，而是各自服务不同目标。

### 7.2 为什么 `REBALANCE` 比很多旧经验更现代

`REBALANCE` 值得单独掌握，不是因为它神奇，而是因为它更符合现代写出前控制的真实目标：

- 你不只想让文件数变少；
- 你还想避免个别分区过大或过小；
- 你关心输出文件布局和业务分布的平衡；
- 你希望写出前最后一公里更像“重新整形”，而不只是“机械压缩”。

这就是为什么它在工程语境里，通常比“直接 coalesce 一下”更现代。

### 7.3 AQE auto-coalesce 为什么不能替代输出控制

AQE 自动合并可以帮你减少碎 task，但它并不理解：

- 你的最终文件大小目标；
- 下游想读多少文件；
- 业务 key 分布是否均匀；
- 是否需要范围重整或按值域布局。

所以更准确的理解是：

- AQE auto-coalesce 更像执行中自动收口；
- `REBALANCE` / `repartition` 更像你显式定义最终输出形态。

### 7.4 写出前到底该怎样统一考虑文件数和分布

最终至少要同时看三件事：

- 下游想读多少文件；
- 上游数据是不是已经偏斜或不均；
- 当前集群是否还能承受一次显式重分布。

也因此，小文件问题本质上不是“文件系统问题”，而是执行计划与输出分布设计问题。

## 八、最后总结：这篇 SQL 文真正要教会你的是什么

这篇文档最重要的，不是让你背更多算子名，而是让你建立下面这套路径：

1. **先看 Explain，判断有没有走偏；**
2. **Join 优化先走判断流程，而不是先背物理 Join 名字；**
3. **DPP 是否生效必须看 `PartitionFilters` 和 `dynamicpruningexpression(...)`；**
4. **窗口、CTE、子查询都要从“代价”而不是“语法”角度理解；**
5. **输出分布控制要把 `REBALANCE` 放进现代工程语境，而不是只剩 `coalesce(1)`。**

如果你建立了这套心智，那么面对一条慢 SQL 时，你就不会只会问：

> “这个 Hint 要不要加？”

而会先问：

> “这条 SQL 的执行计划到底哪里走偏了，我应该先修少扫数据、Join 路径，还是写出分布控制？”
