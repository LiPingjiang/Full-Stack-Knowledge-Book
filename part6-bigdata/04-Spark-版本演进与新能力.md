## 一、看 Spark 演进，别只背版本号

很多人学习 Spark 演进，习惯按版本号背诵：

- 3.0 新增了什么；
- 3.2 默认变了什么；
- 3.4 又出了什么；
- 4.x 值得关注什么。

这种记法不能说错，但很容易碎。更好的方法是按 **能力演进线** 去理解：

1. **执行优化能力怎么变强了；**
2. **少扫数据、少错判的 SQL 能力怎么成熟了；**
3. **客户端与使用模型怎么从“嵌入式”走向“服务化”；**
4. **运行环境怎么越来越云原生、越来越平台化。**

这样看，你会更容易理解为什么很多旧经验在今天已经不再是最佳实践。

## 二、第一条演进线：执行优化从“事前估算”走向“运行时纠偏”

### 2.1 早期主线：先拍参数、再看结果

早期很多团队调 Spark SQL，思路往往比较朴素：

- 先手动设 `spark.sql.shuffle.partitions`；
- 看是否该广播小表；
- 看 SQL 写法有没有明显问题；
- 如果慢，再继续试参数。

这套思路在当年并不是错的，因为 Spark 在很多阶段确实更依赖编译期计划和人工经验。但它有一个天然问题：**编译期看到的世界，经常和运行时不一样。**

例如：

- 过滤后数据量比预估小很多；
- 数据分布跟统计信息不一致；
- 某些分区特别碎；
- 某些 key 比预想更热。

于是，“只靠事前拍参数”逐渐变成不够稳的路径。

### 2.2 AQE 的意义：Spark 开始具备运行时再优化能力

AQE（Adaptive Query Execution）是 Spark 3.x 最重要的演进之一。它不是一个零散功能，而是一个方向变化：

> **Spark 不再只在执行前做一次计划，而是能在运行中根据真实统计信息继续优化后续计划。**

这条演进线非常关键，因为它改变了调优方法论。今天遇到 SQL 慢，已经不该只问：

- `shuffle.partitions` 设多少？
- 需不需要手工 repartition？

而是还要问：

- AQE 有没有启用；
- 运行时统计信息有没有让计划得到修正；
- 默认自动能力是否已经足够；
- 哪些地方仍需要手工干预。

### 2.3 AQE 具体把哪些事做得更现代了

AQE 常见收益主要体现在三类场景：

- **自动合并 post-shuffle 小分区**，减少大量碎 task；
- **运行时动态切换部分 Join 策略**，例如发现一边数据量比预估小很多时，选择更合适路径；
- **缓解部分倾斜 Join 问题**，让极端分区不至于完全拖死尾部。

这意味着今天的 Spark SQL 调优，已经从“完全手工参数主义”进入“自动优化优先、人工兜底修正”的阶段。

### 2.4 但 AQE 不是“自动驾驶”

Spark 版本演进里一个很容易被讲歪的点，就是把 AQE 夸成万能机制。更准确的说法应该是：

- AQE 很重要；
- 但 AQE 只能在执行中某些拿到真实统计信息的节点后介入；
- 它解决不了前面 SQL 写法、数据读取、业务写出目标、内存模型等所有问题。

尤其在自动合并分区这件事上，官方文档明确说明了它并不是强保证式“自动定型”。例如：

- `spark.sql.adaptive.enabled` 自 Spark 3.2 起默认开启；
- `spark.sql.adaptive.coalescePartitions.enabled` 控制 post-shuffle 分区合并；
- `spark.sql.adaptive.advisoryPartitionSizeInBytes` 是 **advisory** 目标，不是绝对承诺；
- 默认 `spark.sql.adaptive.coalescePartitions.parallelismFirst=true` 时，Spark 会优先考虑并行度，而不是严格服从目标分区大小。

所以这条演进线真正告诉我们的是：**Spark 会自动帮你纠偏，但不会替你思考业务目标。**

### 2.5 这条演进线对今天的学习重点意味着什么

今天学习 Spark SQL，不应该再把“调 `shuffle.partitions`”当成唯一主线。更合理的认知顺序应是：

1. 先理解 SQL 写法与数据量控制；
2. 再理解 Join / Shuffle / 倾斜；
3. 再理解 AQE 如何在运行时做纠偏；
4. 最后才是一些参数级微调。

换句话说，**AQE 让 Spark 更现代，但也让学习者更需要建立边界感。**

## 三、第二条演进线：SQL 优化从“少调参数”走向“少扫数据、少误判”

### 3.1 旧经验为什么不够了

早期很多 Spark 优化文章会把重心放在：

- `shuffle.partitions`；
- cache / persist；
- Broadcast Hint；
- repartition / coalesce。

这些当然仍然重要，但它们主要集中在“**计算已经开始以后怎么少走弯路**”。而现代 Spark SQL 的一个明显变化是：

> **越来越重视在“读入之前和读入之时”就少扫数据、少做无用计算。**

这也是为什么今天分区裁剪、列裁剪、谓词下推、统计信息、DPP 会变得更重要。

### 3.2 DPP 的意义：把维表过滤真正传回事实表扫描

DPP（Dynamic Partition Pruning）是这条演进线里的代表能力。它解决的问题不是“Join 更快一点”这么简单，而是：

> **维表已经过滤得很小了，为什么事实表扫描还像没看见一样全扫？**

DPP 的价值就在于，把维表过滤结果动态传回事实表扫描阶段，让事实表分区读取更少。

这件事在星型模型、分区设计合理的数仓查询里，收益往往很直接。

### 3.3 DPP 为什么代表的是“现代 SQL 优化思路”

因为它把优化重点前移了。以前很多调优讨论默认接受“先把事实表扫上来，再说”；而 DPP 的思路是：

- 如果能少读，就先少读；
- 如果过滤已经在维表发生，就应该争取把这个信息尽早传到事实表；
- 优化不是只靠执行后半段的 Shuffle 调整，而是要尽早在扫描入口止损。

这就是为什么今天讲 Spark SQL 优化，不能只讲 Join 类型，还得讲 **少扫数据的能力线**。

### 3.4 但 DPP 也不是“有 Join 就一定触发”

DPP 的表述同样很容易被夸大。更准确的说法是：

- `spark.sql.optimizer.dynamicPartitionPruning.enabled` 默认是开启的；
- 但是否触发，跟 Join 结构、分区设计、过滤选择性、是否能复用 broadcast 等因素有关；
- 官方配置里还有 `reuseBroadcastOnly=true` 这类限制条件，意味着它并不是任意场景都无成本启动。

所以今天判断 DPP 是否生效，不能靠“我觉得应该有”，而要去看物理计划中的：

- `PartitionFilters`
- `dynamicpruningexpression(...)`

这也说明现代 Spark 学习正在从“背功能名”走向“验证执行证据”。

### 3.5 REBALANCE：小文件治理和输出分布控制也变得更现代

另一个容易被忽略的变化，是写出前最后一公里的处理方式在升级。

以前很多经验会把小文件治理简单写成：

- `coalesce(n)`；
- 或者再粗暴一点，`coalesce(1)`。

今天这种写法已经明显不够成熟。因为真实目标通常不只是“文件更少”，而是要同时兼顾：

- 文件数量；
- 文件大小；
- 分区均衡；
- 下游读取效率；
- 业务 key 的分布。

所以现代 Spark 语境里，`REBALANCE` 这类能力更像是在告诉你：**输出控制不再只是机械压缩分区数，而是更关注重新均衡。**

当然，这也不该被讲成“REBALANCE 一定优于所有老方法”。更准确的说法是：它更适合“写出前重新整理分布”的场景，前提是你理解自己的写出目标，而且它依赖 AQE 语境。

## 四、第三条演进线：Spark 的使用方式从“嵌入式客户端”走向“服务化客户端”

### 4.1 早期默认心智：客户端和运行环境更强耦合

很长一段时间里，大家对 Spark 的使用心智更接近：

- 在某个客户端环境里发起 Spark 会话；
- 客户端和 Spark 运行环境之间耦合较强；
- 不同语言、IDE、Notebook、平台接入时，经常要自己处理很多本地依赖和环境问题。

这并不意味着 Spark 不能远程用，而是说它的主流使用体验并不天然强调“解耦式服务化接入”。

### 4.2 Spark Connect 的意义：不是多一个协议，而是多一种使用模型

Spark Connect 是 Spark 3.4 引入的一个很关键的新能力。官方给出的核心描述是：

- 它是 **decoupled client-server architecture**；
- 允许客户端远程连接 Spark 集群；
- 以 DataFrame API 和 unresolved logical plans 作为交互协议；
- 适合嵌入 IDE、Notebook、多语言客户端和应用程序。

所以 Spark Connect 的意义，不应该只被理解为“多了个远程接口”，而应该理解为：

> **Spark 正在从“你来靠近运行时”转向“运行时作为服务能力被接入”。**

### 4.3 这会带来什么认知变化

它至少带来三种变化：

- **平台化更自然。** 数据平台、交互分析平台、Notebook 系统更容易把 Spark 作为后端能力承载；
- **客户端更轻。** 不再要求每个客户端都和完整 Spark 运行环境强绑定；
- **多语言与工具集成更顺。** IDE、脚本、应用可以更自然地通过远端服务使用 Spark。

从文章结构角度看，这类能力不适合被写成“一个孤立新功能”，因为它改变的是 **使用模式**。

### 4.4 但它还不等于“传统提交方式过时了”

成熟的表述也必须讲边界：

- Spark Connect 很重要；
- 但传统提交方式、批处理作业链路、既有平台体系依然长期存在；
- 对很多团队来说，它首先是“值得关注的新方向”，而不是“所有基础学习都要立刻重写”。

所以在教学上，Spark Connect 更适合被放在“版本演进与新能力”专题里，作为现代使用模型的认知升级，而不是塞回主线基础章节里占据过高比重。

## 五、第四条演进线：运行环境从传统资源管理走向云原生与弹性回收

### 5.1 Spark 运行环境的重点已经不只是 YARN

过去谈 Spark 部署，很多默认背景是 YARN；今天情况明显变了。越来越多团队会在容器环境和平台环境里运行 Spark，这意味着：

- 资源治理方式变化了；
- 日志入口变化了；
- 本地盘生命周期变化了；
- 节点下线和资源回收语义变化了；
- 排障视角也随之变化。

所以“运行环境演进”不只是部署姿势变化，而是整个运维与排障模型在变化。

### 5.2 Kubernetes 支持增强，说明 Spark 在适应现代平台环境

Kubernetes 不是简单的“另一种提交命令”，它代表的是 Spark 对现代平台环境的适配能力在增强：

- 更自然地接入容器化资源池；
- 更容易融入统一平台治理；
- 更适合弹性与多租户场景；
- 更容易与云原生基础设施能力结合。

因此今天讲 Spark 运行，不再适合把 Kubernetes 仅仅当成“部署补充阅读”。它已经是 Spark 运行方式演进里非常重要的一条线。

### 5.3 Decommission 为什么变重要

当环境开始大量使用弹性伸缩、抢占式实例、自动回收节点时，节点并不会总是“稳定在线直到任务自然结束”。这时就会引出一个更现代的问题：

> **节点要下线时，Spark 能不能更优雅地迁移、回收和保留必要状态，而不是粗暴中断？**

Decommission 之类能力的意义就在这里。它体现的不是“又多了个参数”，而是 Spark 在适应 **不稳定但更弹性的基础设施环境**。

### 5.4 这条演进线对工程实践的提醒

今天学习 Spark 部署与运行时，不该再只记：

- 怎么提一个作业；
- 怎么配几个 executor；
- 怎么看 YARN 页面。

还要知道：

- 不同资源管理器下日志怎么取证；
- 本地盘与 Shuffle 文件生命周期有什么差异；
- 节点回收、资源弹性对运行时行为有什么影响；
- 为什么现代 Spark 运维越来越接近平台工程问题。

## 六、Spark 4.x：应该怎么关注，而不是怎么神化

### 6.1 4.x 值得关注的，不是“背新名词”，而是看方向

对于大多数读者来说，Spark 4.x 更适合作为“前沿观察窗口”，而不是立刻塞进主线基础的必修清单。更值得关注的是方向：

- 更强的声明式与 SQL 化能力；
- 更服务化的客户端接入；
- 更贴近现代平台与数据工程工作流的组织方式。

### 6.2 Declarative Pipelines 这类方向说明了什么

像 Declarative Pipelines 这类能力，提示的是 Spark 正在朝着更现代的数据工程表达方式靠近。它的意义更像：

- Spark 不再只是一台执行引擎；
- 它也在尝试承载更高层的数据工程组织方式；
- 未来的数据平台和 Spark 之间可能会有更紧密的声明式接口。

但这类内容目前更适合放在“值得关注”层，而不是“基础面试必会”层。

### 6.3 哪些是今天必须学扎实的，哪些是先建立认知就够了

如果面向当前主流生产实践，优先级大致应该是：

**必须学扎实：**

- Spark 执行模型；
- Shuffle / Join / 倾斜 / 内存；
- AQE；
- DPP；
- Kubernetes 等运行差异的基本认知。

**先建立认知即可：**

- Spark Connect 对使用模型的改变；
- 4.x 的声明式方向；
- 更前沿的平台化能力演进。

这也是这篇文章的核心态度：**既要现代，又不能把“新”误写成“主线基础”。**

## 七、最后总结：Spark 这些年到底变了什么

如果只用一句话概括 Spark 这些年的演进，可以这样说：

> **Spark 正在从“靠开发者手工拍参数的分布式计算框架”，逐渐演进为“更能运行时纠偏、更重视少扫数据、更适合服务化接入、更能适应云原生平台环境的数据处理引擎”。**

因此今天再学 Spark，不能只记老口诀，也不能只追新名词。真正成熟的学习顺序应该是：

1. 主线原理先扎实；
2. 现代能力线要补齐；
3. 每个新能力都要同时知道它的价值和边界；
4. 把它们放回真实工程语境里理解。

这样你看到的就不再是一串版本号，而是一条很清晰的能力演进线。
