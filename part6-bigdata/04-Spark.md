## 一、为什么今天还要系统学 Spark

Spark 之所以重要，不是因为它只是“比 MapReduce 更新的一个框架”，而是因为它把下面几件事放到了同一套引擎里：

- 批处理；
- SQL 分析；
- 迭代计算；
- 统一的执行模型；
- 更现代的运行时优化能力。

也因此，今天学 Spark 不能再只学：

- RDD 是什么；
- 有哪些算子；
- `spark-submit` 怎么写。

更重要的是建立一张完整脑图：

1. **Spark 为什么常常比旧路径更快；**
2. **一段代码是怎样从逻辑描述变成集群执行的；**
3. **为什么今天大多数 Spark 问题其实发生在 SQL、Shuffle、资源与运行环境边界上；**
4. **现代 Spark 和早期 Spark 的主线差别在哪里。**

这篇主文的任务，就是先把这张脑图搭起来。

## 二、为什么 Spark 常常比 MapReduce 快

### 2.1 关键不只是“内存计算”，而是“少做无效边界”

很多人会把 Spark 的优势简单概括成“基于内存”。这句话不算错，但太不完整。更准确的理解是：

> **Spark 会尽量把一串可以连续执行的计算组织成 DAG，在必要的边界才切 stage、做 Shuffle、写中间结果。**

也就是说，Spark 的优势来自几件事叠加：

- 尽量减少不必要的中间落盘；
- 多个 transformation 可以按 DAG 连续执行；
- SQL 层还有 Catalyst、CBO、AQE 这类优化能力；
- 缓存、广播、运行时优化都让“重复工作”更少。

### 2.2 Spark 快的典型语境

Spark 的优势最容易体现在这些场景里：

- 多步 ETL；
- 多轮迭代计算；
- 同一份数据要被多次复用；
- SQL 计划可以明显受益于 Catalyst / AQE / DPP；
- 需要统一批处理和分析路径。

所以 Spark 快，不只是“磁盘变少了”，而是“重复启动、重复落盘、重复计算、低效执行路径都尽量减少了”。

### 2.3 Spark 快也有边界

Spark 不是天然无敌。以下情况里，它的优势会明显下降：

- 扫描量本身就失控；
- Shuffle 非常重，网络和磁盘成为主瓶颈；
- 数据倾斜严重，少数 task 拖死全局；
- 任务大量 Spill，已经远离“内存友好路径”；
- SQL 写法本身把执行计划带偏。

所以一句更成熟的总结是：

> **Spark 快，不是因为“永远在内存里”，而是因为它把“少落盘、少重复、少无效计算”做成了默认方向。**

## 三、先建立 Spark 的运行时心智模型

### 3.1 从代码到集群执行，中间会经过哪些层

无论你写的是 RDD、DataFrame 还是 SQL，Spark 都不是“看到一行代码就立刻执行”。更接近真实的过程是：

1. 先描述计算逻辑；
2. 再形成依赖关系和执行计划；
3. 再根据宽依赖切出 stage；
4. 再把 stage 拆成 task；
5. 最后把 task 派到集群中执行。

所以 Spark 的核心不是某个 API，而是：

> **它如何把逻辑表达，变成带有分区、依赖、Shuffle 和资源调度的执行过程。**

### 3.2 RDD 为什么仍然值得理解

今天大多数业务已经不直接用裸 RDD 写主逻辑，但 RDD 依然重要，因为它让你理解 Spark 的三个底层事实：

- 数据是按分区组织的；
- 计算是沿依赖关系推进的；
- 容错主要依赖 lineage 重算，而不是默认靠副本恢复。

也就是说，RDD 不是只教你 API，而是在教你 Spark 的设计哲学。

### 3.3 Transformation、Action、宽依赖、窄依赖为什么重要

Spark 执行模型最关键的几个词，必须放在一起理解：

- **Transformation**：描述如何从旧数据派生新数据；
- **Action**：真正触发执行；
- **窄依赖**：通常更容易流水线执行；
- **宽依赖**：通常意味着 Shuffle 和 stage 边界。

其中最关键的是：

> **宽依赖往往决定了哪里会切 stage，而 Shuffle 往往决定了性能是否开始变贵。**

### 3.4 Job、Stage、Task 之间的层级关系

你可以把 Spark 的执行层级理解成：

- **Job**：一次 action 触发的计算目标；
- **Stage**：按 Shuffle 等边界切开的执行段；
- **Task**：落到具体分区上的最小执行单元。

这三个层级几乎能承载你对大多数性能问题的第一层解释：

- Job 太碎，可能是 action 太多；
- Stage 太重，可能是 Shuffle / Join / 排序太贵；
- Task 拖尾，可能是分区不均、倾斜、单 task 过重。

### 3.5 Driver、Executor、Cluster Manager 分别负责什么

再换一个角度，Spark 的运行时还可以按角色理解：

- **Driver**：负责解释逻辑、构建计划、切分 stage、调度 task；
- **Executor**：负责真正执行 task、缓存数据、维护运行时状态；
- **Cluster Manager**：负责资源分配，常见是 YARN、Kubernetes、Standalone。

一句最直观的话是：

> **Driver 决定怎么干，Executor 负责把活干完，Cluster Manager 决定你能拿到多少工人。**

## 四、今天的大多数 Spark 实战，其实发生在 Spark SQL 语境里

### 4.1 为什么主线已经从“RDD API”转向“SQL / DataFrame”

今天的大多数 Spark 生产任务，本质上是 SQL、DataFrame、数据仓库分析和 ETL 问题，而不是“我要手写一个底层 RDD 转换链”。

这意味着学习重点也要变化：

- 主线不再是“背多少算子”；
- 主线变成“理解执行计划、Join、Shuffle、AQE、DPP、输出分布控制”。

### 4.2 Catalyst、CBO、AQE 分别在解决什么

现代 Spark SQL 的优化，不是一个单点能力，而是一条链：

- **Catalyst**：做逻辑与物理计划优化；
- **CBO**：基于统计信息做更合理的代价判断；
- **AQE**：执行中基于真实统计信息继续纠偏。

所以今天说“Spark SQL 很强”，真正指的是：

> **它不仅会在编译前优化，还会在运行时继续优化。**

### 4.3 DPP、REBALANCE 这类能力为什么代表“现代 Spark”

现代 Spark 和早期经验最明显的差别之一，在于优化不再只靠：

- 手工调 `shuffle.partitions`；
- 盲目 `coalesce`；
- 强塞 Hint。

更现代的主线是：

- 在读入阶段尽量少扫数据，例如 DPP；
- 在执行中让 AQE 自动纠偏；
- 在写出前用 `REBALANCE` 等方式更合理地整理输出分布。

但这些能力都不是万能的，它们是“更现代的默认工具”，不是“自动驾驶”。

如果你要系统理解这一层，请直接跳到：

- [Spark SQL 与算子优化详解](./04-Spark-SQL与算子优化详解.md) —— 当你想判断 Join、DPP、Explain、REBALANCE 时看这篇。

## 五、运行环境为什么会改变你对 Spark 的理解

### 5.1 Client 和 Cluster 不只是提交方式不同

提交模式会直接影响：

- Driver 在哪里；
- 日志先去哪里看；
- 提交端挂了会不会影响作业；
- 排障第一入口在哪一层。

所以 client / cluster 不是命令层小差异，而是运行视角差异。

### 5.2 YARN 和 Kubernetes 不只是两个 cluster manager

今天理解 Spark 运行环境，不能只停留在“YARN 和 K8s 都能跑 Spark”。更关键的是它们会改变：

- 日志入口；
- 本地盘生命周期；
- Shuffle 中间结果稳定性；
- 节点回收语义；
- 多租户和弹性资源治理方式。

这也是为什么 Spark on YARN 和 Spark on Kubernetes，不只是提交流程不同，而是两套不同运行语境。

- [Spark 部署与云原生运行](./04-Spark-部署与云原生运行.md) —— 当你关心 YARN / K8s 差异、本地盘、PVC、Decommission 时看这篇。

## 六、Spark 的问题通常可以按四条主线来学

### 6.1 如果你的问题是“为什么慢”

优先沿下面顺序走：

1. 先看扫描量；
2. 再看 SQL 写法和 Join；
3. 再看分区、Shuffle、倾斜；
4. 再看资源和内存；
5. 最后才看细节参数。

对应专题：

- [Spark 性能优化](./04-Spark-性能优化.md) —— 调优总入口，适合先判断主矛盾在哪一层。
- [Spark Shuffle 机制与调优参数](./04-Spark-Shuffle机制与调优参数.md) —— 当你卡在分区、AQE auto-coalesce、REBALANCE、FetchFailed 语境时看这篇。
