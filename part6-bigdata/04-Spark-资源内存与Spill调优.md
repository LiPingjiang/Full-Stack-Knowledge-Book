# 6.4 Spark 资源内存与 Spill 调优

> 适用场景：任务慢、OOM、Spill 过多、资源参数难以理解，或总分不清 Driver / Executor / 容器三层问题

## 一、先明确：这篇文档的角色是“资源诊断文”，不是参数说明书

Spark 资源调优最容易学成两种误区：

- 看到 OOM 就加内存；
- 看到 Spill 就调几个 memory 参数。

这两种做法都可能短期有效，但经常会掩盖主矛盾。因为 Spark 里的“资源问题”，很多时候并不是参数单独失配，而是：

- 分区太粗；
- 单 task 太重；
- SQL 逻辑膨胀；
- 倾斜把少数 task 打爆；
- Driver、Executor、容器三层边界没分清。

所以这篇文档的核心任务不是参数穷举，而是帮你建立一套更稳的分型路径：

> **先区分问题发生在 Driver、Executor，还是容器层；再判断它是资源承载不足，还是执行路径本身就不健康。**

## 二、先建立资源心智模型：CPU、内存、并行度、分区是联动的

### 2.1 为什么这些量不能拆开单独看

Spark 的资源问题从来不是“把 CPU、内存、分区数各调一遍”这么简单。因为它们天然联动：

- 分区数决定 task 粒度；
- task 粒度决定单 task 压力；
- executor.cores 决定一个 executor 同时跑多少 task；
- executor.memory / overhead 决定这些 task 能在多大空间里竞争；
- 集群总 executor 数量决定整体并发上限。

所以一个参数“看起来合理”，不代表整条执行路径就合理。

### 2.2 Executor 是资源容器，task 才是实际消耗者

这是资源调优里特别容易被忽略的一层：

- Executor 是一块资源容器；
- task 才是具体吃 CPU、吃内存、做 Spill、做 Shuffle 的执行单元。

因此你真正该问的问题往往是：

- 一个 executor 同时跑多少 task；
- 每个 task 平均要吃多少内存；
- 这些 task 是 CPU 型、内存型还是 IO 型；
- 单 task 是否已经重到不该靠“再加点内存”来缓解。

### 2.3 为什么“加机器”经常不是第一反应

如果主矛盾是：

- SQL 写法不合理；
- 倾斜严重；
- 输出分布失控；
- 分区过粗；
- collect / toPandas / 广播把压力带回 Driver。

那么加机器通常只会把总成本抬高，而不会把根因拿掉。

## 三、第一层分型：先区分 Driver、Executor、容器三层

### 3.1 Driver 问题：很多时候根因是“把不该集中的东西集中回来了”

Driver 问题最典型的场景包括：

- `collect()` 拉回过多结果；
- `toPandas()` 规模失控；
- 广播对象太大；
- Driver 端做了本该分布式完成的汇总、组装或转换逻辑；
- 计划、元数据或对象本身很重。

这类问题的关键不是“Driver 内存小”，而是：

> **是否把本该分布式处理的负担，重新集中回了单点。**

### 3.2 Executor 问题：最常见的是单 task 太重，而不是总内存天然不够

Executor 问题常见表现包括：

- Executor OOM；
- Spill 很重；
- 排序 / 聚合 / Join 阶段异常慢；
- 少数大 task 把 executor 打爆。

常见根因往往是：

- 分区太少；
- 倾斜严重；
- 聚合 / 排序状态过大；
- 广播 / 反序列化后对象膨胀；
- 多个 task 在同一个 executor 内部竞争太激烈。

### 3.3 容器层问题：它不一定等于 JVM 自己抛 OOM

YARN / Kubernetes 等环境下，你必须额外分清容器层问题。因为这类问题常见表现是：

- 容器被 kill；
- Pod 被系统终止；
- exit code 像 143 这类外部终止信号；
- JVM 堆看起来没明显打满，但进程仍被回收。

这通常意味着：

- 堆外内存消耗大；
- memoryOverhead 不够；
- Python / 本地库 / Netty 等附加开销超出容器边界；
- 系统从“总占用”看已经超限，而不是只看堆。

## 四、第二层分型：先判断是“资源承载不住”，还是“执行路径本来就不健康”

### 4.1 哪些信号说明更像资源承载问题

以下情况更像资源层本身已经成为主矛盾：

- 全局并发明显不足；
- 大量 executor 都在普遍高压；
- 整体吞吐随着 executor 数量变化很敏感；
- 不是少数 task 拖尾，而是整体都被资源边界限制。

### 4.2 哪些信号说明更像执行路径问题伪装成资源问题

以下情况更应优先怀疑执行路径：

- 只有少数 task 特别重；
- OOM 主要集中在某类 stage；
- Spill 伴随明显倾斜或分区过粗；
- collect / 广播 / toPandas 把问题带回 Driver；
- SQL 写法导致中间数据异常膨胀。

这类问题如果直接加资源，通常只是让错误路径更贵。

## 五、Dynamic Allocation：它解决的是弹性，不是计划本身

### 5.1 静态配置的痛点是什么

静态资源配置的问题很典型：

- 高峰时不够用；
- 低峰时浪费明显；
- 多作业共存时很僵硬；
- 容易出现“平均配置看似合理，实际对具体作业不友好”。

### 5.2 Dynamic Allocation 真正解决什么

Dynamic Allocation 解决的是：

- 根据 task 积压动态增减 executor；
- 提高资源池利用率；
- 让低峰和高峰的资源占用更灵活。

一句最准确的话是：

> **它解决的是“有多少工人”，不是“活怎么干最合理”。**

### 5.3 Dynamic Allocation 和 AQE 为什么不能混为一谈

它们经常同时出现，但职责不同：

- **Dynamic Allocation**：决定资源弹性；
- **AQE**：决定运行时计划纠偏。

一个解决“人数”，一个解决“路径”，不能混着讲。

### 5.4 Shuffle Tracking / External Shuffle Service 为什么和资源回收有关

这类机制的关键问题是：

> **executor 被回收后，shuffle 数据还能不能安全被后续阶段读取。**

也就是说，它们不是孤立“资源配置项”，而是直接连着运行时稳定性。

## 六、内存模型：执行内存、存储内存、堆内堆外到底在分什么

### 6.1 执行内存和存储内存分别在支撑什么

最核心的区分是：

- **执行内存**：排序、聚合、Join、Shuffle 等运行期使用；
- **存储内存**：缓存、持久化数据使用。

理解这个区分的意义是：你要知道当前任务更像是在“算的时候吃内存”，还是“存的时候吃内存”。

### 6.2 `memory.fraction` 的意义是什么

`memory.fraction` 影响的是 Spark 统一内存管理里可用的比例。它的关键不在于“越大越好”还是“越小越稳”，而在于：

- 当前任务更偏执行内存还是存储内存；
- 是排序 / 聚合压力大，还是缓存压力大；
- 你的主矛盾是不是已经到了需要动这一层。

如果连任务分型都没做，单独讨论这个参数通常意义不大。

### 6.3 堆内、堆外、统一内存管理为什么要和容器边界一起看

真实环境里，你至少要同时知道三层：

- JVM 堆内空间；
- 堆外和非 JVM 附加开销；
- 容器从外部看到的总内存占用。

这就是为什么很多“堆看起来没爆，但进程还是被 kill”的问题，不能只用 JVM 视角解释。

### 6.4 Task 级内存竞争为什么特别关键

即使一个 executor 总内存看上去够大，也可能因为：

- 同时跑的 task 太多；
- 单 task 负载偏重；
- 排序、聚合、反序列化竞争激烈；
- 同一个 executor 里热点分区扎堆。

最终让 executor 内部竞争先爆掉。

所以资源调优里，“一个 executor 能跑多少 task”常常比“executor.memory 单看有多大”更有解释力。

## 七、Spill：不要把它学成“坏事”或“参数问题”，而要学成诊断信号

### 7.1 Spill 本质上是什么

Spill 可以理解成：

- 内存已经不适合继续完全承载当前运行状态；
- Spark 选择把中间结果部分落到磁盘，以保护执行继续进行。

也就是说，Spill 不是神秘异常，而是执行压力在向你报警。

### 7.2 Spill 是坏事吗

不是。适度 Spill 是 Spark 处理大规模数据时的正常保护机制。

真正值得警惕的是：

- Spill 量异常大；
- 大量 task 持续在 Spill；
- Spill 已经显著拖慢 stage；
- Spill 同时伴随高 GC、低吞吐、长尾 task。

### 7.3 看 Spill 时最重要的不是“有没有”，而是“为什么这么多”

真正该问的是：

- 分区是不是太粗；
- 单 task 是否太重；
- 排序 / 聚合 / Join 是否本来就过大；
- task 并发是不是导致 executor 内部竞争激烈；
- 数据对象是不是异常宽、异常长、异常膨胀。

所以 Spill 不是最终结论，而是你要继续追问根因的信号。

### 7.4 为什么很多 Spill 问题根本不该先调内存参数

因为很多时候主因是：

- 分区没切开；
- 倾斜没处理；
- SQL 写法让中间状态过大；
- 输出前最后阶段负载集中；
- 单行对象异常大。

这类问题如果只调内存参数，通常只是把 Spill 推迟，而不是把问题解决。

## 八、几类高频资源问题，第一反应该怎么分流

### 8.1 Driver OOM：先怀疑 collect / toPandas / 广播，而不是先调 executor

如果问题发生在 Driver，优先看：

- 是否 `collect()` 过多；
- 是否 `toPandas()` 规模失控；
- 广播对象是否过大；
- Driver 是否承接了不该承接的组装逻辑。

这类问题和 executor 参数往往不是同一层。

### 8.2 Executor OOM：先怀疑分区、倾斜、单 task 过重

如果问题在 Executor，优先看：

- 分区是不是太少；
- 是否有明显倾斜；
- 排序 / 聚合 / Join 状态是不是过大；
- 单 task 是否已经远远超出合理粒度。

### 8.3 容器被 kill：先怀疑 overhead 和非堆消耗

如果表现更像被系统回收，优先看：

- memoryOverhead；
- 堆外消耗；
- Python / 本地库；
- 容器总占用而不是只看 JVM 堆。

### 8.4 动态分区写出 OOM：为什么经常是“前面都好好的，最后挂掉”

这类问题往往出现在写出阶段，因为最后一个 stage 可能把压力集中到了：

- 某些输出分区；
- 某些热点 key；
- 某些单 task 写出路径上。

所以它常常不只是“写出接口问题”，而是输出分布设计问题。

### 8.5 大对象、长字符串、超长 JSON 为什么特别容易误导判断

这类任务经常出现一种错觉：

- 行数看起来不大；
- 但任务就是很痛苦；
- Spill、序列化、GC、网络传输都异常重。

根因常常不是“条数多”，而是“对象形态坏”。

## 九、资源调优方法论：为什么常常先改分区 / 逻辑，再谈参数

### 9.1 先降单 task 压力，再考虑加内存

如果问题集中在少数大 task，最优先通常不是加内存，而是：

- 切细分区；
- 处理倾斜；
- 减少中间状态；
- 重写局部逻辑。

因为单 task 本来就太重时，加内存只是在拖延问题暴露。

### 9.2 先看分区与并发关系，再看 executor.cores

`executor.cores` 调高会提升并发，但如果单 task 本来就吃内存，这可能反而让 executor 内部竞争更激烈。

所以 cores 不是越大越好，而要和：

- 分区数；
- 单 task 负载；
- executor memory

一起看。

### 9.3 哪些场景下参数调优收益本来就有限

以下场景里，继续调参数通常收益有限：

- SQL 写法明显不合理；
- 上游扫描量过大；
- 倾斜很严重；
- 输出分布失控；
- collect / 广播 / Driver 侧逻辑本身就错位。

这时更该回到逻辑层，而不是继续堆资源。

## 十、最后总结：这篇资源文真正要教会你的是什么

这篇文档最重要的，不是让你记更多参数，而是建立下面这套分型习惯：

1. **先分 Driver、Executor、容器三层；**
2. **再分资源承载问题，还是执行路径伪装成资源问题；**
3. **把 Spill 看成诊断信号，而不是简单“坏事”；**
4. **优先改分区、单 task 压力和逻辑路径，再考虑细调参数。**

如果你建立了这套心智，那么面对 OOM、Spill、资源异常时，你就不会只会问：

> “这个参数要不要再调大一点？”

而会先问：

> “问题到底发生在哪一层，我现在该先改资源边界，还是先把执行路径修健康？”
