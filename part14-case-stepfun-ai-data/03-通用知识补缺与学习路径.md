# 14.3 通用知识补缺与学习路径：把“数据 sense”练成可验证能力

## 先纠正一个误解：数据判断力不是“经验玄学”

很多人把数据 sense 理解为“看一眼就知道数据好不好”。真正可迁移的数据判断力，是一套可以写成检查表、转成统计指标、经过抽样校验、再用实验验证的工作方式。

面对一批训练样本，至少从五个问题切入：它是真是假，是否与目标任务相关，答案或标签是否可靠，是否增加了新覆盖而非重复已有内容，是否引入隐私、版权、安全或偏见风险。最后还要问第六个问题：为它付出的清洗、标注、训练和推理成本，是否值得。

```mermaid
flowchart LR
    A["业务/能力目标"] --> B["定义样本单元与质量量表"]
    B --> C["自动规则 + 统计剖析"]
    C --> D["分层抽样与人工校验"]
    D --> E["数据版本与受控实验"]
    E --> F["离线评测 + 线上观测"]
    F --> G["保留 / 降权 / 修改规则 / 回滚"]
    G --> B
```

所谓“看一眼”，只是这套闭环已经内化后的快速判断；没有闭环的直觉很容易被样本量、表面流畅度或模型自评分误导。

## 知识缺口一：从 ETL 质量到“训练价值”质量

传统数仓质量强调完整性、唯一性、及时性、一致性和准确性。LLM 数据还要增加任务相关性、知识新颖度、难度分布、多样性、答案可验证性、泄漏风险、偏见与安全风险。一个字段非空、格式正确的网页文本，可能对训练毫无价值；一条回答语言漂亮的 SFT 样本，也可能逻辑错误或在奖励“迎合用户”。

建议先回顾 [6.14 数据质量](../part6-bigdata/14-数据质量.md) 的规则与异常检测框架，再把规则扩展为下面的训练数据质量卡：

| 维度 | 要问的问题 | 可量化信号 | 人工抽检要看什么 |
|---|---|---|---|
| 有效性 | 文件和字段是否可用 | 解析成功率、空文本率、OCR/ASR 置信度 | 内容是否与提取结果相符 |
| 正确性 | 事实、代码、答案是否正确 | 单测通过率、检索证据覆盖、交叉模型分歧 | 推理链是否成立，引用是否支持结论 |
| 相关性 | 是否服务目标能力 | 任务分类命中率、Embedding 相似度、专家打分 | 是否是“看起来像”但实际不需要的样本 |
| 覆盖与多样性 | 是否补上长尾而非重复头部 | 领域/语言/难度熵、簇覆盖、新颖度 | 有无关键任务桶缺失 |
| 安全与合规 | 是否可合法、安全使用 | PII 命中、风险分类、许可证字段完整率 | 是否存在上下文泄露或误杀 |
| 训练收益 | 是否带来净提升 | 消融增益、退化桶、单位增益成本 | 改善是否与预期一致 |

## 知识缺口二：实验设计与统计直觉

“加了一批数据，分数涨了”还不是因果结论。至少要固定模型基座、训练步数/Token 预算、Tokenizer、学习率和评测脚本，只替换一个数据变量；如果同时改数据、改训练配方、改推理参数，任何结论都不可靠。

实践中至少要掌握四种比较：同预算数据配比消融，比较“加入/不加入某类数据”；阈值扫描，比较质量分阈值不同的版本；分桶评测，观察目标能力提升是否以其他桶退化为代价；时间切分或来源切分，防止近重复样本让测试集虚高。

当评测变化很小，还需要报告置信区间或重复运行结果，而不是把随机波动解释成优化。对于生成式评测，最好同时保留确定性指标、人工抽样和经过校准的 LLM-as-a-Judge，避免把单一裁判模型的偏好当成事实。

相关基础见 [7.5 微调入门](../part7-ai-engineering/05-微调入门.md)、[7.7 分布式训练](../part7-ai-engineering/07-分布式训练.md) 和 [7.9 AI 安全与可信](../part7-ai-engineering/09-AI安全与可信.md)。

## 知识缺口三：数据版本、血缘与删除能力

AI 数据项目最容易留下“幽灵版本”：文件夹名写着 `final_v2`，但没人知道里面来自哪些来源、跑过哪些规则、被哪次训练使用。解决它不是再造一个复杂平台，而是给数据版本建立最小的不可变协议：内容哈希、Manifest、加工代码版本、输入快照、质量报告、使用记录和访问审计。

这与 [6.19 元数据管理与智能数据治理](../part6-bigdata/19-元数据管理与智能数据治理.md) 的血缘思想完全一致。区别在于 AI 数据要额外追踪“一个原始样本被哪些数据集、哪些模型训练 run、哪些评测或模型权重间接使用”。当出现授权撤回或隐私删除时，能够给出影响范围比“立刻删文件”更重要。

## 知识缺口四：理解 Agent Trace 是一种新的事实表

传统埋点的一个事件通常能直接映射到页面点击或交易状态。Agent 的一次用户任务则包含多轮推理、工具调用、检索、重试、沙箱和人工/自动评分。只存一行“请求—响应日志”无法解释为什么失败。

先学习 [7.6 Agent 基础](../part7-ai-engineering/06-Agent基础.md) 的工具调用与执行流程，再读 [6.15 平台可观测性](../part6-bigdata/15-平台可观测性.md) 的监控框架。练习时按 `session → trace → span → tool_call` 建模，并始终保存 model/prompt/tool/data/evaluation 的版本维度。这样才能在回归发生时做真正的多维归因。

## 一个四阶段学习与实践路径

### 第一阶段：两周内做一个“可审计的网页数据集”

选一个许可明确的公开网页或文档数据源，不要以绕过网站限制为目标。用 Python 完成正文抽取、语言识别、长度/重复规则、精确去重和 MinHash 近重复检测；输出保留/拒绝原因、来源哈希、处理版本和质量统计。再随机抽取通过与拒绝样本各 50 条，亲自检查误杀和漏放。

验收不是“跑出了 CSV”，而是能回答：某条样本为什么被保留，规则换一个阈值会影响哪些来源，如何重跑同一版本。

### 第二阶段：做一个小型 SFT/评测实验

选择一个规模足够小、合法可用的开源指令数据或分类任务。构造两个只有一个变量不同的数据版本，例如是否加入某领域样本、不同去重阈值或不同答案过滤规则；冻结训练配置和评测集；报告总体指标、分桶指标、失败样本和成本。

这一阶段的目标不是训出更强模型，而是建立“数据版本—实验 run—评测结果”的证据链。

### 第三阶段：构造 Agent Trace 分析项目

用一个简单的工具调用 Agent 或公开 Trace 样例，生成 `session/trace/span/tool_call/evaluation` 五张逻辑表。将 Trace 写入任意本地分析库或 OLAP，完成三类查询：按版本看任务成功率，按工具看失败率和重试次数，按任务类型看 P95 延迟和 Token 成本。再设计一个坏例子：某工具偶发超时，说明如何把它从“总体成功率下降”定位到具体 Span。

### 第四阶段：练习“数据决策备忘录”

每次改规则不要只提交代码，还写一页备忘录：目标是什么，改了什么，影响的数据规模和桶，已知风险是什么，如何验证，失败时怎么回滚。持续三到五次后，数据判断力会从零散技巧变成可沟通的决策能力。

## 30/60/90 天准备计划

| 时间 | 目标 | 可交付物 |
|---|---|---|
| 前 30 天 | 补齐数据处理与版本意识 | 一个有 Manifest、质量报告和抽检记录的公开数据集项目 |
| 31–60 天 | 补齐实验和评测闭环 | 一份受控消融报告，包含数据版本、指标、分桶与退化分析 |
| 61–90 天 | 补齐 Agent 可观测和产品视角 | Trace 数据模型、看板/查询、bad case 回流设计与 10 分钟讲解 |

## 三个常见误区

第一，只学工具不学验收：会 Spark、Ray 或 Flink 不能自动证明懂训练数据。必须能把工具输出接到质量和模型收益上。

第二，只看总分不看分桶：平均分提升可能掩盖安全、长尾语言、长上下文或工具使用能力的退化。

第三，迷信自动评分：LLM 评分、质量分类器和 Embedding 相似度都只是信号，不是最终事实。它们需要人工抽样、可靠参考和持续校准。

当你可以系统规避这三个误区，才真正从“能处理数据”走向“能为模型数据决策负责”。
