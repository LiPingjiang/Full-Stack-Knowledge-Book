# 14.5 面试准备：自我评价、实战题与反问清单

## 先准备一段 90 秒岗位理解

> 我理解这类 AI 数据处理与分析岗位不是传统的数仓 ETL，也不是单纯的数据清洗，而是连接训练数据、模型评测和生产 Agent 运营的闭环角色。数据侧需要把网页、代码、图文、标注和线上 Trace 做成有来源、有版本、有质量报告、可复现的数据资产；算法侧要区分预训练、SFT、偏好、轨迹和评测数据的不同质量标准；分析侧要通过数据版本、分桶评测和 Trace 回放定位模型质量、工具调用、检索或基础设施的问题。我会以“目标能力—数据标准—加工版本—实验验证—线上回流”组织工作，而不是只交付一条 pipeline。公开资料里阶跃的多模态、Agent 和 StepTrace 实践，也说明这个岗位需要同时理解训练数据与 Agent 运行数据。我希望承担的是把算法目标翻译成可生产、可验收数据方案的责任，而不仅是执行清洗任务。

这段话不要逐字背诵。它需要用你的真实项目替换其中的“我会”：如果做过数仓，讲你如何做数据契约、质量和回溯；如果做过 NLP/多模态，讲你如何做样本过滤和评测；如果做过平台或后端，讲你如何让 Trace、版本和成本可观测。

## 自我评价模板

以下是一版不虚构具体指标的通用自我评价。使用时应把“熟悉”“参与”等模糊词替换为真实项目、你承担的边界和可核验结果；没有做过的内容不要写成生产经验。

> 我具备数据工程与分析的复合能力，能够用 Python 和 SQL 将数据清洗、质量校验、统计分析与自动化流程串成可复现的 pipeline；在复杂数据问题上，我习惯先定义数据粒度、质量标准、版本与验收口径，再推进实现，避免只交付一次性脚本。我的优势是将技术实现与业务/算法目标对齐：面对训练数据或线上 bad case，我会从来源可信度、覆盖度、正确性、风险、成本和目标能力收益六个维度做判断，并通过抽样、分桶和对照实验验证结论。对于跨团队协作，我能将“模型效果不好”“需要更多数据”这类抽象问题拆解为可执行的数据方案、质量 Gate、指标看板与复盘项。后续我希望继续提升大规模多模态数据处理、Agent Trace 可观测和评测实验设计能力，在训练数据、模型评估和生产反馈之间建立更完整的数据闭环。

## 高频问题一：给你一批网页文本，如何定清洗规则并验证对模型有益？

先澄清目标能力和使用边界：是通用预训练、中文知识、代码问答还是某一领域任务；数据是否有授权、是否含 PII、是否允许进入训练。然后保留不可变原始快照，以内容哈希和来源元数据建立血缘。

清洗分层执行。第一层做解析、空文档、乱码、长度、模板、语言和精确重复等低成本规则；第二层做文档和段落级近重复、质量评分、风险/隐私检测；第三层按领域、语言、长度、难度和来源做分桶统计与分层抽样，校验误杀和漏放。最终将通过、拒绝、降权、人工复核四种结果和原因写入质量报告。

验证时冻结模型、Token 预算、训练参数和隔离评测集，只比较不同数据版本；同时报告总体分数、目标能力桶、退化桶、安全指标和单位成本。若只是“文本更干净”但目标评测无提升或安全退化，就不能称规则有效。

## 高频问题二：SFT 数据和偏好数据分别怎么看质量？

SFT 是“给定任务应如何完成”的示范，重点看指令是否清楚、上下文是否充分、目标答案是否正确、格式是否满足要求、工具/代码是否可执行、风格是否一致。可以用 JSON Schema、单测、检索证据、专家抽样等手段验证。

偏好数据是“同题候选中哪个更好、为什么更好”的相对信号。除正确性外，还要看候选是否可比、rubric 是否明确、标注一致性、长度与位置偏差、偏好理由是否可审计。偏好胜者并不自动等于可直接拿去做 SFT 的唯一标准答案。

## 高频问题三：评测集掉了 2 分，如何从数据侧排查？

第一步验证波动：固定随机种子、解码参数、评测脚本、裁判模型和样本版本，检查样本量、置信区间和是否存在评测服务故障。第二步确认变量：模型、Prompt、检索索引、工具版本、训练数据、Tokenizer、数据顺序是否只有预期项变化。第三步做分桶：按任务、领域、语言、长度、难度、工具依赖和安全类型找下降集中区。第四步回溯数据版本和 Trace：是否误删了某类样本、是否引入近重复污染、是否出现输出格式回归、工具超时或 RAG 召回异常。

最后给出的结论必须有证据。例如“下降主要来自工具类任务，Trace 显示工具参数校验失败率上升，模型文本桶稳定，因此优先回滚工具 Schema/Prompt 而非盲目追加训练数据”。

## 高频问题四：如何设计 Agent Trace 数据模型？

采用 `session → trace → span → tool_call/evaluation` 的层级。Session 描述多轮用户目标；Trace 对应一次可判定的任务执行；Span 表示模型调用、检索、工具、沙箱等步骤；Tool call 保存参数引用、返回码、重试和耗时；Evaluation 保存可执行检查、Rubric、人工分或用户反馈。所有事实表必须关联 model、prompt、tool、dataset/index、环境和代码版本。

常用指标包括按任务类型和版本计算的任务成功率、P50/P95 延迟、单任务 Token/工具/沙箱成本、工具失败率、重试率、安全拦截正确率和会话完成率。大文本和用户内容默认脱敏或保存受控引用，不能为了回放便利而无边界存储。

## 高频问题五：Spark Shuffle 倾斜或实时消费延迟飙升怎么处理？

Spark 先用 UI 确认是否个别 Task 明显慢，再定位倾斜 key、Join 方式、分区数、数据膨胀和 Spill；根据小表大小、倾斜比例和业务语义选择广播 Join、AQE、倾斜 key 拆分/加盐、预聚合或自定义分区。不要把“加内存”当作解决数据分布问题的万能答案。详见 [6.4 Spark](../part6-bigdata/04-Spark.md)。

实时链路先区分是 source 读入慢、算子反压、状态膨胀、sink 写入慢还是下游依赖异常；看 consumer lag、checkpoint、watermark、busy/backpressure、状态大小、写入延迟和错误率。处理顺序应是先恢复正确性和积压可控，再做扩容、并发、批量和数据模型优化，而非只盯吞吐数字。

## 一个可展示能力的作品集题目

做“Agent 轨迹质量分析与数据回流平台”的最小 Demo。输入是模拟或合法公开的 Agent Trace；实现 Trace/Span/ToolCall 逻辑模型、质量/成本/延迟聚合、按模型版本和任务桶的回归看板、失败分类、Bad case 标注队列和 Dataset Manifest。最后写一份消融报告：从某类失败 Trace 构造少量候选 SFT/评测样本，说明为什么没有直接回灌、如何做脱敏与去污染、如何验证收益。

这个题目比“爬网页做清洗”多了一层关键能力：它能展示你理解训练数据、评测、Agent 产品和数据治理是同一个闭环。

## 简历写法：关键词应服务事实，而不是堆砌

可以围绕真实经历组织为“数据目标—你做的工程—质量/实验方法—业务结果”。例如：“建设数据版本与质量校验流程，覆盖来源血缘、规则过滤、抽样审计和异常告警；将问题样本按任务桶回流至评测集，支持版本级回归分析。”只有做过 Spark/Flink/Doris/Iceberg/Ray/向量库等组件时再写具体技术名，并说明用在什么数据规模和什么难题上。

不建议写“精通 PB 级多模态数据工程”这类无法被追问验证的表述。更可信的方式是明确自己的规模和边界，例如“在 TB 级日志/文件数据中负责某一处理链路”，再说明可迁移到更大规模时会怎样分区、并行、监控、重跑和控制成本。

## 推荐反问

第一，这个岗位主要服务哪条闭环：预训练语料、后训练/评测，还是生产 Agent 的 Trace 与数据平台？三者的占比如何。

第二，数据需求进入团队后，是否有统一的数据集版本、许可证/隐私审批、质量报告与训练消费登记；当前最痛的断点是什么。

第三，模型效果出现回归时，团队如何区分训练数据、模型、Prompt、工具、检索与基础设施问题；是否已有可回放的 Trace 和分桶评测。

第四，这个岗位与算法、标注/供应商、产运、法务安全的协作机制是什么；谁定义数据验收标准，谁拥有最终上线门禁。

第五，岗位在前六个月最期待交付什么：一条数据 pipeline、一个数据集版本体系、一个评测分析闭环，还是生产可观测平台？成功如何量化。

这些问题不是礼貌动作，而是在判断团队到底需要“只接需求的人”，还是愿意让数据工程师对数据资产和效果闭环真正负责。

## 最后的准备原则

准备这类岗位时，最容易低估的是“把数据结论讲得可证伪”。不要说“数据质量提高了”，要说提高的是哪项质量信号、抽样误差是多少、哪个评测桶验证了收益、代价和风险是什么；不要说“模型效果差”，要说 Trace 里哪类失败占比上升、哪个版本变化相关、下一步验证什么假设。

当每一个结论都有数据版本、指标口径、对照实验或 Trace 证据支撑时，你展现的就不再是一个会写脚本的人，而是能对 AI 数据决策负责的人。
